# Harness Prompt · Agent Harness 实施 Spec（给 agent 的可执行版）

这份文件是正文《Harness Study》的**可执行配套材料**。正文讲"有哪些机制、为什么这样设计"，这份讲"按什么顺序动手、每一步怎么验证做对了"。

**怎么用**：把这份文件连同你的具体场景需求（"帮我做一个 X 场景的 agent"）一起交给编码 agent。agent 按 Phase 0 → 1 → 2 → 3 的顺序执行，每个 Phase 末尾的**完成判据（gate）不通过，就不进入下一个 Phase**。判据回答的是"怎么验证做对了"，而不是"做了什么"：没有可验证的证据，就当这一步没完成。

**全局约定**：

- 文中所有具体数值（token 占用阈值、单工具输出上限、工具数量、通过率门槛等）都是**起步默认值**，按场景实测调整，不是普适常数。有文献出处的会单独注明。
- 每个 Phase 标了正文对应的章节（`↪`），需要展开原理时回到正文对应位置细读。`↪` 行里的 P0、P1、P2 是正文第五章给机制标的优先级：P0 是最小可用版本必备，P1 是上生产前要补的，P2 是规模化之后再做的。
- 主力用**强模型**。弱模型跑不稳多轮工具调用，会在 Phase 1 的 gate 上反复失败。
- 每个 Phase 末尾的完成判据尽量配**可运行的检查**：一段脚本、一条断言、一个能跑的对照，不要只有文字描述。执行这份 spec 的是 agent，而文字形式的判据恰恰最容易被 agent 一句"已满足"糊弄过去（这正是产物声明不符（AP04，见附录 F）的温床）；判据能跑，就没有糊弄的空间。例：Phase 1 的 gate 至少要配"用假的模型服务（fake provider）跑通一次完整 ReAct 循环，并断言每个工具调用都有配对的工具结果"这样的硬检查。
- 这份 spec 的覆盖范围取折中：通用 runtime、场景收窄、成本结构三段（来自实践总结），加上行为探测、四原则自检、机制准入检查。Harness Lab 五层、可组合性三轴这两块进阶内容只给判断标准，不展开，需要时回正文。

## Phase 0 · 行为探测 · 动手前先摸清模型脾气

**目标**：动手搭 runtime 之前，先给你要用的模型端点跑一套诊断，也就是行为探测（behavioral probing，本书也称"把脉"），产出一张画像：这个模型需要哪些机制、不需要哪些、哪些机制对它是陷阱。价值不在"了解模型"本身，而在于**缩小后面要试的机制范围**，并**提前标出会起反作用的陷阱**。

**方法核心：探针三段式**。每条探针由三部分组成：

1. **刺激**：一个为暴露某一种行为而设计的极小任务（不求难，求能逼出这个行为）。
2. **行为分类**：判断它"是怎么做的"，而不是"做得对不对"。优先用程序判定（崩没崩、译没译、读了几次，都是二元或可计数的），只在模糊的维度才让模型当裁判。
3. **机制推论**：根据行为类别，给出**一个配置决策，加一个可以被后面的消融实验证伪的预测**。探针的产出是配置决策和可验证的预测，而不是分数。

**四族探针**（按"出错后果"从硬到软分族，从 A 往 D 跑）：

- **A 族，协议层**：出错时 harness 直接崩溃，而不只是效果变差。优先级最高，二元硬判定。典型探针：给一个带嵌套对象和数组的复杂严格 schema 工具，看模型是在请求层直接失败，还是能正常注册和调用。直接失败，就必须做 schema 规范化层。
- **B 族，工具使用层**：效果变差但不崩溃。典型探针：给一个需要先用工具的多文件任务，数它动手前读了几次。反复读、迟迟不动手，就要加"读取完整性"或"证据充分性"一类的检查。
- **C 族，指令遵循层**：典型探针：任务里用英文标题，看模型在中文上下文里会不会把标题译成中文。会译，verifier 就不能只认英文固定字符串，要开启多别名匹配。
- **D 族，自我纠错层**：最深，也最能区分模型。典型探针：给一个会报错的操作，看模型是盲目重试，还是能读懂错误信息、换个方法。

**✅ 完成判据（gate）**：

- [ ] A、B、C、D 四族各跑了几条探针，每条都归入一个行为类别（程序判定的要留下原始观察：崩了、译了、读了 N 次）。
- [ ] 每条探针都产出了"配置决策"和"可证伪预测"两项，而不是只留一个分数。
- [ ] 产出一张画像表：这个模型**必须开**哪些机制、**不需要**哪些、哪些是**陷阱**。这张表直接缩小 Phase 1–3 要做的机制范围。

**注意**：行为探测只给**定性的先验判断**，不给定量结论。"开 X 能挽回一部分漏掉的工具调用"，这个"一部分"到底是多少，要等 Phase 3 的消融实验拿到干净数据再回答。行为探测看一眼就能确定的，是"崩没崩""译没译"这类事实，不依赖不同配置之间的精确对照。

`↪ 正文：行为探测（把脉），Harness Lab 三步中的第一步`

## Phase 1 · 通用 Agent Runtime · 不绑语言，不绑场景

**目标**：搭一个能对着任意工具集发起 ReAct 循环的通用 runtime。这一步不碰具体业务，只把框架跑起来。

### 1.1 模块划分：五块

三大块加两块支撑：

- **engine**：跑循环。主循环就是一个 ReAct：发消息 → 收回复 → 有工具调用就执行 → 结果写回 → 判断是否终止。再加一个状态机管理多轮：等用户输入、等用户确认、跑完、出错。每轮开头先查取消信号，停止要立即生效。
- **llm**：做多供应商抽象。抽成一个统一接口，各家差异在适配层处理。`thinking`、reasoning 这类参数每家写法不同，用 `extra` 字段各自配置。**发往国内模型服务的请求，在代码里按域名显式绕过代理**；别只靠环境变量，不同的库分别读大写 `NO_PROXY` 和小写 `no_proxy`，要设环境变量就两个同时设。
- **tools**：管工具的注册和执行。每一步都重新加载工具列表，**不要缓存**：POST hook 里新注册的工具，下一轮要能看见。
- **storage**：存 session 和 checkpoint。
- **types**：集中定义消息和工具签名。

`↪ 正文：Agent Loop（§5.1，P0）/ Model Adapter & Routing（§5.2，P0 边界）`

### 1.2 三条协议与运行时红线

- **消息协议**：assistant 消息发出工具调用（OpenAI 协议里是 `tool_calls` 字段，Anthropic 协议里是 `tool_use` 块）之后，下一条必须是对应的工具结果（OpenAI 是 role 为 `tool` 的消息，Anthropic 是 user 消息里的 `tool_result` 块），中间不要插入别的消息，否则下一轮请求会被 API 以 400 拒绝。
- **严格 schema 规范化**（如果 Phase 0 的 A 族探针显示模型对严格 schema 敏感）：注册工具前先把 schema 规范化，含嵌套对象、数组的要处理成模型能接受的形式。
- **取消信号**：每轮开头检查。持锁期间只把 engine 取出来，取出后立刻释放锁；然后异步执行并监听取消信号，成功、取消、出错三条路径都要保证把 engine 归还。不要在锁里同步等待长任务。

`↪ 正文：Model Adapter & Routing（§5.2）`

### 1.3 工具层

工具层不只是"注册和执行"。**工具调用的质量**（模型真的去调、调得对、结果干净地写回、失败后能自己修正）由下面几组做法共同决定。

**接口与防护**

- Tool 抽象按正文的五个字段定义（`name`、`description`、`input_schema`、`execute`、`policy`；policy 即 ToolPolicy，包括 allowed_paths、timeout、requires_confirmation 等）。Registry 对每次工具调用做三件事：schema 校验 → 策略决策（通过、人工审批或拒绝）→ 执行，并把审计记录写进 trajectory。
- 单工具输出设**硬上限**（起步默认值：读文件 20k、搜索 10k、shell 15k），超限的走下面的「结果收口」。
- shell 和 git 命令一律用参数数组调用，不经 shell 解析：Node 用 `execFile`，Python 用 `subprocess.run([...])` 且不设 `shell=True`，Go 用 `exec.Command`。**拒绝字符串拼接**，防止命令注入（command injection）。

**调度：工具批次的四种模式**（一批工具该并发、该串行，还是该停下）

- **parallel_read**：只读、无副作用、无路径冲突，默认并发（read_file、grep、glob、list_dir、web_search、web_fetch）。
- **sequential_write**：写文件、改工作区、变更状态，默认串行（write_file、edit_file、shell_exec、git_* 及任何标了 DANGEROUS 的工具）。
- **barrier**：需要权限确认、危险操作、批次切换，或者需要根据上一批的观察重新决策，就明确停下来，在这个切换点做决策。
- **background_sidecar**：交给一个轻量的旁路 agent，与主线互不干扰。
- **主线原则**：单个 agent 批量执行工具 → 结果收口后写回 → 必要时才启用旁路 agent。不要一上来就开 sub-agent：安全边界、上下文隔离、结果汇总三方面的成本，多数任务承担不起。

**结果收口：工具结果不以原文直接进入主对话**

- 一批工具执行完，产出两样东西：原文存入 **ArtifactStore**（返回一个引用），另加一份 **observation stub**（精简摘要，起步默认值约 200 字符，进入上下文）。主线程只读 stub；需要原文时，模型自己再调用 `read_observation(obs_id)` 或 `read_artifact` 按需取。口诀：**全文提取，按需注入，不截断，不跳页**。
- stub 必须带元信息 `truncated:true`、`size`、`preview_truncated_at`，以避开两种相反的失效模式：**过载**（全部塞进上下文，触发中段遗失（lost in the middle），花了 token 却没被模型注意到）和**失真**（粗暴截断丢了信息，agent 还不知道自己看到的是截断版）。**原文必须持久存储、可以按引用取回**，只截断而不保存原文，仍然是失真。
- 配套给 agent 的三句 prompt：① 反馈内容大时只看 stub，要完整内容用 `read_observation` 取；② stub 带 `truncated` 标记时，看 `size` 判断要不要取全文；③ `PreprocessError` 一类错误是多模态内容的预处理失败，不是工具调用失败，可以重试或换一种方式。

**错误返回：决定 agent 能不能自己修正**

- **可操作（actionable）**：说清"哪里错了、怎么改"，但不要丢掉原始调用栈（stack trace）里的有用信息。例：`file_path 'data/output.txt' 不存在，是不是 'data/input.txt'？先 list 一下 data/`，比抛一个原始的 `FileNotFoundError` 强得多。按作者经验，它是 ACI（智能体-计算机接口）设计里提高工具调用正确率的关键一环；不过正确率的提升是整套 Tool Registry 与 ACI 设计共同作用的结果，不是单靠这一条。
- **原始错误还是脱敏错误，按工具来源区分**：内部代码实现、执行过程完全可控的工具，返回原始错误（含细节，方便 agent 自己修正）；接外部数据源、执行结果含外部内容的工具，返回脱敏后的错误（去掉调用栈、内部路径、敏感字段）。也可以按环境区分：开发环境用原始错误，生产环境用脱敏错误。**错误返回是提示词注入（prompt injection）最常见的注入点之一**。

**建议默认配上 web_search 和 web_fetch**

- 模型权重是冻结的，知识有截止日期。截止日期之后的事实（新的版本号、刚改过的 API、当前的文档）模型只能猜，猜不准就会幻觉。这两个工具把"训练之后的世界"接进来，现查现核，往往比再调一轮 prompt 更能提升质量。
- 两条配套要求：① 返回内容量大（一次几十条结果、一篇几万字）时，必须走上面的「结果收口」，不要让原文灌进主对话；② 抓回的内容是外部输入，要先判断来源可信度或交给 verifier，不要把搜到的错误信息直接当成事实依据。

**排查：该调工具却没调**

模型该调工具，却只输出一段文本，有三种成因，分别在三个层面，对策完全不同。按响应解析 → 请求参数 → prompt 装配的顺序依次排除，比反复改 prompt 或换模型快得多：

1. **响应解析层（假阴性）**：模型可能把调用写成了正文里的文本标签（如 `<tool_call>…</tool_call>`），没有进入结构化的工具调用字段（OpenAI 的 `tool_calls`、Anthropic 的 `tool_use` 块）；Adapter 只认结构化字段，就把它当普通文本丢掉了。对策：解析层在结构化字段之外，再用正则兜底提取文本标签。
2. **请求参数层**：默认的 `tool_choice: auto` 表示可调可不调。某一轮必须用工具（必须查库、必须写盘）时，把 `tool_choice` 设为必须调用工具（OpenAI 写 `required`，Anthropic 写 `any`），或者指定具体工具。**按轮、按场景开启，不要全局常开**（长期强制调用会逼模型在不该调时硬调，制造噪声）。
3. **prompt 装配层**：过长的中文 prompt 会让某些模型跳过工具调用、直接用文本作答。把"要调用工具"的指令写短、放在靠前的位置，长说明拆开。

### 1.4 上下文压缩：三种力度

- **micro**：压缩力度最轻的一种，对单个工具的大结果做局部收口（stub 进上下文，原文存到外部，用 `read_observation` 按需取）。具体机制见 1.3「结果收口」，这里只标出它在三种压缩力度中的位置。
- **auto**：token 估算达到窗口的 60–70%（起步默认值，常用 70%）时，用小模型把整段历史摘要。摘要**必须保留四类信息**：未闭合的 `tool_call_id` 及其状态；每轮的关键决策和理由；artifact 的引用 id；verifier 的失败信息。丢了任何一类，agent 后续都会编造（编出假的 observation、假的 id，或者再撞一次同样的错误）。
- **rolling window**：最粗暴的兜底，超长时直接丢掉最早的几轮。
- **压缩后必须重新注入任务目标和 system 身份**，否则几十轮之后 agent 会偏题，以为自己在做别的事。

`↪ 正文：Context（§5.4，P0）/ Prompt Assets 身份重注入（§5.5，P0）`

### 1.5 可观测性：从第一行代码就开始埋点

- 埋点放在**决策点**，而不是执行点，也就是机制判断"该不该做"的地方。
- 四种状态都要记：触发并执行了；条件不满足，没执行；触发了但被拦截；执行出错。
- **没有事件是最危险的信号**，说明这段代码路径根本没走到。
- 循环检测拦截重复的工具调用；介入消息先放进队列，等本轮工具结果处理完再统一推送，不要在中途破坏消息协议。

`↪ 正文：Observation Surface（§5.6，P0）/ Trajectory（§5.7，P0）`

### 1.6 Safety 控制面起步：横切所有机制，而不是第 9 个机制

Safety 不是又一个 runtime 机制，而是横切在所有机制之上的控制面：每次工具调用、状态变更、产物写入都必须经过它，就像操作系统的系统调用关口，没有例外。完整的形态是 **4 层权限决策模型**：

- **permission mode**：agent 整体的运行模式（只读、可写工作区等几个级别）。
- **allow、deny、ask 规则**：按工具、按参数模式配置的细粒度规则，采用**默认拒绝加显式允许**（允许 `git status`，拒绝 `git push`，询问 `git commit`）。
- **Hooks**：在调用前后运行的用户脚本，做规则表达不了的复杂决策。要**按完整的命令词和规范化后的意图匹配，而不是按原始命令字符串的前缀匹配**，否则放行了 `cargo check`，`cargo checkpoint` 也会被放过（cargo 会把它当作 PATH 上的外部程序 `cargo-checkpoint` 执行）。
- **sandbox**：OS 级沙箱（Seatbelt、bubblewrap、容器），限定文件读写范围和网络出口。前三层的逻辑判断被绕过时，它是最后一道防线。

起步至少先做到两条：

- **关键安全判断写在代码里，而不交给模型**（Hard Gate）：危险操作（删文件、推代码、发网络请求、花钱）的拦截判断写在代码层，不靠 prompt 让模型自觉。模型只在软性判断（判断内容是否有害）上辅助，不做最后一道防线。
- **人工审批关口（HITL approval gate）**：高影响操作（删数据、转账、部署、发邮件）标上 `requires_confirmation`，agent 调用前先交给人确认才执行，不让 agent 自己决定做不做。审批模式沿父子 agent 链传递（sub-agent 默认继承父 agent 的设置，不能更宽松）。

`↪ 正文：Safety 控制面 · 4 层权限决策模型 + HITL（§5.9，cross-cutting）`

### 1.8 前端接入（如果有）

后端是**唯一的真相源**，不要在前端另存一份状态副本。切换 session 时从后端拉取 `last_messages` 和 `is_running`。

**✅ Phase 1 完成判据（gate）**：

- [ ] runtime 能对着**任意工具集**发起 ReAct 循环，至少跑通一个任务。
- [ ] trajectory 有完整的事件流，事件埋在决策点，覆盖四种状态。
- [ ] 危险命令（删除、推送、花钱）被**代码层**拦住：写一个会触发拦截的任务，验证拦截真的生效，而不是 prompt 里写了一句"不要删"。
- [ ] 高影响操作（删数据、转账、部署）会触发人工审批，agent 调用前真的停下来等人确认。
- [ ] Hard Gate 能对一个任务判出 PASS 或 FAIL。
- [ ] 工具结果走收口：跑一个会返回大量内容（如 5000 行）的工具，确认主对话里只进了 stub，原文能被 `read_observation` 取回，stub 带 `size` 和 `truncated`。
- [ ] 连续跑几十轮不偏题（压缩后身份和目标的重新注入生效）。

## Phase 2 · 从通用到场景的收窄 · 不绑行业

**目标**：通用 runtime 跑通后，针对具体业务场景（客服、标书、质检、运维、翻译、数据分析等）做收窄。方法对所有行业都一样，分八步。

1. **建评测集**：从 3–5 个典型任务起步，每个任务都有可以自动判定的通过或失败标准、预期的工具调用序列、最终的数据库状态。评测集和代码一起演化，不要"做完再测"。评测集分成开发集和留出集两部分：日常调 prompt、调规则只看开发集；留出集不参与调参，每次改动前后都跑，只用来检查开发集上的提升是否还在，避免对固定测试集过拟合（AP20，见附录 F）。上线后遇到的失败输入，要回流进评测集作为新的判例。
2. **工具收窄**：通用 runtime 可能挂着几十个工具，业务场景一般只用一小部分（起步默认值 8–15 个）。用白名单只放行这些工具，或者把其余工具列进黑名单**显式禁用**；不要只是放着不调，留在上下文里的工具会分散模型的注意力，提高选错工具的概率。
3. **工具描述强化**：每个业务工具的 description 里直接列出必填字段名、类型、枚举值。字段是 `user_id` 还是 `userId`，是数组还是对象，枚举有几个值，都不要让模型猜。**按作者经验，这是投入产出比最高的单点优化**，通常比反复改 system prompt 有效得多。
4. **策略规则引擎**：业务规则不要全堆在 system prompt 里（模型跑几十轮就忘了）。做成"**调用 X 工具前注入结构化提醒**"：取消操作前弹出资格检查，删除前弹出二次确认。即时提醒比全局声明有效得多。
5. **提示词分层**：系统层写角色和能力边界，场景层写业务规则和禁止的行为，执行层写输出格式。三层分开，方便单独调整和做 A/B 测试。
6. **开推理模式**（如果模型支持，且 Phase 0 显示有收益）：多步判断、数值计算、规则检查密集的场景开，简单问答别开（贵、慢、没收益）。
7. **跑消融实验**：每加一个机制，就关掉它再跑一遍评测集，看分数掉多少。正贡献的保留，负贡献的砍掉，接近零的看维护成本再决定。关键在这一步：有些"看起来正确"的机制，关掉后结果反而更好，单元测试看不出来。工具调用质量方面的一个具体反例：**参数容错**（工具参数解析失败或不符合 schema 时，harness 自己兜底、照常调用工具）看似帮模型省事，实际遮蔽了模型本该收到的错误信号，局部正确、全局有害；单元测试看不见，要靠单个机制的消融或专项审计抓出来。消融要细到单个机制的开和关，不要整组一起开关。
8. **失败归因分维度**：不只看通过率，还要看：**该调的工具调了没有**（没调，就回到 1.3「该调工具却没调」按三处排查）；工具调用的参数对不对；数据库的最终状态对不对；回复里该说的数字、条款说了没有；该走的流程走完没有。单一维度的评测会掩盖真实问题（数据库对了，但没说出数字，在客户看来就是没把事办成）。

### 2.1 什么时候从"收窄"升级为"独立的副 harness"

副 harness 指按任务动态调起、自带领域规则的子 harness。如果一个场景的领域知识塞进主 agent 的上下文会撑爆，或者它需要独立演化、独立迭代，就把它做成**独立的副 harness**。判断标准是**5 个维度的领域模型是否齐全**（正文借用"本体"一词称之为"5 维度本体"，这里指领域模型 schema）：

1. **领域实体**：这个领域有哪些"东西"（如 PPT 副 harness 里的 slide、layout、content_block）。
2. **实体属性**：每个实体有哪些字段，以及字段的类型和约束。
3. **关系规则**：实体之间的逻辑约束（比如 layout 决定 content_block 的类型）。
4. **状态机**：实体的合法状态和转换路径（draft → review → approved → exported）。
5. **操作集**：副 harness 对外暴露的工具集合。

**判断标准**：5 个维度齐全，才算设计完成；缺的维度越多，离真正的副 harness 越远；缺三个或更多，就还停留在"万能 prompt"阶段，不算副 harness。只写一个 5000 字的 system prompt 让模型自由发挥，不等于副 harness。

`↪ 正文：副 harness cell 5 维度本体（§8.5）`

### 2.2 verifier 从 Hard Gate 扩展到三层

Phase 1 只上了 Hard Gate。这里按需补上另外两层：

- **第二层，Outcome Judge**：用**另一个模型**对最终产出做语义评分。评审模型与 agent 所用的模型要**跨厂商或跨模型家族**，以减轻偏好泄漏（preference leakage：评审模型会偏袒与自己同一家族或有继承关系的模型所生成的内容）。只有开放式任务才需要这一层。
- **第三层，PRM（过程评分）**：对推理过程逐步评分。长任务跑稳之后再加，为消融实验提供逐步的信号。
- **组合规则**：Hard Gate 不通过，整体直接判失败，不让模型在失败的任务上靠过程分蒙混过关。

`↪ 正文：Verifier 三层 + 三层组合策略（§5.8）`

**✅ Phase 2 完成判据（gate）**：

- [ ] 评测集里每个任务都能**自动判定**通过或失败，且开发集与留出集已经分开。
- [ ] 收窄后跑评测集，分数比通用版高，而且**用消融实验证明**这是收窄带来的，不是错觉；留出集上的分数没有明显低于开发集。
- [ ] 失败按多个维度归因（参数、数据库状态、该说的话、流程），而不是只看通过率。
- [ ] 如果做了副 harness：5 个维度齐全；如果只是收窄：工具白名单只含场景用到的工具，关键规则做成了调用前注入。
- [ ] 如果上了 Outcome Judge：评审模型与 agent 的模型跨家族。

## Phase 3 · 成本结构 + 机制准入 · 钱花在刀刃上

**目标**：资源不平摊，瓶颈在哪里就投在哪里。顺序错了，花同样的钱拿不到同样的结果。

### 3.1 投入顺序

1. **先投评测集**：没有评测就是闭着眼调优，后面所有改动都说不清"到底有没有用"。粗糙到只看通过率，也比没有强。
2. **再投工具描述**：按作者经验，这是单点投入产出比最高的位置。模型猜字段名猜错一次就浪费一轮，几十轮下来浪费的轮数可能相当可观。
3. **接着投策略规则引擎**：把业务规则做成"调用前注入"，模型就不会忘。做完这一步再看表现，比直接换模型便宜得多。
4. **推理模式看任务**：多步判断、规则检查、数值计算密集的场景开，简单问答别开。
5. **模型升级放最后**：贵、不可逆（换了模型要重跑评测）、对大部分场景提升有限。真正卡住通过率的一般不是模型能力，而是外围机制没调好。**第一步就换模型是最常见的误区**：钱花了，分数没涨。

**基础设施（压缩、观测、循环检测、锁和取消）是入场券，不是投入**：不做，一切都谈不上；但做到"能跑就行"的程度就够了，过度工程反而拖慢迭代。

### 3.2 按场景类型分配

| 场景类型 | 先投哪里 |
|---|---|
| 客服 / 规则执行类 | 工具描述 + 策略规则，再考虑推理模式 |
| 代码 / 复杂规划类 | 推理模式 + 强模型，工具描述和规则次之 |
| 长对话 / 多轮类 | 压缩 + 观测，不然跑几十轮自己就崩 |
| 高并发 / 低延迟类 | 便宜模型 + 工具输出缓存 + 简化工具集 |

### 3.3 机制准入检查：每个进入默认配置的机制都要通过

不能只凭"机制看起来合理"就默认启用。每个机制进入主 harness 的默认路径之前，至少满足四条：

1. **能改变真实行为**：不只是多加了 DTO、schema 或日志字段。
2. **有开关消融数据**：关掉后能看到通过率、成本、延迟或可靠性的变化。
3. **有机器可读的 trace**：记录触发原因、规则 ID、输入摘要和结果。
4. **通过稳定性检查**：收益不能只靠偶然通过。做法有三：多次复跑，且每次都从干净状态开始（关闭响应缓存、不固定 seed、不共享文件、记忆与工作区），否则复跑之间不独立，稳定性会被高估（复跑不独立，AP01，见附录 F）；做输入扰动测试，即给输入加不改变任务含义的微小变化（如每次 run 加一个随机 nonce、同义改写、打乱无关字段），看结果是否稳定；同时报告 pass@1 与 pass^k（k 次全部通过的比例）。

达不到这四条的机制，保留为**实验开关**，不进默认配置。**负贡献的机制要及时砍掉**：继续维护等于双重损失（占资源，还拉低通过率）。舍不得砍"看起来正确的代码"是常见错误，消融一测就能看出来。

**✅ Phase 3 完成判据（gate）**：

- [ ] 投入按上面的顺序走过，评测集在模型升级**之前**就已建好。
- [ ] 每个进入默认配置的机制都通过了准入四条（尤其要有开关消融数据）。
- [ ] 负贡献和接近零贡献的机制已经砍掉，或降为实验开关。

`↪ 正文：起步建议四维度（各章末）/ 机制准入检查（本章 §3.3）`

## 横切 · 四原则自检 · 每个 Phase 收尾时跑一遍

每个 Phase 完成时，用控制论四原则（本书借用控制论的概念作类比，见第九章）各查一遍：任何一项没守住，都回去补，不要带着问题进入下一个 Phase。遇到任何 bug，也先把它归到这四项中的一项。

- **可观测**：有没有静默失败（错误被 try/catch 吞掉，没有产生事件）？有没有隐藏状态（agent 内部状态没有对应的事件）？"声称与实际的差距"（declared_vs_executed gap，即 agent 声称做了的，与工具或 verifier 实际观测到的之间的差距）持续偏高，就是预警信号。
- **可控**：控制点会不会被绕过（Hook 与白名单绕过，AP13，见附录 F）？工具粒度是不是太细，让模型选不准？有没有"假落地"，即机制在仓库里，但生产路径上什么都不做？
- **稳定**：每个机制有没有上限（max_turn、max_token、max_depth、max_retry）？这些上限都能监测到吗？有没有循环盲区、上下文膨胀、奖励投机（reward hacking）？
- **闭环反馈**：每个改动有没有消融数据支撑？"我觉得这样更好"但没有数据，就是闭环反馈没守住。

`↪ 正文：控制论四原则与反模式的对应（§9.2）`

## 进阶判断标准 · 什么时候才上（不展开，需要时回正文）

下面几块进阶能力默认**先不上**，满足判断标准再上。其中的数字除注明出处的以外，都是起步默认值，按场景调整。

- **多智能体 / sub-agent fork-join**：先回答"单 agent 跑这个任务，10 次 run 的通过率是多少？"没跑过，就先跑单 agent；通过率已经在 80% 以上，就别上多智能体，优化单 agent 更划算。据 Anthropic 多智能体研究系统文章（2025-06），单个 agent 的 token 消耗约为普通对话的 4 倍，多智能体系统约为 15 倍；编码这类子任务之间依赖强、可并行部分少的场景，尤其别上。
  - **如果判断必须上**（任务超过 60 轮，子任务真正独立、可分别验证）：再问控制流能不能预先确定，即哪些子步骤并行、谁交叉验证谁、结果怎么汇总，开跑前就清楚吗？**能预先确定**，就把这段编排写成**确定性脚本**，交给运行时在后台跑（dynamic workflow）：模型推理只发生在叶子 agent 干活时，主 agent 的上下文最后只剩一个汇总答案，省掉主 agent 临场编排的那层开销，编排也可以重跑、可以审计。**不能预先确定**（探索性任务，下一步要看上一步的结果），就只能让主 agent 临场编排，成本回到约 15 倍的预期。gate：编排脚本能脱离某次具体的 run 重跑，每一步的 `hands_off`、`calls_tool` 都记进 trajectory。
  - **边界**：dynamic workflow 降低的是编排成本，不放宽准入门槛。单 agent 优先、10 次 run 通过率 80% 以上别上、编码类强耦合任务别上，这几条不变。
  `↪ 正文：多 agent 过度拆分（AP09）+ dynamic workflow（§5.1.5 末段 + 脚注 / §5.1.6）/ fork-join 并发（§6.6）/ 拓扑轴（§八）`
- **dynamic harness，即副 harness 的运行时路由**：这是 §2.1"要不要造一个副 harness"之后的下一步，也就是 harness 跑起来之后，**按任务在多个副 harness 之间动态选择**。先回答两个问题：① 你是不是真的有两个以上 5 个维度齐全的副 harness（不齐，就先把单个做齐，回到 §2.1）；② 能不能靠"实体特征"而不是"模糊的文本"判断该走哪一个（判断不出来，就还不到上路由的时候，单个 harness 跑）。上了路由，要满足 3 条可验证的规则：路由依据任务的实体特征；主 harness 只能调用已挂载的副 harness，不能凭空造；每次路由决策都写进 trajectory（写一个任务，验证 trajectory 里能查到"为什么走 A 不走 B"）。dynamic harness 和上面的 dynamic workflow 是相互独立的两件事：前者管挂哪些工具、策略和 verifier，后者管控制流由谁掌握。**ReAct + dynamic harness + dynamic workflow** 这种组合是正文作者正在实践、仍在演进的方向，这里按当前实践给出方向，不当作定论。在两者之间怎么选，主要看奖励信号的强弱：开放、没有标准答案的弱奖励任务偏向 dynamic workflow（用编排里内建的交叉验证顶替缺位的硬性 verifier）；标准化、反复出现、Hard Gate 判得了的强奖励任务（To B 核心交付的典型形态）偏向 dynamic harness（把机制固定下来，用硬性验证收口）。`↪ 正文：主副 harness 路由规则（§8.7 "写什么 prompt"）/ dynamic harness（§5.1.6）`
- **Harness Lab 工作台（Observe-Score-Ablate-Tune-Iterate 五层）**：先回答"8 个 runtime 机制加 Safety，项目里已经有几个稳定了？"6 个以上才考虑。harness 自身的通过率如果还在按周浮动 10 个百分点以上，就先别做 Ablate（消融），这时跑出来的差异大多会被噪声淹没，先把评测稳定下来。`↪ 正文：Harness Lab（§七）`
- **跨厂商协议（A2A 等）**：当前阶段建议自己定义 JSON-RPC schema，写成文档作为内部标准，不要把架构绑在仍在演进的外部规范上。`↪ 正文：交互边界轴（§八）`

## 使用顺序

1. **Phase 0 行为探测**先跑：便宜的定性诊断，先把后面要试的机制范围和陷阱标出来。
2. **Phase 1** 搭通用 runtime，不考虑业务，把框架跑起来。gate 通过了再往下走。
3. **Phase 2** 跟业务一起演化、做收窄，不要等"通用版做到完美"再收窄。
4. **Phase 3** 在任何阶段都可以对照：它决定的不是"做什么"，而是"先做哪个"和"钱花在哪"。
5. **四原则自检**在每个 Phase 收尾时各跑一遍。

总逻辑一句话：**先摸清模型脾气，再搭一个能跑的东西，针对场景削出锋利的刀，然后把钱花在刀刃上。每一步都用可验证的 gate 确认做对了，没有 gate 证据就当没做完。**
