# Agent Harness 通用落地提示词（评测先行）

三段通用指令，输给编码 AI，可以直接按此搭建和落地一套 agent runtime。
三段之间是上下游关系：先搭通用 runtime，再针对场景收窄，最后按成本结构分配资源。
提示词里的时长、阈值、百分点等数字都是作者项目中的经验起点，已在文中标出，按场景调整，不是硬性指标。

---

## 第一段：通用 Agent Runtime（不绑语言）

```
搭一个 agent runtime。下面的时长和阈值都是经验起点,按场景调整。
Python 最快两天跑通、TypeScript 方便接前端四天、Rust 稳但工程量大
要一周。模块划三大块加两块支撑:engine 跑循环、llm 做多供应商抽象、
tools 管注册和执行,storage 存 session 和 checkpoint,types 集中定义
消息和工具签名。

engine 的主循环就一个 ReAct:发消息→收回复→有工具调用就执行→结果回
写→判终止。再加一个状态机管多轮:等用户输入、等用户确认、跑完、出错。
每轮开头先查取消信号,stop 要即时生效。

llm 抽成一个统一接口,各家差异在适配层处理。thinking 参数每家写法不
同,用 extra 字段各自配。消息协议不能乱:assistant 消息发出工具调用
(OpenAI 协议里是 tool_calls 字段,Anthropic 协议里是 tool_use 块)
之后,下一条必须是对应的工具结果(OpenAI 是 role 为 tool 的消息,
Anthropic 是 user 消息里的 tool_result 块),中间别插别的消息,否则
下一轮请求会被 API 以 400 拒绝。发往国内模型服务的请求一律在代码里
按域名显式绕过代理;别只靠环境变量,不同库分别读大写 NO_PROXY 和小
写 no_proxy,要设就两个同时设。

上下文两层压缩。消息多了先清旧工具结果(micro),token 估算达到窗口
的 60-70%(经验值)时触发小模型摘要(auto)。压完必须把任务目标和
system 身份重新注入,不然几十轮后 agent 会偏题,以为自己在干别的事。

工具层每步重新加载列表别缓存,POST hook 里注册的新工具下一轮要看得
见。单工具输出分别设硬上限(读文件 20k、搜索 10k、shell 15k 起步),
超限送外置存储返 ID。shell 和 git 命令一律用参数数组调用,不经 shell
解析:Node 用 execFile,Python 用 subprocess.run([...]) 且不设
shell=True,Go 用 exec.Command。拒绝字符串拼接,防命令注入。

工具结果别以原文直接进主对话。批次跑完原文落外置存储返 ref,只把一
条精简摘要(stub,带 size 和 truncated 标记)塞进 context,要原文模
型自己再发 read_observation 按需取:全文提取、按需注入、不截断、不
跳页。错误返回要 actionable(讲哪里错了、怎么改,别丢原始 stack
trace),接外部数据源的工具错误先 sanitize 防注入。

模型该调工具却只吐一段文本,按三处依次排除,别先改 prompt 或换模型:
一是响应解析,模型可能把调用写成文本标签,没进结构化的工具调用字段
(OpenAI 的 tool_calls、Anthropic 的 tool_use 块),解析层再兜一道
正则提取;二是请求参数,该轮必须走工具就把 tool_choice 设为必须调
用工具(OpenAI 写 required,Anthropic 写 any),按轮开,别全局常
开;三是 prompt 装配,过长的中文 prompt 会让模型懒得调工具,把触发
指令写短、写靠前。

可观测性从第一行开始埋。埋在决策点,不在执行点:也就是机制判断"该不
该做"的地方。四种状态:触发执行了、条件不满足没执行、触发但拦截了、
执行出错。没事件是最危险的信号,说明代码路径根本没走到。

循环检测拦重复工具调用,介入消息先攒到队列里,等本轮工具结果处理完
统一推送,别中途破坏消息协议。

并发别在锁里同步等长任务。锁里只把 engine 取出来就立刻释放锁,异步
跑并监听取消信号,成功、取消、出错三条路径都保证 engine 归还。

前端接入时后端是唯一真相源,别做前端状态快照。切换 session 从后端
拉 last_messages 和 is_running。

单 agent 跑通按上面三种语言估时,加上观测埋点、循环检测、多 agent 隔
离再加一周(经验值)。接强模型,弱模型带不动多轮工具调用。
```

## 第二段：从通用到场景的收窄（不绑行业）

```
通用 runtime 跑通后,针对具体业务场景做收窄。不管是客服、标书、质检、
运维、翻译还是数据分析,方法一样,八步做完。文中数字都是经验值,以本
场景评测结果为准。

第一步建评测集。3-5 个典型任务起步,每个任务有可自动化的通过/失败判
定,有预期工具调用序列和最终数据库状态。评测集和代码一起演化,不要
等"做完再测"。每一步的验收也一样,尽量用能跑的检查代替文字自评:执
行者是 AI 时,文字形式的验收标准最容易被一句"已完成"糊弄过去。

第二步工具收窄。通用 runtime 可能挂 40-50 个工具,业务场景一般只用
8-15 个(经验值)。用 enabledTools 白名单只放行这些工具,或把其余工
具写进 disabledTools 黑名单,不要只是放着不调:留在上下文里会分散模
型注意力,选错工具的概率上升。

第三步工具描述强化。每个业务工具的 description 里直接列必填字段名、
类型、枚举值。字段是 user_id 还是 userId、是数组还是对象、枚举有几
个值,别让模型猜。猜错一次就浪费一轮。按经验,这是投入产出比最高的
单点优化,通常比反复改 system prompt 有效得多。

第四步策略规则引擎。业务规则不要全堆在 system prompt 里,模型跑几十
轮就忘。做成"调用 X 工具前注入结构化提醒":取消操作前弹资格条件检
查,删除前弹二次确认,赔偿前弹前置条件。即时提醒比全局声明有效得多。

第五步提示词分层。系统层写角色和能力边界,场景层写业务规则和禁用行
为,执行层写输出格式(比如必须报数字、必须同语言回复、必须等用户确
认)。三层分开,方便单独调整和 A/B。

第六步开推理模式(如果模型支持)。对多步判断、数值计算、规则检查密
集的场景,推理模式通常能明显提高通过率(作者项目中见过约十个百分点
的提升,仅作参考,开前开后各跑一遍评测集确认)。简单问答场景不用开,
浪费 token。

第七步跑消融实验。每加一个机制,关掉再跑一次评测集,看分数掉多少。
正贡献保留,负贡献砍掉,接近零的看维护成本决定。关键在这一步:有些
"看起来正确"的机制,关掉反而提升,单元测试根本看不出来。

第八步失败归因分维度。不止看通过率,还要看:工具调用参数对不对、数
据库最终状态对不对、回复里该说的数字/条款有没有说出来、该走的流程
走完没有。单维度评测会掩盖真问题。数据库对了但没说出数字,在客户看
来就是没办成事。

这套收窄做完,通用 runtime 在特定场景下的通过率通常能明显提升(作者
经验中约 10-20 个百分点,仅作参考,以本场景评测为准)。比换模型便宜,
比重写框架快。
```

## 第三段：成本结构（什么先砸、什么后砸）

```
资源不要平摊到每个机制。瓶颈在哪里就砸哪里。顺序错了,花同样的钱拿
不到同样的结果。文中数字都是经验值,以本场景评测结果为准。

先砸评测集。没评测等于闭眼调优,后面所有改动都说不清"到底有没有用"。
评测集粗糙到只看通过率也比没有强。三五个能自动判定的典型任务,跑起
来就行。每次改动跑一遍,慢慢补充边界 case。

然后砸工具描述。按经验这是单点投入产出比最高的位置:模型猜字段名猜
错一次就浪费一轮,几十轮对话下来浪费的轮数可能相当可观。写清必填字
段、类型、枚举值,比反复改 system prompt 有效。

接着砸策略规则引擎。业务规则做成"调用前注入"。几十轮之后模型会忘
system prompt 里的规则,即时注入的不会忘。这一步做完之后再看模型表
现,比直接换模型便宜得多。

推理模式开不开,看任务是不是多步判断。规则检查、数值计算、多条件
判断密集的场景开,通常能明显提高通过率(作者项目中见过约十个百分点,
以实测为准)。简单问答场景别开,贵、慢、没收益。

模型升级放到最后。从便宜模型开始,调到瓶颈再换。模型贵、不可逆(换
了要重新跑评测)、对大部分场景提升有限:真正卡通过率的一般不是模型
能力,而是外围机制没调好。大部分团队的误区是第一步就换模型,结果钱
花了分数没涨。

基础设施(压缩、观测、循环检测、锁和取消)是入场券,不是投入。不做,
一切都谈不上。但做到"能跑就行"的程度就够用,过度工程反而拖慢迭代。

按场景类型看分配:
  客服和规则执行类     先砸工具描述 + 策略规则,再考虑推理模式
  代码和复杂规划类     先砸推理模式 + 强模型,工具描述和规则次之
  长对话和多轮类       先砸压缩 + 观测,不然跑几十轮自己就崩
  高并发和低延迟类     选便宜模型 + 工具输出缓存 + 简化工具集

最后一点最反直觉:负贡献机制要及时砍。有些机制做了反而掉分,继续维
护等于双重损失:占资源,还拖通过率。消融一测就看出来。舍不得砍"看
起来正确的代码"是常见错误。

反过来,机制能不能进默认 profile,过四条:能改变真实行为(不是只加
DTO/schema/日志字段)、有 on/off 消融数据、有机器可读 trace、过稳
定性检查(N 次重跑加扰动 prompt,收益不能只靠偶然)。达不到的留作实
验开关,不进默认 profile。
```

## 三段的使用顺序

1. 先用第一段搭通用 runtime。这一步不考虑具体业务，只把框架跑起来。
2. 通用 runtime 能对着任意工具集发起 ReAct 循环之后，用第二段做场景收窄。这一步和业务一起演化，不要等"通用版做到完美"再收窄。
3. 第三段在任何阶段都可以对照。它决定的不是"做什么"，而是"先做哪个"和"钱花在哪"。顺序错了，通用 runtime 搭得再好，业务上也拿不出结果。

三段合起来的总逻辑：**先搭一个能跑的东西，再针对场景削出锋利的刀，然后把钱花在刀刃上。**
