前三章搭好了框架：第一章的坐标系、第二章的判据、第三章的实战检验。判据已经在一次真实事故上逐帧圈中根因，坐标系不再只是纸上推演。那场事故还提供了一个回看的角度：每个根因，都是某个组件的职责没人认领；组件图一模糊，事故就有缝可钻。从第五章起，本卷要逐项深入：状态机、持久化、恢复、副作用，每章放大矩阵上的几项。深入之前还差一样东西。第一章 1.4 由失效场景反推出八个组件，那一节回答的是"为什么恰好是这八个"；它没有回答的是"每一个长什么样"：职责边界画到哪里、跟谁怎么接、靠什么手段守约、换一种做法要付什么代价。读者马上要进入第五章的转移表和第六章的表结构，手里的图得先从存在性证明升级成工程图纸。

本章就做这一件事：给八个组件各写一张**组件卡**。一张卡六栏：

1. 职责（一句话）；
2. 边界（明确不做什么）；
3. 上下游接口；
4. 主守契约与守约方式；
5. 替代方案与取舍；
6. L 级起步预期。

八张卡合起来，是本章的核心交付物 **Component Register**（组件登记表）。builder 深入各章之前拿它当全图，assessor 拿它当评审对照物：第十五章评审时，被评团队自己画的组件图，就是拿这八张卡逐张对照，对不上就标红。除了八张组件卡，本章还给出一张业界逐组件映射表和一页部署概览。

## 4.1 组件卡怎么读：拿状态层做样张

先说读法。第一张卡给状态层，它由第一章 1.4 的第一条硬约束（真相只放一处）催生：

![](../diagrams/tb-04-1.png)

六栏各有分工。前四栏让组件**可指认**：它是谁、不是谁、跟谁接、守什么约。评审时拿任何一个系统对着问，哪一栏答不出，就缺哪一块。第五栏让蓝图保持为**设计空间**：每张卡记的是取舍的过程，单机基线只是取舍后的一个选择，负载特点变了，选择也跟着变。第六栏把第一章的成熟度尺细化到组件粒度，预告各深入章的验收底线。八张卡的完整六栏收录在本卷工作制品 Component Register（附录 G），正文按组件群展开重点栏，尤其是第五栏：后面各章不会再回头讲选型，取舍在这里说清。

还有两个疑问要先排除。为什么不另设"失效模式"栏？组件的失效已经拆进两处：被否方案的失效原因写在取舍栏（内存快照败在状态撕裂，进程内执行败在工具崩溃拖垮 runtime）；被选方案自身的失效表现，归各深入章的破坏实验，蓝图层不重复收录。也不另设"四问"栏：可观测、可控、稳定、闭环是矩阵的纵轴，体现在每张卡进入深入章后的动线里，不在卡面上。说到底，组件卡没有另起一套分类法：它是六契约×四问矩阵按组件切出的一片（主守契约栏就是挂在横轴上的钩子），也是 L0-L5 尺按组件的对应（第六栏标刻度），三者是同一张架构的三个切面。接口栏同理只记到"谁写谁读"一层；具体接什么（事件 schema、实体链）收录在工作制品 Event Schema 与第六章，卡上不重复。

最后交代两份"八项"清单的关系，入门卷读者到这里多半已经在心里比对了。入门卷的八个 runtime 部件（agent loop、model adapter 与 routing、tool registry 与 ACI、context/memory/artifact、prompt assets、observation surface、trajectory、verifier，外加 safety 控制面）按**能力**切分：一个 agent 要能做什么，每个部件承载一种能力。本章的八张卡按**守约职责**切分：六份契约各由谁负责。同一套系统的两种切法，对应关系有四种：

- **同名承接**两个：agent loop 与 model adapter，本卷各加了新约束（内存即易失；routing 裁决移交 run manager）。
- **职责重排**两个：tool registry 管"有哪些工具"，执行那一半在本卷独立成 tool executor；observation surface 并入事件流的输入侧。
- **升格**一个：trajectory 在入门卷是一份记录，本卷把它拆成事件流与证据存储，记录本身成了承担契约的组件。
- **新增**三个：状态层、run manager、入口层。入门卷的单机单入口教学场景用不到它们，一旦要跨故障执行、多入口并发，就非有不可。context、memory、artifact 与 prompt assets 相应归位：持久的归状态层，组装出来的是投影（从持久状态派生出的只读视图，可随时重建，不回写）。

safety 控制面没有消失，并入了 run manager 的 policy 裁决与第十一章的权限契约。逐行对照表在第一章附录 A，两卷冲突以那张表为准。

## 4.2 真相侧的三个组件：状态层、事件流、证据存储

状态层的卡已经给出。真相侧还有两个组件，都由第一章 1.4 的第二条硬约束（只追加）催生。

**事件流**这张卡，取舍栏最有分量，先从它说。"发生过什么"的机器可读记录有三种做法。可变行加审计表已被第一章 1.4 排除：解释一旦允许事后修订，就都不可信。剩下两种都守只追加：单机 append-only 表，和消息队列（Kafka 一类）。队列带来投递语义和横向扩容，失去的是单机运维的简单，以及"一条 SQL 就能核对完"的可审计性；在走向多实例之前，表更合适。载体定了，职责随之清楚：每次状态转移都记在这里，trigger、guard、终结原因随行，恢复扫描、UI 订阅、审计回放都从这里取材。它主守转移契约。两条边界要划明：它不当消息队列用，不承诺投递语义，完成通知这类"送没送到"的事，按第二章的确定性分级只算尽力而为；它也不存大负载，事件行放引用、正文外置，否则高频小事件和低频大内容会挤在同一条读写路径上。起步 L2：它本身就是 L2 的载体，这张卡若不在，全系统的"能看"无从谈起。

**证据存储**归档四样东西：trajectory、policy 决策、verifier 结论、artifact 来历。它只存不判：verifier 的结论存在这里，判断动作在第十三章的证据面；实时呈现也不归它，那是事件流加投影的事。它主守证据契约。要不要跟事件流合储，是这张卡唯一的取舍：合储能省一个组件，却把"高频小事件"与"低频大归档"压进同一套访问模式；分储则各按各的读写特点建，代价是多一条归属线。单机基线选分储，因为第十三章要在归档上做对账与回放，那套访问模式与事件订阅本来就不同。起步 L2，归档本身就是事件记录。

三者的分工第一章 1.4 讲过，这里一句带过：状态层回答"现在"，事件流回答"怎么来的"，证据存储回答"凭什么信"。第三章的缺失证据清单五条，三条是事件流的空缺，两条压在状态层的写入时机上；这三个组件缺一角，那张清单就长一截。

## 4.3 执行侧的两个组件：run manager 与 agent loop

真相侧有了着落，再看执行侧的两张卡。

**run manager** 是单执行内核：准入、同会话互斥、policy 与 limit 裁决、孤儿 run 的发现与收尾，全在这一个关口里。它是入口层的唯一下游，也是 run 记录与终态的持有者。边界在两头划清：不碰模型、不碰工具，执行细节归 agent loop 和 tool executor；也不长业务逻辑，它裁决"能不能跑"，不参与"跑什么"。转移契约与权限契约的裁决点在这里，交互契约的收敛义务（悬而不决的 run 由它给出终点）也在这里。集中还是自治，是这张卡的取舍。自治的失效第一章 1.4 论证过：同一个"取消"长出三种语义。集中则把代价转到另一头：内核成了单点，每种入口语义都得经过它评审，在路线图上它就是瓶颈；换来的是 permission、cancel、resume、工具执行四种语义只实现一次。入口到内核的 Routing Matrix 细则在第五章 5.11。起步 L2：准入、互斥、抢占三类决策都要有事件。第三章帧 7 那次无声抢占（决策没留下任何事件），就是这张卡缺 L2 的实例。

**agent loop** 是一轮任务的编排者：组装 context、调模型、执行工具、循环到给出最终回答。它的卡最特殊：它不单独主守哪份契约，而是所有契约实际履行的地方，因此承担全卷最硬的约束：内存即易失，积累的一切要么立刻落盘，要么等于不存在（第一章 1.4）。它不持久化真相、不自证正确，证据一律外置。写法上有两条路：手写同步循环，或交给声明式 graph 引擎。graph 引擎提供声明式并行、内建重试和可视化，失去的是"每一行都能标出落盘点"的透明度；本卷的判断标准（第一章 1.4：任何机制都要能在时序上标出位置）恰好偏向透明这一侧，所以单机基线手写循环。两种 graph 的完整辨析在第八章 8.12，这里不展开。它的 L 级起步只有一项要求：loop 每步 emit 事件，也就是从 L1 到 L2 那一步。第一章的假落地公式检查的就是它。

## 4.4 面向外界的三个组件：入口层、model adapter、tool executor

剩下三张卡都在系统与外界的边界上，各自面向一个方向。

**入口层**（UI、API、IM、scheduler）面向用户，负责适配意图、转发流。它的边界就是第一章 1.6 破坏实验给出的判定标准：投影不回写，界面显示的一切都是持久状态的只读呈现；它也不实现任何 permission、cancel 的捷径，四种语义只在内核实现。它主守交互契约的呈现部分。把界面做厚一直有诱惑：客户端缓存能带来离线体验和更快的首屏，但它引入了第二个真相源。桌面案例那条 localStorage 恢复路径（第三章缺口二的一环）就是客户端缓存代价的一个例子。所以单机基线坚持薄投影。起步 L1 即可：它的正确性取决于"不写"，靠第一章 1.6 那个破坏实验来验证，不靠它自己的事件。

**model adapter** 面向模型，负责记录每一次调用。每次调用完整留档：模型标识、参数、上下文摘要、输出。恢复时，已完成并已记录的调用直接复用记录，不再重调；崩溃时正在进行、结果还没记下的调用，只能重新发出。工业先例是 Temporal 把不确定的操作收进 activity（第一章 1.4 已引），语义与此一致：已完成的 activity 在重放时复用记录的结果，未完成的 activity 按重试策略重新执行。它不做 routing 裁决（归 run manager，第一章附录 A 已定），也不解释输出，那归 loop。它主守转移契约与证据契约中与模型调用相关的部分。另一条路是抽出独立的模型网关：集中计量、限流、多应用复用，代价是多一跳延迟、多一个单点。单机用库内实现就够，多租户时再考虑网关。起步 L2，调用记录本身就是事件。

**tool executor** 面向外部世界，是副作用的唯一入口，顺序固定：先落盘意图，再执行，再落盘结果，工具返回只算执行方的一面之词（第一章 1.4 定下的顺序）。policy 判定不在这张卡上：裁决归内核，它只执行裁决结果；结果解释也不归它。它主守副作用契约。执行放在哪里有三种选择：进程内、子进程沙箱、远端 worker，用执行开销换隔离强度。进程内执行的风险是工具崩溃连带拖垮整个 runtime；单机基线选子进程沙箱，远端 worker 留给多实例（4.7 的切换信号之一）。起步 L2，intent 与 result 两类事件缺一个就是假落地。

到这里八张卡都已给出。每张卡的六栏全文在 Component Register；下面三节把八张卡串回整体：动线、业界、部署。

## 4.5 两条动线：每张卡在什么时候干活

静态的卡要靠动线检验。正常动线第一章 1.4 已给过九步走查，这里不重列，只补本章新增的一层：九步里每个落盘点归哪张卡。

- 步 2 的 run 记录与步 8 的 run 终态，归 run manager；
- 步 3 的用户消息与步 8 的消息终态，经状态层的单写者写入；
- 步 5 的调用记录，归 model adapter；
- 步 6 的 intent 与 result，归 tool executor；
- 事件流全程随行。

agent loop 自己一个落盘点都没有，它的全部产出都经别的卡写入，这正是"内存即易失"约束在结构上的体现。

恢复动线是九步的镜像，概览级走一遍：进程重启，扫描从事件流开始（最后一个完整事件即截断点）；状态层里 status=running 的孤儿 run 由 run manager 收敛，终态化或续跑，依据是第五章的状态机；续跑时，已完成并已记录的模型调用从 model adapter 的留档复用；已发出的副作用拿 tool executor 的账本对账；投影最后由入口层从库里重建。七步的完整时序和每步的失败分支在第七章 7.10 展开。这里只求看清一点：恢复不是某一个组件的事，八张卡各有各的职责。

## 4.7 部署形态一页

八张卡是逻辑架构，放到哪里运行是物理架构。单机基线一句话说完：八个组件都在同一个进程边界内，SQLite 文件、子进程沙箱、进程内事件分发，逻辑图即物理图。

蓝图对部署的承诺是：**组件边界即迁移断口**。负载增长时逻辑架构不动，换的只是部署方式。四个切换信号各对应一条边界：

- 多实例或出现多写者：状态层的 SQLite 换成 Postgres 加 lease；
- run manager 单例撑不住：互斥从进程内换成分布式锁或 lease；
- 工具执行要隔离出去：子进程沙箱换成 worker queue（独立工作进程＋任务队列）；
- 订阅方跨了机器：进程内事件分发换成事件总线。

四个信号的详表在第十四章部署基线，生产工程的完整处理在第三卷。本章只给这一页概览，因为取舍栏里写的每个"多实例再谈"，都要有这一页作为依据，才不算空话。

## 破坏实验：逐组件抽除

本章的破坏对象是蓝图自身。第一章 1.4 说这八份职责缺一不可，当时只举了三例，这里逐一验证。这是一个**思想实验**，按四步协议执行。它验证的是职责必要性，即八份职责里没有一份多余；它不验证八份职责必须由八个独立组件分别承担（4.2 已经说明，证据存储可以与事件流合储），也不验证任何实现的质量，后者归各深入章自己的破坏实验。至于"每份契约都有履行人"这一面，来自第一章从契约反推组件的失效推导，本实验把它当作基线，不重复证明。

1. **破坏动作**：从蓝图上抽掉一个组件，其职责无人接管，逐一做八次。
2. **观测点**：六契约承诺句逐条问"履行人还在吗"；四问逐条问"哪一问从此答不出"。
3. **判定**：抽掉后至少一份契约失去履行人，该组件的职责即为必要；若全部契约仍有人履行，蓝图该瘦身。
4. **复跑**：八次抽除即八次复跑，结论逐一记录。

结果：

- 抽掉状态层：真相没有 owner，"哪份算数"永远没有答案。
- 抽掉事件流：转移契约无处记录（第一章已示）。
- 抽掉证据存储：四问全部答不出（第一章已示）。
- 抽掉 run manager：互斥与准入散落进各入口（第一章已示）。
- 抽掉 model adapter：恢复时重跑已完成的调用，制造出第二个版本的历史。
- 抽掉 tool executor：副作用没有统一入口，从源头就没有记录。
- 抽掉 agent loop：无人编排，系统不成立。
- 抽掉入口层：意图无从进入，系统无用。

判定：8/8 职责必要。需要说明的是，后两个（loop、入口）的必要性是平凡的，抽掉它们系统根本不运转，这部分论证不携带信息量；真正承担论证压力的是前六个，六次抽除各自击穿至少一份契约，没有一次落空。第一章"八份职责缺一不可"的说法，至此从三句示例变成了逐一验证。

## L 级自检

成熟度尺（L1 能跑、L2 能看，全表见第一章 1.3）在本章换一个用法：本章不给自己评级，因为 L 尺量的是机制，本章交付的是图。它只做一件与 L 尺相关的事：把每个未来机制的 L 级起步预期写进卡的第六栏（六张定 L2、两张 L1），作为第五章到第十三章的验收底线预告。图本身对不对（状态机对不对、恢复语义成不成立）要等各深入章的破坏实验来验证，本章不预先下结论。

## 立即可做的一个动作（五分钟）

builder 版本：拿自己的系统对着八张卡过一遍，每张卡问一句：这张卡在我的系统里叫什么名字？找不到名字的卡，它的职责现在谁在干？答案是"散落在三处"的，每一处都可能酿成第三章那样的事故，记下来。

assessor 版本：拿被评系统已有的架构图（没有就请对方现画一张），五分钟只做一件事，问三个问题：单写者是谁？抢占决策记在哪？副作用的入口有几个？回答与图对不上的地方标红；图上画了一个入口、代码里却有三条路的，按第一章的假落地公式处理。
