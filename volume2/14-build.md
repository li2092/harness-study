# 十四、从零构造一个最小但完整的 Runtime

> （本版本注与"审稿日志""引用来源"两节同属编辑工作区，出版前整体删除。）

第十三章结尾撂下一句：纸上讲得通，不等于造得出来。前十三章立了六契约、五平面、证据面，可它们从没合在一起跑过一次。一份契约单看都对，十几份拼到一起，常在集成那一刻相互冲突——permission 挂在还没建的 principal 上，resume 去读一个还没定义版本的 checkpoint，subagent 想关联一个还没有 correlation 的事件流。这是全卷那条根主张——部件正确加不出系统正确——最后一次现身，也是本章要过的坎。

主张压成一句：**以可运行骨架逐步点亮六契约**。每个词都有讲究——骨架，不是完整产品；逐步，按依赖顺序一步步来；点亮，判据不是 happy path 跑通，是每份契约对应的失败场景被守住。读完本章，手里应当多一张十四步构造序、一份标准故障包。

## 14.1 集成才是最后一道坎

先说清楚为什么单独立完十三章契约还不够。

最朴素的做法，是把前十三章的机制各自实现、拼到一起，happy path 一跑通就算完成。这条路的失效出在接缝上：各契约单独成立，合起来相互妨碍。失效根因有两个——一是没把"依赖顺序"当成构造纪律，谁先谁后随手排，于是有的机制挂在还没落地的前提上；二是没把"失败场景"当成完成判据，只演正常路径，就把"不出错时能跑"误当成了"契约守住了"。

设计是两条老纪律的合流：写一个测一个（每个可测单元完成即验证）加破坏一次（全卷每章都跑的破坏实验协议）。落到构造上，就是按依赖顺序逐步推进，每一步交五样——最小数据结构、关键伪代码、一条正常 trajectory、一条失败 trajectory、验证证据。代价是从零走一遍比在现成系统上改要慢；但慢换掉的，是集成期才暴露、最难定位的契约冲突——那种"每块单测都绿、合起来就错"的排查，比慢启动贵得多。

## 14.2 构造顺序就是依赖顺序

第一条纪律具体化：十四步的排序不是随意的，每一步只依赖已经点亮的契约。

顺序按三层落。地基层：（1）实体、ID 与 State Registry——一切状态的挂靠点，必须最先立。执行与账层：（2）单一 Execution Kernel 与 run 状态机、（3）model invocation record、（4）tool 的 intent/attempt/result/outcome 四段账、（5）event stream 与客户端重建。治理与验证层：（6）cancel 与 HITL、（7）checkpoint/resume 与 durable timer、（8）permission/sandbox 与 authority lifecycle、（9）context assembly 与 compaction、（10）可显式建模案例的 world model 闭环、（11）parent/child run、（12）Evidence Plane、（13）runtime 的 meter/limit/version 接口、（14）标准故障包验证。

倒置任何一步都会落空：permission（第八步）没有 principal（第一步）就无处挂靠，resume（第七步）没有版本（第一步的 State Registry 里定义）就不知道该不该续跑。所以这份序列本身就是一张依赖拓扑——每一步的前提都排在它上面，谁先谁后没有商量余地。代价是顺序被锁死，想先做看得见的功能（漂亮的工具、能演示的 UI）得等地基先立；但地基不先立，那些功能就是空中楼阁，第一次真出故障就立不住。

## 14.3 点亮一份契约，看的是它的失败 trajectory

第二条纪律更反直觉：一份契约算不算点亮，判据是它的失败场景被守住，正常场景跑通不作数。

每一步都要交五样：最小数据结构（够用就行，不为假想的未来预支灵活性）、关键伪代码、一条正常 trajectory、一条失败 trajectory、验证证据。前四样里，失败 trajectory 才是分水岭。只演正常路径，证明的仅仅是"不出错时它能跑"——可契约存在的全部理由，就是应对出错。失效根因在这儿：把 demo 当成了验收，happy path 绿灯给了一种"已经守住"的错觉。

设计上，每一步都配一条注入了该契约对应扰动的失败 trajectory，并写明判定口径。做副作用那一步（第四步），失败 trajectory 就是"工具已执行、结果未落账时把进程杀掉"——第四步先立下这条账，把该行留成 intent 无 result 的未决态；到第七步恢复时才据它进对账、不被无脑重放。代价是每一步都要额外写失败场景，工作量比只写 happy path 多一倍；但这多出来的一倍，正是"点亮一份契约"和"做一个能演示的 demo"之间的全部差别。

## 14.4 双层控制流的最小骨架

前面的步骤里，第二步的执行内核值得单独展开——它是第十二章双层控制流从原则落到骨架的地方。

先实现 node-local loop：单个 agent 内部那圈"调工具、看结果、决定下一步"的自治循环。再在它之上加一个含 branch 与 join 的最小 graph workflow：跨节点的编排层，决定 spawn 谁、等谁、怎么合。两层都要有，但顺序是先自治层、后编排层——因为编排层调度的是一个个已经能自己跑起来的 node。失效形态就是第十二章讲过的那种混层：把本该由模型判断的一步硬编进图（该自治的锁死在确定性代码里、变脆），或把本该确定的分派丢给 loop 里的模型自由发挥（该编排的失了可追踪）。

代价是这个最小 graph 也是一层实打实的实现，单 agent 的任务根本用不上它；但没有这层骨架，多 agent 协作就没有挂靠点，等真需要并行时再从 loop 里硬长出编排层，比一开始留好接口要难得多。

## 14.5 可显式建模的那一步

第十步是个例外，得说清它的适用边界，免得被误当成通用要求。

在一个状态紧凑、转移可观察的案例里，实现一条完整闭环：写出 world model、用完整历史做 replay certificate、在模型里 search 或 dry-run、只让 guarded commit 触碰真实世界、预测与观察不符就生成 counterexample 并 replan。这五步（观察／建模／认证／规划／提交）正是第十三章 13.8 那条模型闭环的可运行形态，本章把它从纸面落成一条能跑的代码路径；也是第十三章那七条认识论边、第六章 6.12 那份信念工件从纸面到可运行的一次示范。

关键的边界要划死：这条路径是显式可建模任务的扩展，适用面就到这里——普通 agent 任务无需配一套完整 simulator。代价正在于此——建一个像样的 simulator 是重投入，只有当任务的状态紧凑、转移大体确定、真实动作昂贵而内部仿真便宜时才划算（这条域边界第十三章已经立过）；域选错了，这笔投入就白花在一个仿真并不比真跑省的地方。所以本章把它放进构造序，同时明说它可选。

## 14.6 标准故障包：验收不看能跑，看它全绿

到最后一步，本章最要紧的方法论浮出来：这套 runtime 到底验收什么。

答案不是"能跑"。前面的深潜章里，有九章在章末留了一个"第十四章工单"——一个 fixture。验收这套 runtime，就是逐格问六契约在故障下守没守住；第五、六、七、八、九、十、十一、十二、十三这九章的 fixture 在这里汇编成的标准故障包，正是那张逐格验收表：

![](figures/embed/tb-14-1.png)

六契约每一格都有对应的故障场景压着——转移、副作用、交互、真相、权限、证据，无一漏空。验收判据从此改口：不是 happy path 亮绿灯，是标准故障包全绿。失效根因还是那句全卷开篇批过的老话——"能跑就不要动"，在构造层就表现为拿 happy path 交差。设计上，标准故障包是 executable spec 和参考实现共用的同一套验收，谁跑都是这一包。代价是维护一套故障包是持续开销，改一处机制要回归整包；但它是"六契约每一格的代表性失败都被守住"这件事唯一可复算的证据——全绿证的是每格有一条失败场景站得住，不是契约被穷尽守护；省了它，连这条代表性证据都没有，"守住了"就只是一句口头声明。

## 14.7 底线交付一份 spec，参考实现是加分

交付什么，首先是方法论选择，其次才是工程选择。

底线交付是一份语言无关的 executable spec：数据结构、状态转移、事件 schema、标准故障包的判定口径，都写成不绑定任何语言的规格，任意语言都能照着实现。加分交付才是一个可运行的参考实现。这么分层有个明确理由——方法是要能迁移的，一份语言无关的 spec 谁都能照着造；而参考实现是加分的验证，它证明 spec 可实现，却不等于 spec 本身。把 spec 定为底线，成书就不会被某一种实现的进度卡住，第三卷的接口清单也以 executable spec 为准。代价是写一份严谨的语言无关 spec，比直接敲代码更费神，很多在代码里能含糊过去的边界，在 spec 里必须写死；但换来的是这套方法不被绑在一种技术栈上，任何团队都能照着它造自己的 runtime。

## 14.8 先单机跑对，再谈规模

最后是部署形态。这一步的纪律是：逻辑架构和部署规模解耦。

先立单机基线——SQLite、单例、进程内跑任务、进程内广播事件。它看着像个玩具，但它的价值正是把逻辑对不对，和规模够不够，分成两个可以先后回答的问题。规模是后一个问题，靠一组明确的切换信号触发迁移，逻辑架构一格不动：

![](figures/embed/tb-14-2.png)

代价是单机基线在能撑住真实流量之前，确实只是个骨架；但先在单机上把六契约和标准故障包跑对，再按信号逐个换组件，比一上来就上分布式、在规模和正确性两个维度同时挣扎，要稳得多。

业界的一个对照正落在这里（回指第七章）：checkpoint 类框架容易把"存档点"当成 durable execution 的全部——按 Diagrid 的公开比较（Diagrid 自身是 durable-execution 竞争方，这是其厂商立场、非中立结论），这类框架不管失败检测、恢复触发与跨实例协调三件；本章第七步的 checkpoint/resume 只是存档点，真正把这三件补回来的，是第二步 run 状态机的启动扫描、第七步的看门狗，和本节单机→多实例的切换信号。

## 破坏实验：标准故障包本身

本章不另设破坏实验——标准故障包就是它。九个 fixture 各自定义了一套"破坏—观测—判定—N 次复跑"流程，逐一执行即验收协议、不代表已经跑过，判定口径已在各自出处章立过（第五、六、七、八、九、十、十一、十二、十三章的破坏实验节）。

实证状态照实分层【经验】：九个 fixture 目前均以 executable spec 的判定口径存在——每个 fixture 写明破坏动作、观测点、判定与 N 次复跑要求，属思想实验层的可执行规格；参考实现的实跑覆盖是加分项。配套实现项目当前落地的是 append-only 事件流、run 状态机、correlation、intent/result 记录这几件底座，够给 contract test 与 replay/reconciliation 三个 fixture 搭实跑接线，但含这三个在内、九个 fixture 均未跑绿——fixture 级的实跑尚未接齐。整包实跑覆盖是本章加分交付的待补项，照实记，既不说成"已部分实跑"，也不粉饰成"整包已实跑绿"。

## L 级自检

按第一章的成熟度尺（L1 能跑、L2 能看，全表见第一章 1.3 节）。本章是全卷 L 级的收敛点：前十三章各自把机制推到 L1／L2，本章的判据把它们合起来往上顶——一套 runtime 的成熟度，不由它有多少机制有名字（L1）决定，由标准故障包绿了几格决定。套第一章那条假落地诊断的构造版：十四步里某一步的机制在代码里有名字（L1 在），可它对应的那个 fixture 从没跑绿过、甚至没写（L2 缺），这一步就按未点亮处理——有骨头、没验证，不算点亮。

四问落位：可观测由每步的验证证据与 Evidence Plane（第十二步）兑现；可控押在依赖顺序与单一执行内核——构造被顺序锁死、执行只有一个内核入口；稳定兑现在标准故障包——九类扰动逐一注入、包全绿才算稳；闭环是本章的元层——构造本身就是一个"立机制→跑故障包→哪格红补哪格"的反馈环，检测（故障包）、纠正（补机制）、验证（重跑包）三样在设计与 executable spec 判定层都到位；但照实说清：配套实现里故障包只有 contract test 与 replay／reconciliation 三个 fixture 搭好了接线、且尚无一个跑绿，这个环还没在本地完整闭合过一圈。它仍是全卷四问第一次落到"造一套系统"这件事本身上——落在方法层，不是落在已跑通的实现层。

坐标系落位补一句：全卷那条根主张"部件正确加不出系统正确"在这里拿到正面答案——部件要加成系统，靠的正是三件合流：依赖顺序让每个部件不挂在还没立的前提上、逐份点亮让每个部件在自己的失败场景下站得住、标准故障包全绿证明它们合起来仍同时成立。本章不新守某一份契约，它守的是这三件叠出来的集成正确性。

配套实现项目现状照实记账：本章机制整体在 L1 与 L2 之间——骨架的几步（State Registry、状态机、事件流、correlation、intent/result）是实的（L1），但标准故障包的完整实跑、executable spec 的完整成文都还没接齐（L2 缺），不粉饰成半格；补齐是本卷落地的收尾工程，也是第三卷生产化的起点。

## 交付物

1. **语言无关 executable spec**（底线交付）——十四步的数据结构、状态转移、事件 schema、标准故障包判定口径，不绑定语言；成书不被实现进度阻塞，第三卷接口清单以它为准；
2. **可运行参考实现**（加分交付，当前仅骨架几步落地、整包实跑待补）——证明 executable spec 可实现，与 spec 共用同一套标准故障包验收；
3. **标准故障包**（正文表，验收 SSOT）——九 fixture × 破坏场景 × 主守契约，六契约每格有对应故障场景；第十五章评审直接取用。

近道读者可单取标准故障包作评审尺——不看被评系统的功能清单，只问它的六契约每格有没有一个跑得绿的故障场景；答不出的那一格，就是它没点亮的那份契约。

## 立即可做的一个动作（五分钟）

builder 版本：从标准故障包里挑一个最贴近自己系统的 fixture（比如"工具已执行、结果未记录时杀进程"），在系统上手动制造这个故障，看它恢复后是把那个动作进对账、还是无脑重放一遍。跑绿了，这一格契约就点亮了；跑红或压根没法跑，记下来——这是 runtime 上一个有名有姓的缺口。

assessor 版本：问被评团队一个问题——"你们的验收，是 happy path 全过，还是有一套固定的故障场景每次回归都要全绿？"答"happy path 全过"的，按本章的账记：这套系统只被证明过"不出错时能跑"，它在故障下守不守得住六契约，从来没被验收过。

## 遗留问题

从零造出一套能跑、能扛故障、能自证的 runtime，方法齐了。可现实里，从零开始是少数——更多时候是接手一个已经在线上跑、来历不明、没人说得清它守没守住哪几份契约的系统。面对这样一个既成系统，怎么在有限时间里审出它的残余风险？把全卷方法压缩成一套能带走的评审工具，第十五章。
