入口到内核的路由矩阵：前两列入口自理，后四列只有一个去处

入口清单比直觉里长——除了有人在场的四个，还有两个没有人在场的。每个入口只做两件事：适配意图、转发流；permission、cancel、resume、工具执行四种语义只在内核实现一次。这张表就是工作制品 E（Entry-to-Kernel Routing Matrix）的填法样张。
入口一行一个 意图适配入口自己做 流转发入口自己做 permission cancel resume 工具执行
UI 点击与输入 → 统一意图，携 idempotency key 事件流 → 界面渲染——投影不回写 全部路由到内核
四种语义只实现一次 任何入口的"取消"按下去，
走的都是转移表里同一行，
事件里只有发起者不同。

评审用法：拿被评系统照表填一遍，
后四列必须指向内核——
语义分叉当场显形。
API 请求体 → 统一意图，携 key 事件流 → 响应与流式下行
IM 渠道 消息 → 统一意图 事件流 → 消息回推
SDK / CLI 调用 → 统一意图 事件流 → 流式输出
scheduler / timer没有人在场 定时触发 → 统一意图 确认、失败呈现、完成通知全走异步路径
webhook没有人在场 外部回调 → 统一意图——重投是常态，靠 key 去重 回执与异步通知
缺口判据：后四列出现空格或"入口自实现"，即缺口。桌面案例只有一个 UI 入口，尚且长出了"重载后拿本地缓存当会话真相"的恢复线分叉——多入口系统的分叉只会更隐蔽。

两个没人在场的入口是收口的又一重理由

无人值守的 run，确认、失败呈现、完成通知全走异步路径。有人与无人两种场景的差异若由各入口自行处理，同一台状态机立刻又裂成两套——所以差异只能在内核之内消化，不能摊给入口。

为什么只实现一次

第一章 1.4 的教训：同一种语义实现 N 份，就会漂移成 N 种——UI 的取消只断流、API 的取消杀 run 不记原因，就是这么长出来的。收口的代价也直说：内核成了单点，每种入口语义都得过它评审；换回来的是四种语义只此一份。

业界旁证

对 Claude Code 的第三方源码分析显示：CLI、IDE、SDK 多个入口共用同一套核心循环与权限门（快照 v2.1.88，当前行为以官方文档为准）。做到规模的产品，在这张表上交出的正是"后四列全部指向内核"的填法。
