给窗口腾地方的四种手段：三类解空间，各担各的账

预算有限，历史无限，早晚要给窗口腾地方。动作空间其实只有三类；业界把它细分成四种手段，落点各不同，共用一把尺——省下的注意力预算，要花在高信号的 token 上。
压掉已有的· 移出窗口，再按需拉回· 分流到另一个干净窗口 三类解空间——四种手段是它们的细分，卡片右上角标着各自的类
压掉已有的
压缩
compaction
接近上限时把一段历史摘要成短文，用摘要重启窗口
适合：线性长对话
担着崩溃与缓存的账——半压缩态、前缀断裂；四种手段里唯一动历史本身的（图 10.3）
移出再拉回
记笔记
note-taking
要长期记住的写进窗口外的笔记（如一份 NOTES 文件），后续按需拉回
适合：跨越多轮的任务状态
担着重建成本；写进去的每条要有来历——不然就是又一个没人认领的真相源（10.5）
移出再拉回
按需检索
JIT retrieval
上下文里只存轻量标识（文件路径、查询、链接），运行时才把正文拉进来
适合：大语料
担着重建成本；拉回的正文随源头改动，不参与 replay 一致性（10.8）
分流
子代理
subagent
让子代理用干净窗口做一段深活，只回传一两千 token 的浓缩结论
适合：能切分的深探
担着子代理的往返；委派的完整账法在第十二章
收益是可量的（Anthropic 官方口径，指标各有出处）

context editing ＋ memory 工具组合，内部 agentic search 评测较 baseline 抬了 39%（官方口径是 performance，未拆到具体指标）；百轮 web 检索评测里，仅 context editing 就让原本因 context 耗尽而失败的工作流跑完、token 消耗压了 84%；MCP 工具目录从全量预载改成按需发现，一个跨系统工作流 15 万 token → 2 千——代价换了个地方：agent 生成的代码得跑在带沙箱、限额与监控的执行环境里。

省下的没有一样白得

压缩担着崩溃与缓存的账，移出窗口担着重建成本，分流担着子代理的往返。选手段就是选愿意担哪笔账——四张卡的虚线栏就是这笔账的登记位。

为什么压缩单独占一节

四种手段里只有压缩动的是历史本身——另外三种动的都是窗口外的东西，完整历史原封不动。所以它单独领一套事务纪律：失败回退、边界落盘、约束不入压缩、配对修复（10.3／10.4，图 10.3）。
