# 三、一次"数据丢失"事故

> v1.0（压缩版）· 2026-07-19 · 依据大纲 v5.2 · 已完成压缩去重：卷首开场在 §一，立论数字在 §1.1（3.7 瘦身为对账、原 3.9 删除）；本章职责=用一次真实事故验证 §一 的地图与 §二 的判据 · 待作者终审
> 事故素材来自 Howpot 2026-07-09 韧性摸底（快照见 `../research/volume2/08-howpot-resilience-audit-2026-07-09.md` 与 `08-howpot-resilience-review-2026-07-09.md`），全部结论有 file:line 实证【经验】。

§一摊开了地图，§二立了判据。轮到实战检验——一次真实事故，六类契约集体缺席的现场。

2026 年 7 月 9 日，一个叫 Howpot 的桌面 agent 应用收到用户报告：点了回答里的一个链接，整个窗口跳去了那个网页；退回来之后，"对话记录全没了"。这个应用的结构在同类产品里很典型——Tauri 壳、React 前端、Node 服务端、SQLite 存储，agent loop 跑在服务端，回复经 SSE 流式推给前端。

事故复盘出现了一个吊诡的局面：UI 正常，连接层正常，run 正常，数据库正常，每一层都严格执行了自己的设计。消息仍然永久消失了。

拆完这次事故，四个问题应当有答案：

1. 一条用户消息从发送到落库要经过几个载体，哪一段路上没有真相源？
2. 为什么每一层的单元测试都通过，数据还是会丢？
3. 同一个 bug 的三种修法差在哪里，怎么判断修到哪一档才算修完？
4. 一次孤立事故和一类系统性现象之间，隔着什么证据？

## 3.1 事故时间线：从提问到消失

先看用户经历了什么。

用户在一个已有几轮历史的会话里发出一条消息，回答开始逐字出现。回答里带了一个链接，用户点了它。窗口整个变成了那个外部网页——没有新标签页，没有浏览器工具栏，只能右键"后退"。退回来，应用重新加载，对话列表还在，但刚才那一轮问答不见了。用户判断记录丢了，于是把问题重新问了一遍。第二次得到了回答。后来核对时才发现：第一次的提问和半截回答，从此再也找不到。

摸底报告用 9 路专项审计还原了机制，每条结论都经独立对抗验证【经验】。事故由三个互相独立的缺口串成。

**缺口一：一次点击就能把应用带走。**前端渲染链接的代码只有一行——`Thread.tsx:50` 输出 `<a target="_blank">`。Tauri 壳没有装 opener 插件，`main.rs` 没有注册 on_navigation 回调，capabilities 只有 `core:default`。在 Tauri 的默认行为下，`_blank` 不会开新窗口，主 webview 原地导航，整个 SPA 被外部网页替换，前端所有内存状态蒸发。没有 beforeunload 守卫拦一下。

**缺口二：退回来之后，画面撒了谎。**SPA 重载后从 localStorage 恢复会话选择，再 GET `/api/sessions/:id/messages` 读消息——这条路直读 SQLite（`sessions.ts:372-380`）。问题在于，被打断的那轮 run 还没结束，而这个系统里唯一的落库点 `persistRunMessages()`（`chat.ts:2418-2544`）只在 run 收尾的 finally/catch 里被调用（`chat.ts:2166/2227`）。库里躺着的是 run 开始前的历史。于是画面缺了一轮，看起来就是"丢了"。此刻数据并没有丢——run 还在服务端后台跑，跑完会落库。

**缺口三：用户的合理反应，把假丢变成真丢。**用户在"空了一轮"的会话里重新提问。`RunManager.start()`（`run-manager.ts:43-49`）的抢占语义是：abort 旧 run，随即用新 run 覆盖注册表，不等旧 run 落盘。旧 run 的收尾逻辑走到 `isCurrentRun` 检查（`chat.ts:2219-2220`），发现自己已经不是当前 run，跳过整个持久化。被打断那一轮——用户的提问加上已生成的半截回答——从未写入数据库。抢占的"替换"行为有单元测试锁定，但没有任何测试问过它对持久化的副作用。

值得停一秒的细节：服务端"SSE 断开不杀 run"是有意的设计，`chat.ts:1642-1644` 的注释写得明明白白，还有专门的 safeWrite（`chat.ts:1854-1861`）保证流死了 agent 继续跑完。设计者考虑过断开。只考虑了一半——断开是安全的，"接回来"没有做。摸底报告把这一类问题命名为**半途设计**：机制只接了一半的线，比没有机制更危险，因为它制造"已保障"的假象【经验】。同一次摸底里同构的还有三例：审计表建好了没接线，告警格式化了没发送，降级档位文档化了没实现。

## 3.2 "丢消息"丢在哪一段路上

消息从键盘到磁盘，途经五个载体：

1. 前端内存（React state）——易失；
2. HTTP 请求体——易失；
3. 服务端内存（run 上下文）——易失；
4. SSE 流（回复下行）——易失；
5. SQLite——持久。

摸底报告的总诊断只有一句话："运行中的对话没有真相源（SSOT）。一轮 run 的过程态只存在于两个易失载体里——一条一次性 HTTP 流和 server 内存"【经验】。前四个载体全是易失的，第五个才持久，而通往第五个的唯一写路径挂在 run 收尾。run 越长，这段裸奔的窗口越宽；agentic 任务恰恰以长著称。

这个结构还制造了一个查询盲区。运行中会话被读取时（切回、重载、另一个入口查询），读到的永远是 run 开始前的状态。切回后唯一的"临场感"是一次性 GET `/api/runtime-state/:id` 快照（`App.tsx:395-398`），只含 phase 和 token 计数，没有消息正文，且不再更新。run 后台跑完落了库，界面也没有任何机制自动重拉——用户要再切走一次再切回，才能看到已经存在的东西。

## 3.3 每一层都正常，系统仍然出错

把事故里的五个"嫌疑人"挨个过堂。

**UI 无罪。**它如实渲染了数据库里的内容。切换会话时整体销毁重建 runtime 是有意设计，`App.tsx:626` 的 key 注释自述"ensures the runtime is fully recreated on session switch"。

**连接层无罪。**SSE 断开不杀 run 是深思熟虑的决定，注释和 safeWrite 都在。断开这件事本身被处理得干净利落。

**旧 run 无罪。**它完整跑完了自己的 agent loop，收尾时按写好的分支走：`isCurrentRun` 判假，跳过持久化。这个守卫的本职是防止两个 run 同时写一个会话——单看是正确的防双写逻辑。

**RunManager 无罪。**抢占语义有单元测试，"新 run 替换旧 run"的行为与测试锁定的一致。

**SQLite 无罪。**没有写入失败，没有损坏。它只是从未收到那笔写。

五个组件各自守住了局部契约。"用户消息一旦被接受就不会消失"——这条系统级承诺不在任何一层的职责清单上，没有 owner，没有测试，没有报警。三路独立审计撞上同一个结构缺陷【经验】，因为缺陷本来就在结构里：局部正确逐层相加，加不出系统正确。这句话在 3.8 会给出定量版本。

## 3.4 逐帧重放：状态、事件与副作用

把 3.1 的叙事压成一张状态表。M1–M4 是历史消息，M5 是事故中的提问，R1 是被打断的 run，M5′/R2 是重问后的新提问与新 run。

| 帧 | 事件 | M5 所在载体 | R1 输出所在载体 | SQLite | 用户看到的 |
|---|---|---|---|---|---|
| 0 | 会话空闲 | — | — | M1–M4 | 完整历史 |
| 1 | 用户发送 M5 | 前端内存、请求体 | — | M1–M4 | M5 上屏 |
| 2 | RunManager 创建 R1 | 服务端内存 | — | M1–M4 | 生成中 |
| 3 | 模型流式输出 | 服务端内存 | 服务端内存、SSE 流、前端内存 | M1–M4 | 回复逐字出现 |
| 4 | 点击链接，webview 原地导航 | 服务端内存 | 服务端内存（前端副本蒸发） | M1–M4 | 外部网页 |
| 5 | SSE 断开，R1 依设计后台续跑 | 服务端内存 | 服务端内存 | M1–M4 | 外部网页 |
| 6 | 后退，SPA 重载，读库 | 服务端内存 | 服务端内存 | M1–M4 | 少一轮，"丢了" |
| 7 | 用户发 M5′，R2 抢占：abort R1 并覆盖注册 | 服务端内存（即将无主） | 同左 | M1–M4 | 新回答生成中 |
| 8 | R1 收尾，isCurrentRun 判假，跳过落库 | 随 R1 上下文回收 | 同左 | M1–M4 | 新回答继续 |
| 9 | R2 完成，落库 | 永久消失 | 永久消失 | M1–M4、M5′、R2 | 一切"正常" |

两个观察。

第一，丢失是概率性的。帧 7 若发生在 R1 自然跑完之后，M5 已经落库，事故不成立。丢与保之间隔着一场竞速：用户重问的手速对阵 R1 剩余的执行时间。概率性正是这类 bug 长期潜伏的原因——复现要凑齐导航逃逸、run 未完、用户重问三个条件，日常测试几乎不会同时踩中。

第二，这张表是事后人工重构的。系统本身没有记录帧 4 的导航离开、帧 7 的抢占决策、帧 8 的"跳过持久化"。审计团队靠读代码推演加探针测试复现，才把十帧拼出来。顺手列一份**缺失证据清单**——事故调查想要、系统当时给不出的东西：

1. M5 被服务端接受的持久记录；
2. R1 被抢占的事件：何时、被谁、依据什么；
3. "跳过持久化"分支被走到的任何痕迹；
4. 前端导航离开与 SSE 断开的事件；
5. R1 已生成内容在任一时刻的快照。

这份清单先记下，§十二 Evidence Plane 会把它变成正式需求。

## 3.5 症状修复、局部修复与契约修复

同一个事故，三种修法，Howpot 三种都做了（阶段 0 的三个独立 PR）【经验】。放在一起看，档位差异一目了然。

**档一，症状修复：把触发器拆掉。**S0-1 引入 plugin-opener，markdown 链接 onClick 后交系统浏览器打开；Rust 端补 on_navigation 白名单当第二道闸。点链接再也不会把应用带走。局限同样明确：同族触发器还有一排——托盘退出的 `kill_node()` 先 POST shutdown 再 sleep 2 秒强杀，全程不检查是否有 run 在跑（`main.rs:224-227, 404-429`）；OS 关机；进程崩溃。触发器拆得完吗？拆不完。

**档二，局部修复：堵住升级路径。**S0-2 让抢占前先落盘——`start()` 替换旧 run 前 abort 加 `await waitForFinish`，复用既有的 finishPromise 机制，并补上"抢占后旧轮已落库"的测试。假丢不再升级成真丢。但查询盲区原封不动：切回来画面照样缺一轮，用户照样误判，照样重问——只是重问的代价从"永久丢失"降到了"虚惊一场"。

**档三，契约修复：换掉承诺本身。**S0-3 增量持久化：run 开始即写入用户消息（pending 态），assistant 内容按事件节流 upsert，run 收尾从"一次性写入"改成"终态更新"。系统从此多了一条可以宣称的承诺：任何时刻读库，看到的都是最新已知状态。导航逃逸、强杀、断电，读出来的画面顶多缺最后几秒，永远够用户判断"没丢"。

三档全做完，故事还有续集。12 个功能 commit 落地后，团队对分支 diff（+1665 行）做了 7 维审查加逐条对抗验证，又确认 34 条问题【经验】。其中一条与本事故同族：`tryStart` 的同会话并发抢占存在 check-to-use 间隙（TOCTOU，即检查与使用之间状态已被并发方改变）——双标签页或快速双击时，两个抢占同时通过 recheck，后到者静默 abort 先到者刚建的 run，占位行（增量持久化落下的 pending 消息行）永久卡在"生成中"。修法是把 tryStart 按 sessionId 用 promise 链串行化。更有讽刺意味的两条：threadKey 回归是韧性建设自己引入的；回滚逻辑里的"安全快照"藏着毫秒时间戳碰撞，好快照先被坏内容覆盖再被拷回去。

这段续集给出本节真正的结论。逐点修补没有收敛判据——修完一批，对抗审查再挖一批，没有办法回答"修到什么程度算完"。回答这个问题需要一份完整的承诺清单：系统对外维持哪些保证，每条保证归谁所有，破坏它的路径有哪些。有了清单，"修完"才有定义：清单上每条都有 owner、有测试、有证据。这份清单，就是下一节要命名的东西。

## 3.6 给缺失的东西命名：六类契约

事故里缺的每一样东西，都能归进 §1.9 六类契约的某一问。逐一对照本次事故：

| 契约 | 核心问题 | 本次事故中的缺口 |
|---|---|---|
| 真相契约 | 哪份状态算数，谁拥有它？ | 运行中的对话没有真相源；唯一写路径挂在 run 收尾 |
| 转移契约 | 什么事件能让状态从 A 变成 B？ | 抢占转移没有定义旧 run 数据的归宿；tryStart 存在并发间隙 |
| 副作用契约 | 声称做了什么，外部世界实际发生了什么？ | 本次仅擦边：工具的文件改动实时落盘，但归属消息可随进程终止丢失 |
| 交互契约 | 用户、连接与后台 run 如何保持一致？ | 断开安全但无接回；后台完成零通知；用户依据过期画面做出了致损决策 |
| 权限契约 | 谁以谁的身份、在什么边界内行动？ | 一次点击就能把运行时容器带离应用；导航边界无任何防线 |
| 证据契约 | 凭什么相信状态、动作和完成声明？ | 3.4 那份缺失证据清单本身 |

六条不变量（§1.1）在本次事故里各有对应的违反：

1. **状态可归属**：每个持久状态都有 owner、ID、版本和合法读写路径。（M5 在五个载体间漂流，没有一处算数。）
2. **转移可解释**：每次状态变化都有触发事件、前置条件和终结原因。（R1 从 running 到消失，系统里没有任何一行记录解释它。）
3. **副作用可对账**：每次外部动作都有意图、尝试、结果和真实 outcome。（本次擦边，§七主场。）
4. **权力有边界且有期限**：模型、subagent 和工具的权限，不能只靠 prompt 维持，恢复状态不等于恢复旧授权。（webview 的导航权同理——边界要在结构上关死，一个 `target="_blank"` 就能穿过的防线等于没有。）
5. **失败可收敛**：失败、中断和恢复最终进入已定义状态；不能恢复时明确终结。（被打断的一轮悬在"既没完成也没终结"的暗区，最后无声蒸发。）
6. **结论有证据**：完成、失败和安全声明都能指向运行证据。（复盘全靠读代码推演，十帧时间线没有一帧有运行时记录背书。）

§1.1 那句压缩语在这里有了完整的反面教材：**每个状态有归宿，每个故障有路径，每个中断可恢复或诚实终结**——三条全违。还剩一个问题：一家小团队的一次事故，凭什么代表一类现象？

## 3.7 从一次事故到一类现象

单个事故可以归咎于工期、疏忽或运气。一类现象不能。

证据 §1.1 已经摆过：同一批模型只换 harness 差 23.8 个百分点；1600 余条故障轨迹里三大类故障全在系统层。这里只补一个对账动作——把 MAST 的三类占比按在本次事故上，逐类都能对上号：规范缺陷（"消息不消失"这条承诺没人 own）、协调失败（抢占与持久化两个机制互不知情）、验证缺失（抢占有测试、其对持久化的副作用无测试）。一次小团队的事故，把整个分类法演了一遍。

同款缺陷也不难在别处找到。另一个 agent 项目 z-agent 的会话记录里留着同一句诊断：streaming 中途 abort 抛出 AbortError，异常直接冒出 for-await 循环，当前 step 的文本永远不会进入待持久化列表——落库的只有前几步，用户正在看的那一段恰好是丢的那一段【经验】。两个代码库掉进同一个坑："过程态何时落盘"这个问题只要没被显式回答，答案就默认是"最后一刻"。

## 3.8 改进不可叠加

"逐点修补"的失效还有更精确的度量。AHE 是一个自动演化 coding-agent harness 的系统，其消融数据显示：三个正收益组件单独测量共 +11.1pp，组合后只剩 +7.3pp【预印，arXiv:2604.25850】。论文给了机理——三个组件都把行为推向同类闭包式验证，叠加只是重复检查。改进彼此吞噬。

更值得警惕的是预测能力的不对称。同一工作里，agent 预测"这个改动会修好什么"的精度 33.7%、召回 51.4%；预测"会弄坏什么"的精度 11.8%、召回 11.1%。说清一个改动为什么有帮助，勉强及格；预判它即将破坏什么，接近瞎猜。Howpot 的复审续集是这条统计的现场版：韧性建设自己引入了 threadKey 回归，串行化 tryStart 让两个既有测试的隐式时序假设当场失效【经验】。

这两组数字合起来，就是"需要契约体系"的定量理由。局部改进不可线性外推，破坏面无法事前预测，那么系统的可靠性只能靠另一条路径获得：显式声明每条承诺，给每条承诺配上独立于改动过程的验证。这正是六类契约的立足点。

## 3.9 破坏实验：四处强杀

每章末尾都有一次主动破坏。四个实验都要真跑：kill -9，重启，观察。对象可以是 Howpot 修复前的镜像，更有价值的对象是读者自己的系统。

**一杀：模型调用前。**用户消息已被服务端接受，run 尚未开始。修复前的 Howpot：消息只在内存，重启后无痕，而用户端明明看到它发出去了。要回答的问题：用户消息在哪一行代码之后才第一次落盘？

**二杀：流式中。**回复已生成一半。修复前：半截回复蒸发，重启后这一轮完全缺失，连"[已中断]"标记都没有。要回答的问题：重启后，这一轮以什么状态呈现给用户？

**三杀：落库前。**run 已完成，收尾持久化尚未执行。完整回复用户已经看过，库里却永远不会有——"看过即拥有"是错觉。要回答的问题：收尾写库的窗口有多宽？半写状态可识别吗？

**四杀：工具执行后。**副作用已经发生（文件已改、命令已跑），记录尚未落盘。修复前的 Howpot：file_snapshots 实时落了盘，但它归属哪条消息随进程死亡一起丢失——外部世界改了，没人说得清是谁改的。要回答的问题：外部改动与发起它的对话之间的账，记在哪里？

四杀各自命中一类契约：一杀真相，二杀交互与真相，三杀转移，四杀副作用与证据。答不上来的那几杀，就是自己系统的契约缺口图初稿。§十三会把这四杀做成自动化故障注入，进 CI 反复跑。

## 立即可做的一个动作（五分钟）
