入门卷把一个 harness 拆成了部件：agent loop、model adapter、tool registry、context 与 memory、trajectory、verifier，外加 safety 控制面。每个部件是什么、为什么存在、在一次 turn 里怎么咬合，那一卷讲完了。它的定位是一张蓝图——读完之后，部件的名称和职责一目了然。

入门卷发布之后，收到最多的反馈是同一件事。读者照着蓝图搭出了自己的 agent，多数是让 AI 动手写，自己对着图纸检查。搭完一看，该有的都有：loop 在转，工具挂上了，压缩、验证一样不少。可一跑起来就不对劲。同一个任务，昨天还顺顺当当，今天就卡在半路。出了错，日志翻半天，不知道该怪哪一层。好不容易修好这处，过两天别的地方又塌了。

更具体的怪事也有一批：agent 声称做完了，其实没做；同一个工具悄悄跑了两遍，账单和副作用都翻倍；界面卡在"生成中"，后台其实早就死了。这些事没有一件是"缺部件"——部件都在，是部件没把自己的活干到底。更麻烦的是，干没干到底，从外面看不出来。

所以蓝图之外，还缺另一类知识：怎么发现问题出在哪个机制；怎么判断一个机制是真的在工作，还是只是存在；怎么用工程手段保证它在崩溃、并发、截断这些边角情况下仍然有效。蓝图标出墙的位置，这类知识决定墙里的钢筋怎么绑。这就是第二卷。

第二卷讲运行时：系统在一次运行中究竟发生什么。做法是把部件之间那些从来没写下来的约定一条条写成明文——状态归谁、转移凭什么发生、工具做过的事拿什么对账、中断之后谁负责收场——再用故障证明它们真的成立。全卷贯穿一个可运行的单机 runtime，每章把它主动破坏一次：强杀、断连、并发抢占。要运行几个月才暴露的备份、发布、安全、成本，留给第三卷。

读完本卷，能做到四件事：任何一条消息，说得清它此刻在哪个载体里、哪份算数；进程在任意一行被杀，说得清重启后系统怎么收敛；agent 声称"做完了"，拿得出独立于这句话的证据；拿到任何一个 agent 系统，能按同一套问题清单审出它的缺口。

这些症状还有一个共同点：换更强的模型，好一阵，然后照旧。症状与部件品质关系不大，有测量为证——Harness-Bench 把 8 个模型后端接进 6 个 harness，跑同一组 106 个沙箱任务：模型不动，只换 harness，最好与最差差 23.8 个百分点（NanoBot 76.2 对 OpenClaw 52.4）【预印，arXiv:2605.27922】。同一份测量还有一条对选型的提示：越强的模型，跨 harness 方差越小——前沿模型能在烂 runtime 里自我补救，弱一档的模型没这个本事。由此可推（推断，非论文原文）：runtime 质量对中小模型与私有化部署的价值最高。那 23.8 个百分点落在部件之外的什么地方，是本章要回答的问题。

## 1.1 和在线服务差出三个变量

把 agent runtime 当成普通在线服务来搭，是多数怪事的共同起点。在线服务二十年攒下的可靠性工程——框架、重试中间件、发布流程、SRE 手册——押在三个默认值上：进程可弃、重试无害、行为可复现。这三个默认值不写在任何文档里，它们以出厂设置的形式活在每一层基础设施中。agent 一来，三个默认值逐个失效，而失效是无声的。

进程可弃的默认，活在发布流程里。滚动发布随手杀进程，因为在途请求毫秒级结完，杀掉的损失一次重试就补回来；业务进程无状态，真相全在数据库，挂了拉起来就是——重启是运维的万能药。agent 把两个前提同时抽掉：一次运行分钟到小时级，横跨部署、重启、断连，照旧随手发布，等于每次发布都拿用户跑到一半的任务献祭；loop 又恰恰满身状态——半轮输出、工具结果、下一步计划全在内存里攒着，重启大法照吃不误的结果，是库里只剩开头几步，用户半小时的推进凭空蒸发。执行跨越故障边界，"进程活着"从隐含前提变成撑不满全程的运气。传统计算机科学处理过长活任务——长事务、工作流引擎、durable execution 是一整个领域——但那从来没进过 web 框架的默认件，得自己去请。

重试无害的默认，活在超时逻辑里。超时了就重发，反正 GET 幂等、去重键兜底，重试次数是个随手填三的配置项。agent 的每一步都可能改文件、发消息、花钱——超时重试一个"发邮件"工具，客户收到两封。副作用泄向外部世界，幂等从基础设施的赠品变成每一步的显式义务，而没人通知过重试逻辑这件事。

行为可复现的默认，活在整套验证手段里。出了 bug 复现一遍，改了代码回归一遍，怀疑哪里不对 diff 一遍——全部以"同一输入给同一输出"为前提。模型偏偏在这里例外：同一份输入，两次输出可以不同。核心组件的输出不确定，回归测试不能穷举，重放不能逐字节比对，"预期行为"从一个值变成一个分布。软件工程几乎全部验证手段都建立在确定性上，这个地基在这里空了。

麻烦不止三个变量各自，更在相乘：执行足够长，崩溃就会落在任意一步；每一步都有副作用，重试就可能重复任意动作；输出不确定，事后就无法靠重放判定当时发生了什么。三个变量具体会破坏什么，得逐个说清。

## 1.2 威胁清单与六类契约

三个变量各自划开一类口子。

跨故障执行的口子是状态撕裂：执行的中间成果住在内存，真相住在磁盘，两者随时分家；进程死在分家的瞬间，分家就永久化。开头的"卡在生成中""界面早死"都是撕裂的现场照。

副作用外泄的口子是账对不上：工具返回成功不等于外部世界成功；重试造出第二笔副作用；agent 声称做完不等于真做完。"工具悄悄跑两遍""说做完了其实没做"住在这一类。

输出不确定的口子是无从归因：传统排障的两板斧——重放复现、对照预期——双双失效，重放不出同一条轨迹，预期本身是个分布。"日志翻半天不知道怪哪一层"是这类威胁的日常形态。

三类口子在真实系统里的占比，MAST 给过测量：标注 1600 余条多 agent 故障轨迹（标注者一致性 Kappa 0.88），规范缺陷 41.77%、协调失败 36.94%、验证缺失 21.30%——三类全落在系统设计层；不换模型，只加语义验证可换回 +15.6pp，只改角色规范 +9.4pp【评审，arXiv:2503.13657，NeurIPS 2025 D&B；截至 2026-07 检索为本领域唯一评审级工作，核对记录 `../research/volume2/02-academic-verification.md`】。威胁是系统层的，解药也在系统层。

挡这三类口子，靠在出事的地方打补丁行不通——补丁治的是上一次的路径，威胁下次换一条路进来。要挡住一类威胁，系统得给出一种在所有路径上都成立、并且可检验的承诺。本卷把这样的承诺叫**运行时契约**：系统欠外界的合同，一共六份，每份一句话。哪六份，不靠列举靠反推——站到救援者的位置上问：崩溃已经发生、账已经乱了、轨迹已经无法重放，此刻系统最少要守住什么，事情才有救？

对着状态撕裂问。进程死在半路无法根绝，那重启后的救援凭什么展开？第一凭知道以谁为准——**真相契约**，承诺状态可归属：每个持久状态都有 owner、ID、版本和合法读写路径，"哪份算数"从不含糊。第二凭悬着的东西有终点——**交互契约**，承诺失败可收敛：失败、中断和恢复最终进入已定义状态，不能恢复时明确终结。撕裂无法根绝，悬而不决可以根绝；而悬而不决的东西最后都悬在用户眼前——卡住的"生成中"、断掉的流——所以这份合同签在交互面上。

对着账对不上问。事后对账的前提，是当时记过账。意图、尝试、结果、真实 outcome，四样少记一样，对账就多一个盲区——"工具返回成功"顶多算工具的一面之词，少了 outcome 那一样，盲区恰好盖住最贵的一类事故。四样记全——**副作用契约**，承诺副作用可对账。

对着无从归因问。重放这条路死了，剩下的路只有两条。一条是原因当场记：每次状态变化带上触发事件、前置条件和终结原因，不指望事后推——**转移契约**，承诺转移可解释。另一条是信任换成证据：完成、失败和安全声明都能指向运行证据，组件的话不可全信——**证据契约**，承诺结论有证据。

第六份合同来自变量的组合：输出不确定的组件在长时执行中持有权力。不确定意味着权限不能靠 prompt 维持——模型可能被输入操纵，也可能单纯犯错，边界不能靠自觉；长时执行意味着授权要跨越崩溃、恢复与 fork——批过的事过了多久、换了上下文还算不算数，成了绕不开的问题。**权限契约**，承诺权力有边界且有期限：恢复状态不等于恢复旧授权（§十）。

六份合同压成一句话：**每个状态有归宿，每个故障有路径，每个中断可恢复或诚实终结。**合同立住了，还悬在半空——契约自己不会履行，得有零件对它负责。

## 1.3 职责分配长出组件图

从契约到零件，走的是职责分配：一份一份问，谁来履行它。每一次分配都先看清不设防时的死法——这一章的组件没有一个是发明出来的，全是被死法逼出来的。

先看没人设计时，状态自己会长成什么样。loop 在内存数组里攒消息，攒够一轮写库；前端为了显示快，自己留一份会话状态；工具把结果顺手写进文件。三份记录平时相安无事——直到进程在写库前被杀。重启之后，内存那份没了，前端那份还显示"生成中"，文件那份没人说得清归属哪条消息。这不是丢数据的问题，是"该信哪份"从来没人回答过：写的时候人人能写，读的时候份份都像真的。开头那件怪事——退回来对话记录全没了——就是这么来的：用户看见的那份，从来不是算数的那份。

所以真相契约的第一刀切在写权上：真相只放一处，允许写它的组件只有一个。这个唯一算数的地方，就是**状态层**。数据工程里这条纪律叫单源真相（SSOT），即每个数据元素只在一处被 mastered，其余位置只许只读引用或带调和机制的副本【规范/官方文档，Wikipedia: Single source of truth】——不是新发明，是 agent 系统把老坑重新踩了一遍才想起来。单机参考实现选 SQLite（WAL 模式）单写者，看中的正是它的不宽容：单写者天然串行，写冲突、共识、分布式事务这一整类问题直接不存在。代价也直说：吞吐有上限，将来多实例要迁 Postgres 加 lease。这笔交换划算——原型期死于状态撕裂的系统，远多于死于吞吐不足的。

真相集中了，历史还没着落。天真的做法是状态行就地 UPDATE：run 从 running 改成 failed，一改了之。排障的人半夜对着库问"它怎么变成 failed 的"，库里只有现在的样子，没有来路；文本日志倒是有，但那是给人读的散文，格式随手、字段残缺，恢复扫描没法拿它当依据。死因在于：解释和证据一旦允许事后修订——或者压根没记——就都不可信。转移契约和证据契约要的是同一样东西：改不掉的历史。所以第二刀是只追加：历史永不改写，记错了追加更正，指向原处。载体两件：**事件流**，发生过什么的机器可读记录，供恢复扫描、UI 订阅、审计回放；**证据存储**，trajectory、policy 决策、verifier 结论、artifact 来历的归档处。状态层回答"现在是什么"，这两件回答"凭什么相信"。根基不新：数据库的 WAL、金融的复式账簿，同一条纪律——历史可信，靠的是改不了。代价是存储上涨、内容涉隐私（采集策略交第三卷）；哪天成本真扛不住，事件可以稀疏，不可以改写。

副作用契约的死法要慢放才看得清。天真的执行顺序：模型说调工具，executor 直接调，返回后把结果写库、塞回上下文——账也记了，只是记在动作之后。账与动作之间于是有一条缝：崩溃恰好落在"邮件已发出、记录未写下"的瞬间，系统苏醒后完全不知道自己发过邮件，它能做的最"负责任"的事，恰恰是再发一遍。"工具悄悄跑两遍"多半是这条缝的产物。缝堵不上，除非把顺序定死：先落盘意图，再执行，再落盘结果；工具返回成功也只算一面之词，外部世界是否真的变了，要另一份证据。外部动作一律走这道门，门就是入门卷已有的 tool executor——本卷给它加的是这份先记账再动手的合同（§七是它的主场）。

模型调用的死法藏在恢复路径上。恢复一个跑到一半的 run，直觉做法是把没跑完的部分重跑一遍——对确定性代码这行得通，重跑得到同样的结果。模型不给这个保证：同一份输入，两次输出可以不同，重跑出来的"下半场"接不上用户已经看过的上半场，恢复反而制造出第二个版本的历史。出路只有一条：把每次调用当成一次性事件，完整留档——模型标识与版本、参数、上下文摘要、输出、token 计量——恢复时复用记录，永不重跑。这份档案的管理者就是入门卷的 model adapter，一次调用的全部边界（参数、重试、流式、计量）收在它手里。

循环本身的主人还是 agent loop：组 context、调模型、派工具、判终止。它的死法 1.2 已经讲过，就是状态撕裂的标准现场：内存里攒着半轮成果，进程一死全部蒸发。所以它领到的约束全卷最硬：在内存里攒的一切，要么立刻落盘，要么等于不存在。

还剩两份合同没人认领：交互契约的收敛，权限契约的闸口。它们的死法长在同一个地方。天真的系统里，每个入口各自为政：UI 直接调 loop，API 也调，scheduler 也调，各自实现自己的取消、自己的权限检查。用不了多久，同一个"取消"长出三种语义——UI 的取消只断了流，run 还在后台跑；API 的取消杀了 run，没记原因；双击"发送"，两个 run 同时写一个会话。至于崩溃后满地的孤儿 run，没人认领，因为"谁负责扫尾"从来没被指定过，每个入口都以为是别人的事。病根一句话：同一种语义实现了 N 份，就会漂移成 N 种。解法是收口：所有执行，无论从哪个入口来，过同一道闸——准入、互斥、policy、limit 在这里判，孤儿 run 的发现和送终也归这里。这道闸叫 **run manager**，这个决策叫**单执行内核**：permission、cancel、resume、工具执行四种语义只在内核实现一次，入口只剩两件事——适配意图、转发流。代价直说：每接一个新入口都要多写一层适配，原型期显得绕，直接调内部函数快得多——快出来的每一分钟，将来都要用"两种取消语义对不上"的排障加倍偿还。推翻这个决策需要一种必须绕过内核才成立的入口需求，目前没见过站得住的例子（入口细则与逐格检查表在 §四）。

最后是入口层：UI、API、IM 渠道、scheduler，把外界动作变成一次合法提交。它的死法开场就见过：前端为了体验流畅，自己留一份状态，超时了自己把任务标成失败。猜错的那天，库里 run 还活着，用户照着"失败"重发一遍，两个 run 并行写一个会话；或者反过来，后台早死了没人通知前端，界面永远"生成中"。病根是显示层拿到了定义真相的权力。所以入口层的约束只有一条：界面上显示的一切都是**投影**，即持久状态在别处的只读呈现——可丢弃、可重建、可过期，真相不能。投影不回写，UI 的一切聪明猜测活不过一次刷新。代价是乐观更新受限，用户感知比"前端先改再同步"慢半拍；这个决策不靠辩论检验，靠章末的破坏实验——哪天实验通不过，是实现坏了，回来修实现。

## 1.4 一条时序走到底

架构图是静态的，判断它对错要看动线。一条时序：用户发一条消息，任务顺利完成。**加粗处是落盘点**——数一数有几个、都在谁手里，这张架构的正确性一半押在这上面。

（配图占位：正常路径时序图）

1. 入口收到消息，提交 run manager；
2. run manager 准入：同会话互斥、policy、limit 检查；**落盘：run 记录建立，事件流记 run.created**；
3. **落盘：用户消息入库（pending 态）**——从这一刻起消息归系统管，之后任何崩溃都丢不掉它；
4. agent loop 组装 context：从状态层读消息、摘要、记忆，生成给模型的投影（不落盘——投影可重建）；
5. model adapter 调模型；**落盘：调用记录（模型标识、参数、上下文摘要）**；流式输出按事件节流更新消息，同时经事件流推给 UI；
6. 模型要求调工具：tool executor **先落盘意图（含幂等 key），再执行，再落盘结果与事件**；
7. 循环 4-6，直到模型给出终答；
8. run 收尾：**落盘：消息终态、run 置 succeeded，事件流记 run.finalized**；
9. 事件流推送完成通知；UI 不在线也无妨——下次读库，看到的就是全部。

九步里每一个落盘点，都是将来某次崩溃的救命锚：进程死在任何一行，重启后的系统从最后一个落盘点接着收拾——那条恢复时序怎么走、锚怎么用，是 §六 的主场。这些持久对象（run、消息、调用记录、效应账、事件）的完整登记表在 §五。本章只立一个全卷通用的判断标准：**任何机制设计完，都要能在这条时序上标出自己的位置——哪一步写了什么，将来被谁读到。**标不出位置的机制，多半就是读者反馈的那种"存在但没干活"的部件。

## 1.5 六类契约总览

六份合同、八个组件，收进一张表——这张表同时是全卷的分章地图，每份契约一章主场，逐份展开、逐份破坏、逐份验收：

| 契约 | 承诺 | 核心问题 | 主场 |
|---|---|---|---|
| 真相契约 | 状态可归属 | 哪份状态算数，谁拥有它？ | §五、§九 |
| 转移契约 | 转移可解释 | 什么事件能让状态从 A 变成 B？ | §四、§六 |
| 副作用契约 | 副作用可对账 | 声称做了什么，外部世界实际发生了什么？ | §七 |
| 交互契约 | 失败可收敛 | 用户、连接与后台 run 如何保持一致？ | §八（终态收敛与 §四 分头兑现） |
| 权限契约 | 权力有边界且有期限 | 谁以谁的身份、在什么边界内行动？ | §十、§十一 |
| 证据契约 | 结论有证据 | 凭什么相信状态、动作和完成声明？ | §十二 |

开场怪事里还剩一件没安放："改好一处，别的地方又塌。"它的病根是暗契约——部件之间没写下来的假设，改动踩上谁都不知道。这件事没有单份契约可认领，解法是把六份合同全部写成明文，也就是本卷的全部内容；它的定量画像在 §三。四个承重决策（单写者、只追加、单执行内核、投影不回写）合起来则是同一个偏好：**把复杂度花在"出事之后还能讲清楚"上。**这个偏好有适用边界——失败代价足够低的系统（一次性脚本、随手重跑的实验）用不上本卷多数契约，那类系统的承诺停在"尽力"档就够。

到这里，本章立住的是"系统欠外界哪六份合同"。可是一个具体的 runtime 摆在面前——也许就是读者照入门卷搭的那个——合同履行没履行，拿什么判？承诺要变成判据，判据要能变成检查，检查还得分出"保证"与"尽力"的档位。这是 §二 要解决的问题。

## 1.6 破坏实验：真相源分叉

每章一次主动破坏，本章打"投影不回写"。

做法：在参考实现的 UI 里故意保留一份本地 run 状态副本；启动一个 run，断开事件流，在 UI 本地把状态改成 completed（模拟一个"贴心的"前端根据超时猜状态）；此时数据库里 run 仍是 running。然后做两件事：刷新页面；等 run 真正结束。

预期：刷新后 UI 无条件回到数据库投影（显示 running），本地猜测被丢弃；run 真正结束后，UI 经事件流或重拉收敛到真实终态。通过判据：全程数据库从未被 UI 侧写入。失败样态：实现里存在任何一条"UI 状态回写数据库"的路径（比如前端超时后调接口把 run 标成 failed），实验会让它显形。修复方向只有一个：删掉回写路径，"超时该标 failed"交给 run manager 的看门狗（§四）——UI 的职责是显示真相，判定真相轮不到它。
