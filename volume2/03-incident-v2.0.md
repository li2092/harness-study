2026 年 7 月上旬，桌面案例项目——第二章里反复举例的那个桌面 agent 应用——收到一条用户报告。这个应用的结构在同类产品里很典型：Tauri 壳套 React 前端，Node 服务端，SQLite 存储，回复经 SSE 流式下推。用户在一个已有几轮历史的会话里提了问，回答正在逐字出现；回答里带一个链接，点了它，整个窗口跳去了那个网页。没有新标签页，没有浏览器工具栏，只能右键"后退"。退回来，应用重新加载，对话列表还在，刚才那一轮问答不见了。用户判断记录丢了，把问题重新问了一遍，这次顺利得到回答。后来核对才发现：第一次的提问和那半截回答，从此再也找不到。

复盘出现了一个矛盾的局面。UI 正常，连接层正常，run 正常，数据库正常——每一层都严格执行了自己的设计，消息仍然永久消失了。

第一章展开了地图，第二章把四个问题变成了判据。本章拿这次事故做一个双向的检验。**前向**：把事故逐帧拆开，看缺失的每一样东西能不能在六契约×四问矩阵上找到名字——找不到名字的缺口，说明矩阵漏了格。**反向**：把时间拨回事发之前，拿第一章的六问和第二章的判据把这套系统审一遍，看每个根因能不能被提前圈出——圈不出的根因，说明判据失灵。判定口径先立在这里：前向找不到名字，是矩阵漏了格，得补；反向圈不出根因，先分辨它是结构缺口还是实现 bug——结构缺口漏了才算坐标系失灵，实现 bug 圈不到恰恰是坐标系的正常边界，该标注不该硬扩。读完本章，手里应当多三样东西：一张十帧时间线、一份缺失证据清单、一张第一版契约缺口图——外加一个可以搬回自己系统的检验流程。评估别人系统的读者尤其该在这里停留：事故是全卷最现成的 assessor 素材，别人的每一份 postmortem 都是一张待归格的对账表。

## 3.1 事故还原：三个缺口串成一次丢失

还原要从摸底说起。团队同批收到的其实是两份报告——除了开头那件"点链接后记录全没了"，还有一件"切走再切回，运行中的会话一片空白"。两件症状都指向状态，而状态问题最忌讳边猜边改。团队没有直接动代码，先做了一轮全面摸底：9 路专项审计（7 路主线加 2 路查漏），每条 P0/P1 发现由独立验证者以"默认是误报"的立场对抗核实，全部结论落到 file:line；摸底报告首页写着一句话："本报告未修改任何代码"【经验】。先诊断，后动刀。以下机制还原全部出自这份报告。事故由三个互相独立的缺口串成。

**缺口一**：一次点击就能把应用带走。前端渲染链接的代码只有一行——`Thread.tsx:50` 输出 `<a target="_blank">`，markdown 里的链接总得能点，这一行再普通没有。问题在壳层：Tauri 壳没有装 opener 插件，`main.rs` 没有注册 on_navigation 回调，capabilities 只有 `core:default`。在 Tauri 的默认行为下，`_blank` 不开新窗口，主 webview 原地导航，整个 SPA（single-page application，单页应用）被外部网页替换，前端所有内存状态蒸发。也没有 beforeunload 守卫拦一下。

**缺口二**：退回来之后，画面撒了谎。SPA 重载后从 localStorage（浏览器本地存储）恢复会话选择，再 GET `/api/sessions/:id/messages` 读消息——这条路直读 SQLite（`sessions.ts:372-380`）。问题在于，被打断的那轮 run 还没结束，而这套系统唯一的落库点 `persistRunMessages()`（`chat.ts:2418-2544`）只在 run 收尾的 finally/catch 里被调用（`chat.ts:2166/2227`）。库里存的是 run 开始前的历史。于是画面缺了一轮，看起来就是"丢了"。此刻数据并没有丢——run 还在服务端后台跑，跑完会落库。那件"切走切回一片空白"的另一份报告，根子就是这同一条：读库永远读到 run 开始前。

**缺口三**：用户的合理反应，把假丢变成真丢。用户在"空了一轮"的会话里重新提问。`RunManager.start()`（`run-manager.ts:43-49`）的抢占语义是：abort 旧 run，随即用新 run 覆盖注册表，不等旧 run 落盘。旧 run 的收尾逻辑走到 `isCurrentRun` 检查（`chat.ts:2219-2220`），发现自己已经不是当前 run，跳过整个持久化。被打断那一轮——用户的提问加上已生成的半截回答——从未写入数据库。抢占的"替换"行为有单元测试锁定，但没有任何测试问过它对持久化的副作用。

值得停一秒的细节：服务端"SSE 断开不杀 run"是有意的设计。第二章 2.4 拿它示范过契约六要素，evidence 那一格填不出来；本次事故正是那个空格的兑付现场：这个设计只做了一半——断开确实安全（`chat.ts:1642-1644` 的注释写得明明白白，还有专门的 safeWrite 保证流死了 agent 继续跑完），"接回来"却没有做，后台跑完也无人知晓。摸底报告把这一类问题命名为**半途设计**：机制只接了一半的线，比没有机制更危险，因为它制造"已保障"的假象【经验】。同一轮摸底与复审里同构的还有三例：审计表建好了没接线，告警格式化了没发送，降级档位文档化了没实现。第一章 1.3 的 hook 案例是它在配套实现项目里的同款——写了、接通、生效，是三件事。

三个缺口各自独立，各自都不足以丢数据；串在一起，丢失就只差一个点链接的用户。这一节手里多了根因链，下一节把它铺到消息走过的路上。

## 3.2 "丢消息"丢在哪一段路上

根因链落到载体上看得更清楚。一条消息从键盘到磁盘，途经五个载体：

1. 前端内存（React state）——易失；
2. HTTP 请求体——易失；
3. 服务端内存（run 上下文）——易失；
4. SSE 流（回复下行）——易失；
5. SQLite——持久。

摸底报告的总诊断只有一句话："运行中的对话没有真相源（SSOT）。一轮 run 的过程态只存在于两个易失载体里——一条一次性 HTTP 流和 server 内存"【经验】。前四个载体全是易失的，第五个才持久；摸底那句"两个易失载体"点的正是其中承载 run 过程态的两个——服务端内存与那条下行的 SSE 流——而通往第五个的唯一写路径挂在 run 收尾。run 越长，这段无保护的窗口越宽；agentic 任务恰恰以长著称。

这个结构还制造了一个查询盲区。运行中会话被读取时——切回、重载、另一个入口查询——读到的永远是 run 开始前的状态。切回后唯一的"临场感"是一次性 GET `/api/runtime-state/:id` 快照，只含 phase 和 token 计数，没有消息正文，且不再更新。run 后台跑完落了库，界面也没有任何机制自动重拉——用户要再切走一次再切回，才能看到已经存在的东西。真相源缺席，投影就只能靠猜；靠猜的投影，迟早骗到用户做出致损的决策。这个查询盲区先钉在这里——它落在交互契约那一格，3.6 会拿它兑现。

## 3.3 每一层都正常，系统仍然出错

载体查完，回到组件。把事故涉及的五个组件逐一核查，问同一个问题：它有没有违背自己的设计。

UI 与设计一致。它如实渲染了数据库里的内容。切换会话时整体销毁重建 runtime 是有意设计，`App.tsx:626` 的 key 注释自述"ensures the runtime is fully recreated on session switch"。

连接层与设计一致。SSE 断开不杀 run 是深思熟虑的决定，注释和 safeWrite 都在。断开这件事本身被处理得干净利落。

旧 run 与设计一致。它完整跑完了自己的 agent loop，收尾时按写好的分支走：`isCurrentRun` 判假，跳过持久化。这个守卫的本职是防止两个 run 同时写一个会话——单看是正确的防双写逻辑。

RunManager 与设计一致。抢占语义有单元测试，"新 run 替换旧 run"的行为与测试锁定的一致。

SQLite 与设计一致。没有写入失败，没有损坏。它只是从未收到那笔写。

五个组件各自守住了局部约定。"用户消息一旦被接受就不会消失"——这条系统级承诺不在任何一层的职责清单上，没有 owner，没有测试，没有报警。三路独立审计撞上同一个结构缺陷【经验】，因为缺陷本来就在结构里：局部正确逐层相加，加不出系统正确。第二章 2.9 把这件事列为"看起来对"的第三层，3.8 会给它配上定量版本。

## 3.4 十帧重放：状态、事件与副作用

逐一核查给出了"谁都没错"；要看清"哪里错了"，得把 3.1 的叙事压成一张逐帧的状态表。M1–M4 是历史消息，M5 是事故中的提问，R1 是被打断的 run，M5′/R2 是重问后的新提问与新 run。

![](figures/embed/tb-03-1.png)

两个观察。

第一，丢失是概率性的。帧 7 若发生在 R1 自然跑完之后，M5 已经落库，事故不成立。丢与保之间隔着一场竞速：用户重问的手速对阵 R1 剩余的执行时间。概率性正是这类 bug 长期潜伏的原因——复现要凑齐导航逃逸、run 未完、用户重问三个条件，日常测试几乎不会同时踩中。

第二，这张表是事后人工重构的。系统本身没有记录帧 4 的导航离开、帧 7 的抢占决策、帧 8 的"跳过持久化"。审计者靠读代码推演加探针测试复现，才把十帧拼出来。顺手列一份**缺失证据清单**——事故调查想要、系统当时给不出的东西：

1. M5 被服务端接受的持久记录；
2. R1 被抢占的事件：何时、被谁、依据什么；
3. "跳过持久化"分支被走到的任何痕迹；
4. 前端导航离开与 SSE 断开的事件；
5. R1 已生成内容在任一时刻的快照。

这份清单先记下，第十三章 Evidence Plane 会把它变成正式需求。用第一章 1.3 的成熟度尺说，它就是这套系统从 L1 升 L2 的完整工单。

## 3.5 症状修复、局部修复与契约修复

时间线拆完，轮到修。同一个事故，三种修法，桌面案例三档都做了——摸底方案的阶段 0 拆成三个独立 PR 并行推进【经验】。放在一起看，档位差异一目了然。

**档一，症状修复**：把触发器拆掉。第一个 PR 引入 plugin-opener，markdown 链接点击后交系统浏览器打开；Rust 端补 on_navigation 白名单当第二道闸。点链接再也不会把应用带走。局限同样明确：同族触发器还有一排——托盘退出的 `kill_node()` 先 POST shutdown 再 sleep 2 秒强杀，全程不检查是否有 run 在跑；OS 关机；进程崩溃。触发器拆得完吗？拆不完。

**档二，局部修复**：堵住升级路径。第二个 PR 让抢占前先落盘——`start()` 替换旧 run 前 abort 加 `await waitForFinish`，复用既有的 finishPromise 机制，并补上"抢占后旧轮已落库"的测试。假丢不再升级成真丢。但查询盲区原封不动：切回来画面照样缺一轮，用户照样误判，照样重问——只是重问的代价从"永久丢失"降到了"虚惊一场"。

**档三，契约修复**：换掉承诺本身。第三个 PR 做增量持久化：run 开始即写入用户消息（pending 态），assistant 内容按事件节流 upsert，run 收尾从"一次性写入"改成"终态更新"。系统从此多了一条可以宣称的承诺：任何时刻读库，看到的都是最新已知状态。导航逃逸、强杀、断电，读出来的画面顶多缺最后几秒，永远够用户判断"没丢"。

三档全做完，复审还有新发现。摸底方案四个阶段共 12 个功能 commit 落地后，团队对分支 diff（+1665 行、35 个文件）做了 7 维审查，每条发现照旧逐条对抗验证，确认 34 条、剔除 4 条误报【经验】。其中一条与本事故同族：`tryStart` 的同会话并发抢占存在 check-to-use 间隙（TOCTOU，即检查与使用之间状态已被并发方改变）。双标签页或快速双击时，两个抢占同时通过 recheck；后到者静默 abort 掉先到者刚建的 run，那条 run 落下的 pending 占位行就永久卡在"生成中"。修法是把 tryStart 按 sessionId 用 promise 链串行化。第二章 2.7 拿它当转移契约的反例，出身就在这里——修完事故主路径之后挖出来的第二层。

同一批复审里更有讽刺意味的是另外几条。threadKey 回归是韧性建设自己引入的；回滚逻辑里的"安全快照"藏着毫秒时间戳碰撞，好快照先被坏内容覆盖再被拷回去。还有一条经验值得单列：tryStart 串行化让 abort 晚一个微任务发生，两个既有测试的隐式时序假设当场失效——给并发原语加互斥，时序契约就跟着变，影响范围要 grep 全部调用方和测试【经验】。

这批新发现给出本节真正的结论。逐点修补没有**收敛判据**——修完一批，对抗审查再挖一批，没有办法回答"修到什么程度算完"。回答这个问题需要一份完整的承诺清单：系统对外维持哪些保证，每条归谁所有，破坏它的路径有哪些。有了清单，"修完"才有定义：清单上每条都有 owner、有测试、有证据。清单长什么样，第一章已经立好——接下来把这次事故逐格对上去。

## 3.6 对账矩阵，并把判据倒着跑一遍

先做前向对账：事故里缺的每一样东西，都应当能在第一章 1.2 那六份契约名下找到位置，并说清四问里哪一问最先失守。

![](figures/embed/tb-03-2.png)

第一章 1.2 收尾那句压缩语——**每个状态有归宿，每个故障有路径，每个中断可恢复或诚实终结**——在这里有了完整的反面教材：M5 在五个载体间漂流，没有一处算数；R1 从 running 到消失，没有一行记录解释它；被打断的一轮悬在"既没完成也没终结"的暗区，无声蒸发。三条全违。

对账表还有一个值得当成发现来读的形态：六行里四行最先失守于"看得见吗"。这套系统的结构底色是证据极度稀薄——绝大多数缺口在被追问"管得住吗"之前，先倒在"根本看不见"上；只有交互契约（扰动把投影推离真相）和权限契约（容器去向无干预点）先失守在别的问上。副作用契约那一行也没有落在它第一章的主场格"管得住吗"，因为本次事故里副作用本身落了盘，坏的是它与对话的归属线——这是可观测缺口，够不上对账硬门缺口，故标擦边。

![](figures/t2-matrix-3.6-gap-grid.png)

*图 3.6 · 同一张矩阵的第二次使用：六个缺口格格有名字，四个先倒在"看得见吗"上*

前向对账通过：六个缺口，格格有名字，没有漏网的。但这只证明矩阵够用来**命名**，还没证明它够用来**预防**。所以做反向实验：时间拨回事发之前，判据挨个上。

反向实验有一个必须先交代的方法论陷阱：根因已经被诊断出来了，回头去找哪一问能圈住它，是一场开卷考试，天然带后见之明。这里的诚实边界是：用来审的判据全是与本事故无关的通用问句——第一章的六问、第二章的 catch 三问与六要素表——要判的只有一件事：一个事前逐格问过来、还没见过这次事故的评审员，会不会在这一格停下。下面三格都按这条更严的口径审。

缺口二，六问的第一问就能抓住。第一章五分钟动作的第一问是"哪份状态算数？"对运行中的会话问这一问，答案是"没有哪份"——标红。第二章练习的第 2 题（把"用户可以继续上次会话"改写成契约）是同一个缺口的另一面：guard 一栏要求"上次"精确指到哪个 step，这套系统填不出来。判据抓得住，而且两条判据从不同方向指向同一格。

缺口三，catch 三问全崩。第二章 2.2 要求对代码里每一条 catch、fallback、默认分支都跑三问；逐条跑下来，`isCurrentRun` 判假后跳过持久化那一支会当场崩掉：这条路径的终点状态叫什么名字？——没有名字，数据无声蒸发。谁会知道系统走到了这里？——没人，没有事件。走到这里之后，承诺还成立吗？——"消息不消失"从此不成立。三问一问都答不出，按第二章的规矩，这条分支在事发前就该进 Assumption Register。

缺口一，按事前口径判据抓不住，差的不是问句而是一条用法。六问第五问是"谁批的权限、现在还有效吗？"常规读法只对模型、工具和 subagent 问这一问。把运行时容器本身——webview、进程、壳——也列为权限主体，再问"这个容器能去哪"，导航防线的缺席一问便知。缺的用法就是这一条：权限对象清单必须包含容器层。这不算矩阵漏格，算用法修正，记入第十一章的权限对象清单。

判据圈不到的，也要如实记账。threadKey 回归和毫秒时间戳碰撞，哪条契约判据都不会提前指到它们。这里得先立一条独立于"矩阵抓没抓到"的判准，否则下面的记分就成了同义反复：结构缺口，指契约的 owner、转移或边界在设计层就缺一块，与用什么代码实现无关地存在；实现级 bug，指契约齐备，只在某段代码的某个时序窗口里被违反。这两条按此判准落在后者——契约都在，坏在具体时序。抓住它们的是另一套东西：7 维复审、逐条对抗验证、"修复自身也要过复审"的纪律——第二章 2.6 那门测量学的近亲。所以反向实验的判定是：三个结构性根因，2/3 被事前判据原样圈出；导航逃逸那个圈不到，得先补上"权限对象清单包含容器层"这条用法，而用法是看过根因之后才补的，不计命中，修正入第十一章。两个实现级回归，0/2，落在矩阵之外，归测量纪律管。矩阵是设计期的网，纪律是改动期的网，两张网叠着用，缺哪张都有一类事故漏过去。两张网说的还是老两样：设计期那张就是这张矩阵，改动期那张就是第二章的测量学，按时间先后各管一段——第三套分类法并不存在。

这一节手里多了两样东西：一张被真实事故填过的契约缺口图，和坐标系的第一份能力边界说明——它圈结构缺口，不圈实现 bug。第十五章的评审流程直接建在这两样上。

## 3.7 从一次事故到一类现象

一家小团队的一次事故，凭什么代表一类现象？单个事故可以归咎于工期、疏忽或运气，一类现象不能。

证据第一章 1.0 已经摆过：同一批模型只换 harness，复合分差 23.8；1642 条故障轨迹里三大类故障全落在系统层。这里只补一个对账动作——把 MAST 的三类占比按在本次事故上，逐类都对得上号：规范缺陷（"消息不消失"这条承诺没人 own）、协调失败（抢占与持久化两个机制互不知情）、验证缺失（抢占有测试，其对持久化的副作用无测试）【评审，arXiv:2503.13657】。一次桌面应用的事故，三类故障全部命中。

同款缺陷也不难在别处找到。配套实现项目早期的会话记录里留着同一句诊断：streaming 中途 abort 抛出 AbortError，异常直接冒出 for-await 循环，当前 step 的文本永远不会进入待持久化列表——落库的只有前几步，用户正在看的那一段恰好是丢的那一段【经验】。两个代码库同一位作者，算不上独立复现，只作同款缺陷再现的弱主张；但它印证的规律成立："过程态何时落盘"这个问题只要没被显式回答，答案就默认是"最后一刻"。

## 3.8 改进不可叠加：逐点修补的定量失效

3.5 的复审新发现展示了逐点修补挖不到底；这一节给它配上测量。数字来自 AHE——一套让 agent 自动演化自己 coding harness 的系统，每代改动都跑消融量贡献，因此攒下了罕见的"改动与效果"配对数据【预印，arXiv:2604.25850】。第二章 2.9 在认知层引过它的结论，这里是工程主场。

第一组数字：三个正收益组件单独测量共 +11.1pp，组合后只剩 +7.3pp。论文给了机理——三个组件都把行为推向同类闭包式验证，叠加只是重复检查。改进互相抵消。

第二组更值得警惕，关于预测能力的不对称：agent 预测"这个改动会修好什么"的精度 33.7%、召回 51.4%；预测"会弄坏什么"的精度 11.8%、召回 11.1%。说清一个改动为什么有帮助，勉强及格；预判它即将破坏什么，接近瞎猜。桌面案例的复审就是这条统计的现场版：韧性建设自己引入 threadKey 回归，串行化 tryStart 让两个既有测试的时序假设当场失效——没人预测到，全靠对抗复审兜住【经验】。

两组数字合起来，就是 3.5 收敛判据的定量理由。局部改进不可线性外推，破坏面无法事前预测，那么可靠性只剩一条路径：显式声明每条承诺，给每条承诺配上独立于改动过程的验证。六契约在第一章是反推出来的设计；到这里，它同时是测量数据指回来的结论。

## 3.9 业界对照：如果这套系统跑在 Temporal 上

坐标系搭好了，拿它做一次选型推演收尾。第一章 1.4 对照过 Temporal 的格子厚薄，这里换个用途：把十帧表铺在它面前，逐帧问"这一帧会被记录吗"【厂商实践，依据官方文档整理】。

先把对方说到最强。若 R1 是一个 Temporal workflow：M5 作为 workflow input 在 workflow 启动（帧 2）时即持久化，从此丢不掉；帧 7 的抢占必须走显式 cancel/signal，进 event history；帧 8 的"跳过落库"分支决策可以重放审计。缺口二、缺口三在它的模型里根本不成立——转移契约和真相契约那两列，它填得比多数自研 runtime 都厚。

失效点同样清楚。帧 4 到帧 6 全程发生在它的边界之外：webview 被带走、UI 读到过期投影、用户据此误判重问——交互契约的格子，workflow 引擎不填；帧 4 的导航权限更不在它的词汇表里。此外，给单机桌面应用背一套 workflow 集群，部署成本对产品形态不成比例。结论落回矩阵：名字最响的方案也只填自己那几列，选型的正确姿势是先画满自己的矩阵，再看候选方案盖住哪些格——盖不住的格子，引入之后照样得自己建。

## 破坏实验：四处强杀

每章一次主动破坏，本章的对象是"消息不丢"这条承诺本身。按全卷四步测量协议执行：

1. **破坏动作**：同一套系统，四个时点分别 kill -9——模型调用前（用户消息已被接受、run 未开始）、流式中（回复已生成一半）、落库前（run 已完成、收尾持久化未执行）、工具执行后（副作用已发生、记录未落盘）。
2. **观测点**：重启后消息表的内容与终态标记；事件流里有无中断记录；工具改动（file_snapshots）的归属；UI 最终呈现。
3. **判定**：每一杀之后，重启读库必须能回答四个问题——用户消息还在吗？这一轮以什么终态呈现？半写状态可识别吗？外部改动记在谁的账上？四问各有已定义答案为通过；任何一问的答案是"不知道"，该杀判失败。
4. **复跑**：每个时点 N=3，判定结论不漂移。

实证状态照实分层【经验】：修复前的失败形态，摸底与复审逐环对抗验证过缺口二、缺口三的路径（读完整代码上下文，必要时写探针测试复现）；修复后，验收清单实测过其中两条——任务运行中退出应用，重启可见"[已中断]"标记；Stop 之后"[已停止]"落库，刷新重进可见。四个时点的完整矩阵尚未自动化，是第十四章故障注入的工单；在读者自己的系统上，四杀是作业。四杀各自命中一类契约：一杀真相，二杀交互与真相，三杀转移，四杀副作用与证据。答不上来的那几杀，就是自己系统的契约缺口图初稿。

## L 级自检

按第一章的成熟度尺（L1 能跑、L2 能看、L3 能评，全表见第一章 1.3）给本章的对象打分。事故时点的桌面案例：SSE 断开保护有名字、有注释、随分支合并进主链路，是 L1；帧 4、帧 7、帧 8 在 trajectory 里零事件，L2 缺——第一章 1.3 的假落地公式（有名字、没事件、嫌疑高）在这套系统上再次命中，半途设计正是假落地的桌面版。修复后：增量持久化让"运行中状态"任何时刻可查，真相契约升到 L2；转移契约部分升级——增量持久化落下了 pending 与终态记录，但抢占决策本身（谁抢占、凭什么）仍无事件，只算 L2 半格；那条端到端集成测试（真实 RunManager 加真实 SQLite 贯穿验证"旧轮先终态化，新 run 才拿到手"）给的是接近 L3 的验证信号，属另一把尺，不顶 L2 的事件账。缺失证据清单五条就是剩下的工单，第十三章主场。诚实记账：这套系统离 L3（能评）还差一个 verifier 层，本卷第十三章之前不冒充。

## 立即可做的一个动作（五分钟）

builder 版本：打开自己的项目，grep 落库函数的全部调用点（persist、save、insert，名字不重要），然后回答一个问题：run 进行中，数据库里有什么？答案若是"run 开始前的状态"，3.4 那张表里的每一帧都在这套系统里等着发生——差的只是一个点链接的用户。

assessor 版本：向被评团队要最近一次事故的 postmortem，把每个根因往 3.6 的对账表里归格。三种结果各有含义：格格有主，坐标系和团队的认知对上了；有根因归不进任何格，先分辨它是结构缺口还是实现 bug——前者要质疑矩阵，后者该去查团队的复审纪律；拿不出 postmortem 的团队，证据契约那一格已经有了答案。
