# 一、参考架构与统一语言

> 配图 4 张待补（组件图 / 两条时序图 / 实体关系图），占位以文字图代。附录两表标注核对状态。

入门卷把一个 harness 拆成了部件：agent loop、model adapter、tool registry、context 与 memory、trajectory、verifier，外加 safety 控制面。每个部件是什么、为什么存在、在一次 turn 里怎么咬合，那一卷讲完了。它的定位是一张蓝图——读完之后，部件的名称和职责一目了然。

入门卷发布之后，收到最多的反馈是同一件事。读者照着蓝图搭出了自己的 agent，多数是让 AI 动手写，自己对着图纸检查。搭完一看，该有的都有：loop 在转，工具挂上了，压缩、验证一样不少。可一跑起来就不对劲。同一个任务，昨天还顺顺当当，今天就卡在半路。出了错，日志翻半天，不知道该怪哪一层。好不容易修好这处，过两天别的地方又塌了。

更具体的怪事也有一批：agent 声称做完了，其实没做；同一个工具悄悄跑了两遍，账单和副作用都翻倍；界面卡在"生成中"，后台其实早就死了。这些事没有一件是"缺部件"——部件都在，是部件没把自己的活干到底。更麻烦的是，干没干到底，从外面看不出来。

所以蓝图之外，还缺另一类知识：怎么发现问题出在哪个机制；怎么判断一个机制是真的在工作，还是只是存在；怎么用工程手段保证它在崩溃、并发、截断这些边角情况下仍然有效。蓝图标出墙的位置，这类知识决定墙里的钢筋怎么绑。这就是第二卷。

第二卷讲运行时：系统在一次运行中究竟发生什么。做法是把部件之间那些从来没写下来的约定一条条写成明文——状态归谁、转移凭什么发生、工具做过的事拿什么对账、中断之后谁负责收场——再用故障证明它们真的成立。全卷贯穿一个可运行的单机 runtime，每章把它主动破坏一次：强杀、断连、并发抢占。要运行几个月才暴露的备份、发布、安全、成本，留给第三卷。

读完本卷，能做到四件事：任何一条消息，说得清它此刻在哪个载体里、哪份算数；进程在任意一行被杀，说得清重启后系统怎么收敛；agent 声称"做完了"，拿得出独立于这句话的证据；拿到任何一个 agent 系统，能按同一套问题清单审出它的缺口。

这些症状还有一个共同点：换更强的模型，好一阵，然后照旧。症状与部件品质关系不大，有测量为证——Harness-Bench 把 8 个模型后端接进 6 个 harness，跑同一组 106 个沙箱任务：模型不动，只换 harness，最好与最差差 23.8 个百分点（NanoBot 76.2 对 OpenClaw 52.4）【预印，arXiv:2605.27922】。同一份测量还有一条对选型的提示：越强的模型，跨 harness 方差越小——前沿模型能在烂 runtime 里自我补救，弱一档的模型没这个本事。由此可推（推断，非论文原文）：runtime 质量对中小模型与私有化部署的价值最高。那 23.8 个百分点落在部件之外的什么地方，是本章要回答的问题。

## 1.1 和在线服务差出三个变量

把 agent runtime 当成普通在线服务来搭，是多数怪事的共同起点。在线服务二十年攒下的可靠性工程——框架、重试中间件、发布流程、SRE 手册——押在三个默认值上：进程可弃、重试无害、行为可复现。这三个默认值不写在任何文档里，它们以出厂设置的形式活在每一层基础设施中。agent 一来，三个默认值逐个失效，而失效是无声的。

进程可弃的默认，活在发布流程里。滚动发布随手杀进程，因为在途请求毫秒级结完，杀掉的损失一次重试就补回来；业务进程无状态，真相全在数据库，挂了拉起来就是——重启是运维的万能药。agent 把两个前提同时抽掉：一次运行分钟到小时级，横跨部署、重启、断连，照旧随手发布，等于每次发布都拿用户跑到一半的任务献祭；loop 又恰恰满身状态——半轮输出、工具结果、下一步计划全在内存里攒着，重启大法照吃不误的结果，是库里只剩开头几步，用户半小时的推进凭空蒸发。**执行跨越故障边界**，"进程活着"从隐含前提变成撑不满全程的运气。传统计算机科学处理过长活任务——长事务、工作流引擎、durable execution 是一整个领域——但那从来没进过 web 框架的默认件，得自己去请。

重试无害的默认，活在超时逻辑里。超时了就重发，反正 GET 幂等、去重键兜底，重试次数是个随手填三的配置项。agent 的每一步都可能改文件、发消息、花钱——超时重试一个"发邮件"工具，客户收到两封。**副作用泄向外部世界**，幂等从基础设施的赠品变成每一步的显式义务，而没人通知过重试逻辑这件事。

行为可复现的默认，活在整套验证手段里。出了 bug 复现一遍，改了代码回归一遍，怀疑哪里不对 diff 一遍——全部以"同一输入给同一输出"为前提。模型偏偏在这里例外：同一份输入，两次输出可以不同。**核心组件的输出不确定**，回归测试不能穷举，重放不能逐字节比对，"预期行为"从一个值变成一个分布。软件工程几乎全部验证手段都建立在确定性上，这个地基在这里空了。

麻烦不止三个变量各自，更在相乘：执行足够长，崩溃就会落在任意一步；每一步都有副作用，重试就可能重复任意动作；输出不确定，事后就无法靠重放判定当时发生了什么。三个变量具体会破坏什么，得逐个说清。

## 1.2 威胁清单与六条不变量

三个变量各自划开一类口子。

跨故障执行的口子是**状态撕裂**：执行的中间成果住在内存，真相住在磁盘，两者随时分家；进程死在分家的瞬间，分家就永久化。开头的"卡在生成中""界面早死"都是撕裂的现场照。

副作用外泄的口子是**账对不上**：工具返回成功不等于外部世界成功；重试造出第二笔副作用；agent 声称做完不等于真做完。"工具悄悄跑两遍""说做完了其实没做"住在这一类。

输出不确定的口子是**无从归因**：传统排障的两板斧——重放复现、对照预期——双双失效，重放不出同一条轨迹，预期本身是个分布。"日志翻半天不知道怪哪一层"是这类威胁的日常形态。

三类口子在真实系统里的占比，MAST 给过测量：标注 1600 余条多 agent 故障轨迹（标注者一致性 Kappa 0.88），规范缺陷 41.77%、协调失败 36.94%、验证缺失 21.30%——三类全落在系统设计层；不换模型，只加语义验证可换回 +15.6pp，只改角色规范 +9.4pp【评审，arXiv:2503.13657，NeurIPS 2025 D&B；截至 2026-07 检索为本领域唯一评审级工作，核对记录 `../research/volume2/02-academic-verification.md`】。威胁是系统层的，解药也在系统层。

挡这三类口子，靠在出事的地方打补丁行不通——补丁治的是上一次的路径，威胁下次换一条路进来。真正管用的问法是站到救援者的位置上：崩溃已经发生、账已经乱了、轨迹已经无法重放，此刻系统最少要守住什么，事情才有救？逐类问下去，答案一共六条，本卷叫**运行时不变量**。

对着状态撕裂问。进程死在半路无法根绝，那重启后的救援凭什么展开？第一凭知道以谁为准——每个持久状态有 owner、ID、版本和合法读写路径，"哪份算数"从不含糊，这条叫**状态可归属**。第二凭知道修到哪算修完——失败、中断和恢复最终进入已定义状态，不能恢复时明确终结，这条叫**失败可收敛**。两条缺一，恢复就成了悬案：要么不知道信哪份，要么永远修不完。

对着账对不上问。事后对账的前提，是当时记过账。意图、尝试、结果、真实 outcome，四样少记一样，对账就多一个盲区——而"工具返回成功"顶多算工具的一面之词，少了 outcome 那一样，盲区恰好盖住最贵的一类事故。四样记全，这条叫**副作用可对账**。

对着无从归因问。重放这条路死了，剩下的路只有两条。一条是原因当场记：每次状态变化带上触发事件、前置条件和终结原因，不指望事后推，这条叫**转移可解释**。另一条是信任换成证据：完成、失败和安全声明都能指向运行证据，组件的话不可全信，这条叫**结论有证据**。

第六条来自变量的组合：输出不确定的组件在长时执行中持有权力。不确定意味着权限不能靠 prompt 维持——模型可能被输入操纵，也可能单纯犯错，边界不能靠自觉；长时执行意味着授权要跨越崩溃、恢复与 fork——批过的事过了多久、换了上下文还算不算数，成了绕不开的问题。**权力有边界且有期限**：恢复状态不等于恢复旧授权（§十）。

六条压成一句话：**每个状态有归宿，每个故障有路径，每个中断可恢复或诚实终结。**性质立住了，还悬在半空——不变量自己不会成立，得有零件对它负责。

## 1.3 职责分配长出组件图

从不变量到零件，走的是职责分配：一条一条问，谁来保它。每一次分配都先看清不设防时的死法——这一章的组件没有一个是发明出来的，全是被死法逼出来的。

先看没人设计时，状态自己会长成什么样。loop 在内存数组里攒消息，攒够一轮写库；前端为了显示快，自己留一份会话状态；工具把结果顺手写进文件。三份记录平时相安无事——直到进程在写库前被杀。重启之后，内存那份没了，前端那份还显示"生成中"，文件那份没人说得清归属哪条消息。这不是丢数据的问题，是"该信哪份"从来没人回答过：写的时候人人能写，读的时候份份都像真的。开头那件怪事——退回来对话记录全没了——就是这么来的：用户看见的那份，从来不是算数的那份。

所以第一刀切在写权上：真相只放一处，允许写它的组件只有一个。这个唯一算数的地方，就是**状态层**。数据工程里这条纪律叫单源真相（SSOT），即每个数据元素只在一处被 mastered，其余位置只许只读引用或带调和机制的副本【规范/官方文档，Wikipedia: Single source of truth】——不是新发明，是 agent 系统把老坑重新踩了一遍才想起来。单机参考实现选 SQLite（WAL 模式）单写者，看中的正是它的不宽容：单写者天然串行，写冲突、共识、分布式事务这一整类问题直接不存在。代价也直说：吞吐有上限，将来多实例要迁 Postgres 加 lease。这笔交换划算——原型期死于状态撕裂的系统，远多于死于吞吐不足的；真到要迁的那天，1.6 给切换信号。

真相集中了，历史还没着落。天真的做法是状态行就地 UPDATE：run 从 running 改成 failed，一改了之。排障的人半夜对着库问"它怎么变成 failed 的"，库里只有现在的样子，没有来路；文本日志倒是有，但那是给人读的散文，格式随手、字段残缺，恢复扫描没法拿它当依据。死因在于：解释和证据一旦允许事后修订——或者压根没记——就都不可信。所以第二刀是**只追加**：历史永不改写，记错了追加更正，指向原处。载体两件：**事件流**，发生过什么的机器可读记录，供恢复扫描、UI 订阅、审计回放；**证据存储**，trajectory、policy 决策、verifier 结论、artifact lineage 的归档处。状态层回答"现在是什么"，这两件回答"凭什么相信"。根基不新：数据库的 WAL、金融的复式账簿，同一条纪律——历史可信，靠的是改不了。代价是存储上涨、内容涉隐私（采集策略交第三卷）；哪天成本真扛不住，事件可以稀疏，不可以改写。

副作用的死法要慢放才看得清。天真的执行顺序：模型说调工具，executor 直接调，返回后把结果写库、塞回上下文——账也记了，只是记在动作之后。账与动作之间于是有一条缝：崩溃恰好落在"邮件已发出、记录未写下"的瞬间，系统苏醒后完全不知道自己发过邮件，它能做的最"负责任"的事，恰恰是再发一遍。"工具悄悄跑两遍"多半是这条缝的产物。缝堵不上，除非把顺序定死：先落盘意图，再执行，再落盘结果。外部动作一律走这道门，门叫 **tool executor**（§七是它的主场）。门上还有一条附则：工具返回成功，只证明工具说了成功；外部世界是否真的变了，要另一份证据（§7.10）。

模型调用的死法藏在恢复路径上。恢复一个跑到一半的 run，直觉做法是把没跑完的部分重跑一遍——对确定性代码这行得通，重跑得到同样的结果。模型不给这个保证：同一份输入，两次输出可以不同，重跑出来的"下半场"接不上用户已经看过的上半场，恢复反而制造出第二个版本的历史。出路只有一条：把每次调用当成一次性事件，完整留档——模型标识与版本、参数、上下文投影摘要、输出、token 计量——恢复时复用记录，永不重跑。这份档案的管理者是 **model adapter**，一次调用的全部边界（参数、重试、流式、计量）都收在它手里。

循环本身也要个主人：组 context、调模型、派工具、判终止——**agent loop**。它的死法 1.2 已经讲过，就是状态撕裂的标准现场：内存里攒着半轮成果，进程一死全部蒸发。所以它领到的约束全卷最硬：在内存里攒的一切，要么立刻落盘，要么等于不存在。

还剩两条不变量没人认领：失败可收敛，权力有边界。它们的死法长在同一个地方。天真的系统里，每个入口各自为政：UI 直接调 loop，API 也调，scheduler 也调，各自实现自己的取消、自己的权限检查。用不了多久，同一个"取消"长出三种语义——UI 的取消只断了流，run 还在后台跑；API 的取消杀了 run，没记原因；双击"发送"，两个 run 同时写一个会话。至于崩溃后满地的孤儿 run，没人认领，因为"谁负责扫尾"从来没被指定过，每个入口都以为是别人的事。病根一句话：同一种语义实现了 N 份，就会漂移成 N 种。解法是收口：所有执行，无论从哪个入口来，过同一道闸——准入、互斥、policy、limit 在这里判，孤儿 run 的发现和送终也归这里。这道闸叫 **run manager**，这个决策叫**单执行内核**：permission、cancel、resume、工具执行四种语义只在内核实现一次，入口只剩两件事——适配意图、转发流。代价直说：每接一个新入口都要多写一层适配，原型期显得绕，直接调内部函数快得多——快出来的每一分钟，将来都要用"两种取消语义对不上"的排障加倍偿还。推翻这个决策需要一种必须绕过内核才成立的入口需求，目前没见过站得住的例子；真出现时，解法也是在内核里分策略，轮不到入口自建执行路径。

最后是**入口层**：UI、API、IM 渠道、scheduler，把外界动作变成一次合法提交。它的死法开场就见过：前端为了体验流畅，自己留一份状态，超时了自己把任务标成失败。猜错的那天，库里 run 还活着，用户照着"失败"重发一遍，两个 run 并行写一个会话；或者反过来，后台早死了没人通知前端，界面永远"生成中"。病根是显示层拿到了定义真相的权力。所以入口层的约束只有一条：界面上显示的一切都是**投影**，即持久状态在别处的只读呈现——可丢弃、可重建、可过期，真相不能。**投影不回写**，UI 的一切聪明猜测活不过一次刷新。代价是乐观更新受限，用户感知比"前端先改再同步"慢半拍；这个决策不靠辩论检验，靠章末的破坏实验——哪天实验通不过，是实现坏了，回来修实现。

图上还有一层分工要说破：循环只画了一个，多 agent、并行、分支放在哪？控制流有两层。单个节点内部，是入门卷讲过的观察、决策、行动循环，主人是 agent loop；跨节点的依赖、并行、分支、join、重试和中间变量，归 **workflow graph** 调度层持有——参考实现把它做成 run manager 的下半层（§十三先实现节点内 loop，再加一个含 branch/join 的最小 graph）。允许模型动态生成子图，但生成物先过校验、预算和权限门禁才准执行。名字也拆开：这里的 graph 节点是任务和 agent；§七的 planner 还会遇到 **world-state graph**，节点是对世界状态的表示，边是动作及其预测转移，是搜索对象而非编排骨架。两种图不同层，可以嵌套。

## 1.4 两条时序上的验证

架构图是静态的，判断它对错要看动线。第一条时序：用户发一条消息，任务顺利完成。**加粗处是落盘点**——数一数有几个、都在谁手里，这张架构的正确性一半押在这上面。

（配图占位：正常路径时序图 + 崩溃恢复时序图）

1. 入口收到消息，提交 run manager；
2. run manager 准入：同会话互斥、policy、limit 检查；**落盘：`runs` 新行（created）+ `events: run.created`**；
3. **落盘：用户消息进 `messages`（pending 态）**——从这一刻起消息归系统管，之后任何崩溃都丢不掉它；
4. agent loop 组装 context：从状态层读消息、摘要、记忆，生成给模型的投影（不落盘——投影可重建）；
5. model adapter 调模型；**落盘：`invocations` 行（模型标识、参数、上下文摘要）**；流式输出**按事件节流 upsert 进 `messages`**，同时经事件流推给 UI；
6. 模型要求调工具：tool executor **先落盘 effect 意图（含幂等 key）**，再执行，**再落盘结果 + `events`**；
7. 循环 4-6，直到模型给出终答；
8. run 收尾：**落盘：`messages` 终态更新、`runs` 置 succeeded、`events: run.finalized`**；
9. 事件流推送完成通知；UI 不在线也无妨——下次读库，看到的就是全部。

第二条时序：kill -9 落在第 5 步流式进行中。这是本卷反复回放的镜头：

1. 进程重启，启动扫描发现 `runs` 表里 status=running 的孤儿；
2. 查 `steps` 表定位最后一个完成的 step——恢复粒度锚在这里（§六）；
3. 已完成的 invocation 直接复用记录的结果，不重新调用模型；
4. 流式半截的内容已在 `messages`（pending 态），按 §八 的语义标注中断，用户看得见"断在哪"；
5. 有意图无结果的 effect 进对账流程（§七）：查询、重试、补偿或诚实标 unknown；
6. run 收敛到明确终态，收敛动作本身进 `events`；
7. UI 重连，读到的是最新已知状态——没有僵尸"生成中"，没有凭空消失的轮次。

两条时序合起来给出一个全卷通用的判断标准：**任何机制设计完，都要能在这两条时序上标出自己的位置——正常路径的哪一步写了什么，恢复路径的哪一步被谁读到。**标不出位置的机制，多半就是读者反馈的那种"存在但没干活"的部件。

## 1.5 统一语言：六级实体链

一个真实的争论场景。"进程重启之后 resume，用户的消息还在吗？"工程师 A 说在——他指会话的消息历史，落了库，当然在。工程师 B 说不一定——他指被杀那次执行的半轮输出，没落库，当然不在。两个人都对，因为"会话"这个词在两张嘴里指着两个对象。用错词，就会修错层。

恢复时序第 2 步写着"定位最后一个完成的 step"——这句话的正确性押在 step 这个词只有一种解读上。词汇从这里冻结：六级实体，每级有定义、owner 和生命周期终点。

| 实体 | 一句定义 | 关键裁决 |
|---|---|---|
| Conversation | 用户视角的会话容器，跨 run 存续；持有消息历史、artifact 引用、compaction 摘要 | 删除会话、删除运行记录、撤销外部动作是三件不同的事（§5.10） |
| Run | 一次触发到终结状态的执行单元，全卷最重要的状态机对象（§四）；`triggered_by` 至少区分 user / scheduler / webhook / parent_agent | 可以没有 conversation（定时任务挂系统会话或置空，二选一但显式选）；subagent 是 child run，经 `parent_run_id` 关联（§十一） |
| Turn | run 内的一次循环：模型看最新上下文 → 产出文本或工具请求 → 结果回填 | 消息归属与"半轮内容落不落盘"（§8.7）以它为单位；无独立表 |
| Step | turn 内的原子工作单位，形态是一次 Invocation 或一次 Tool Execution | 三件事的锚点：恢复粒度、幂等 key 派生源、correlation 链末级 |
| Invocation | 一次模型调用的完整记录：模型标识与版本、参数、上下文投影摘要、输出、token 计量 | 是实体，不是日志——恢复时复用的就是它（1.3） |
| Tool Execution | 一次工具执行，intent → attempt → result → outcome 四段（§七主场） | 在状态层的本体是 Effect Ledger 的行 |

三个容易挂错的对象：HITL 等待不设新实体——它是 run 的一个状态（waiting，§四）加一条待办审批记录；compaction 摘要是状态层对象，携带 provenance（§九）；timer 落库持久，进程内定时器只是它的执行代理，进程死了它还在（§6.7）。

物理形态是十一张表——`conversations` / `runs` / `messages` / `steps` / `invocations` / `effects` / `checkpoints` / `artifacts` / `approvals` / `timers` / `events`。"每个状态有归宿"落到操作层面，就是任何机制的任何中间状态都能回答"你在哪张表的哪一行"；答不出的，要么是投影（可丢弃），要么是缺口（本卷要修的东西）。每张表的 owner、字段、删除语义、崩溃后归宿，登记在 [`90-artifacts.md`](./90-artifacts.md) 的 State Registry——本章的正式交付物，§五升 v2。

实体之上还有四条全局规则。**ID**：每个实体全局唯一，带类型前缀（`conv_` / `run_` / `eff_` …），前缀让一条裸日志里的 ID 自我说明类型；生成用时间有序的随机 ID（ULID 一类），但顺序的真相是状态层的单调序号（数据库自增 seq）——钟会回拨，进程会并发，别信 ID 里的时间戳。幂等 key 同理从持久化记录派生（`run_id` + step 序号），不用内存计数器【规范/官方文档，morling.dev: On Idempotency Keys】。**owner**：每个持久状态对象有且只有一个允许写它的组件；"两个组件都能写这张表"不叫灵活，叫缺陷——并发、版本、删除三种语义要在两处同时维护，漂移只需要一处忘记。评审动作：对 State Registry 逐行问"还有谁在写它"。**correlation**：每条事件冗余携带完整从属链（tenant → conversation → run → turn → step），每张状态表带父级外键；冗余是刻意的，事件是排障时第一个被单独拿出来看的东西，自包含比让人做五次 join 便宜。**version**：每条记录带 `schema_version`，run 带 `state_machine_version`（状态机改版后旧 run 按哪套语义收敛，要可判定，§4.10），invocation 带模型与 prompt 资产的版本引用；版本治理在第三卷，本卷只保证每份状态自带"我按哪版规则写的"。

## 1.6 治理视图与部署形态

组件图回答"有什么、怎么连"；出事之后的第一问却是另一种——这份状态怎么会在你手里。回答它要按持有权重新分组：谁被允许持有什么。八个组件归入五个平面：

| 平面 | 组件 | 职责 | 绝不持有 |
|---|---|---|---|
| Interaction | 入口层 | 把外界动作变成合法提交 | 真相——一切显示皆投影 |
| Control | run manager | 准入、互斥、policy、approval、limit | 未留痕的决策——批准与拒绝一律进证据面 |
| Execution | agent loop、model adapter、tool executor、沙箱 | 唯一"做事"的平面 | 任何持久状态——成果即刻落盘，否则等于不存在 |
| State | 状态层 | 唯一 mastered 位置 | 对外部世界的保证——库里写着"成功"不等于外部真成功 |
| Evidence | 事件流、证据存储 | 发生过什么、凭什么相信 | 可变行——append-only，改错靠追加更正 |

平面间的箭头，禁止的比允许的重要。四条禁令，每条背后是一类真实事故：**Interaction 不许写 State**——UI 反向定义真相，崩溃恢复从此没有基准，刷新之后信谁？本章破坏实验就验证这条。**Execution 不许直连 Interaction**——工具或 loop 绕过事件流直推 UI，通道里的数据没有序号、没有留痕，断线重连的语义无从谈起（§八）。**Control 的决策不许不落 Evidence**——审批与拒绝无痕，权限契约只剩口头约定（§十）。**State 不许依赖任何平面**——存储层回调业务，恢复时序出现"恢复数据库需要业务运行、业务运行需要数据库"的死锁。sandbox/permission 横跨两个平面，拆法明确：决策（允不允许）在 Control，强制（拦不拦得住）在 Execution 的边界上——§十会把这个拆分长成硬软之辨的骨架。

平面边界上有三处标准干预点，名字先立住：**assemble**——模型这次看见什么，落在 State→Execution 的投影边界（§九主场）；**model**——这次可选哪些工具与动作，落在 Control→Execution（§十）；**execute**——是否授权并真正执行，落在 Control→Execution 与外部世界之间（§七、§十）。三处各自留证：只在一处留痕，等于宣布另外两处的干预不存在。

以上全部是逻辑架构，不规定部署形态。原则一条：**先做单机最低充分解，不预支分布式复杂度。**单机形态就是 1.3 那张图的直译：SQLite、进程内 run manager 单例、进程内任务、进程内广播加 SSE、事件表加启动扫描（§6.10）。切换信号出现再升级：出现多写者或单文件备份不够用，状态层换 Postgres；多实例部署后两个进程可能 resume 同一个 run，run manager 外挂分布式锁或 lease（§4.8）；run 量超出单进程，执行改 worker queue；消费者跨机，事件流换消息总线；durable execution 何时该换 Temporal 一类引擎，§6.11 给判断条件。契约不因部署形态打折——单机版一样要回答"kill -9 之后谁收敛孤儿 run"。

## 1.7 六类契约总览

六条不变量是对外的承诺，五个平面是内部的持有规则，中间还缺一层组织：承诺怎么逐条兑现、由哪章负责。按"系统欠外界什么"把承诺分成六类契约，每类一章主场：

| 契约 | 核心问题 | 典型对象 | 主场 |
|---|---|---|---|
| 真相契约 | 哪份状态算数，谁拥有它？ | run、message、checkpoint、memory、artifact | §五、§九 |
| 转移契约 | 什么事件能让状态从 A 变成 B？ | lifecycle、并发、retry、resume | §四、§六 |
| 副作用契约 | 声称做了什么，外部世界实际发生了什么？ | tool 的 intent/attempt/result/outcome | §七 |
| 交互契约 | 用户、连接与后台 run 如何保持一致？ | stream、cancel、interrupt、HITL | §八 |
| 权限契约 | 谁以谁的身份、在什么边界内行动？ | principal、delegation、approval、sandbox | §十、§十一 |
| 证据契约 | 凭什么相信状态、动作和完成声明？ | event、trajectory、policy trace、lineage | §十二 |

检查周全性用三个正交维度，不靠章节数量：对象（状态/副作用/权限/证据）× 事件（创建/读取/修改/并发/失败/中断/恢复/删除）× 边界（进程/worker/subagent/网络/数据库/provider/工具/用户）。例如"副作用 × 恢复 × 网络边界"就是恢复时序的第 5 步。这套维度只用来查遗漏，正文不穷举笛卡尔积（§十四给热点交叉表）。

开场怪事里还剩一件没安放："改好一处，别的地方又塌。"它的病根是暗契约——部件之间没写下来的假设，改动踩上谁都不知道。这件事没有单条不变量可认领，解法是把契约整个写成明文，也就是本卷全部内容；§3.8 有它的定量画像。四个承重决策（单写者、只追加、单内核、投影不回写）合起来则是同一个偏好：**把复杂度花在"出事之后还能讲清楚"上。**这个偏好有适用边界——失败代价足够低的系统（一次性脚本、随手重跑的实验）用不上本卷多数契约，那类系统的承诺停在"尽力"档就够（§二的四档语言）。

到这里，本章立住的是"什么不能坏"。可是一个具体的 runtime 摆在面前——也许就是读者照入门卷搭的那个——六条不变量成立还是不成立，拿什么判？承诺要变成判据，判据要能变成检查。这是 §二 要解决的问题。

## 1.8 破坏实验：两次分叉

每章一次主动破坏，本章破坏两条承重规则。

**实验一：真相源分叉**，打的是"Interaction 不许写 State"。做法：在参考实现的 UI 里故意保留一份本地 run 状态副本；启动一个 run，断开事件流，在 UI 本地把状态改成 completed（模拟一个"贴心的"前端根据超时猜状态）；此时数据库里 run 仍是 running。然后做两件事：刷新页面；等 run 真正结束。预期：刷新后 UI 无条件回到数据库投影（显示 running），本地猜测被丢弃；run 真正结束后，UI 经事件流或重拉收敛到真实终态。通过判据：全程数据库从未被 UI 侧写入。失败样态：实现里存在任何一条"UI 状态回写数据库"的路径（比如前端超时后调接口把 run 标成 failed），实验会让它显形。修复方向只有一个：删掉回写路径，"超时该标 failed"交给 Control 的看门狗（§4.8）——UI 的职责是显示真相，判定真相轮不到它。

**实验二：入口语义分叉**，打的是单执行内核。给 SDK 和 UI 各写一套 permission 检查与 cancel 路径（模拟入口自建捷径），对同一会话分别经两个入口执行同一组操作：受限工具调用、中途取消、断开重连。预期：入口一致性 contract test 报出语义分叉——同一 intent 经任何入口进入内核，policy、cancel、resume、evidence 四种语义要完全一致。修复方向同 1.3：捷径删掉，入口只留意图适配与流转发。
