§三 解剖过桌面案例项目的一次"数据丢失"事故：用户点了回答里的链接、整个应用被带走，回来发现少了一轮对话，重问一次之后，第一次的提问与半截回答从此永久消失。那一章把事故压成一张十帧时间线，逐帧追踪消息躺在哪个载体上；十帧里有两帧，至今还是欠条。帧 7，用户重问触发抢占，旧 run 被 abort——这个改写了旧 run 命运的决策，系统里没有任何事件记录它发生过。帧 8，旧 run 收尾时发现自己已不是"当前 run"，跳过持久化——用户的半轮成果就在这条无人知晓的分支里无声蒸发。两次状态转移都真实发生了，都没有任何状态机为它们背书。§四 把这张欠条挂到了具体的卡上：run manager 的卡面写着准入、互斥、抢占三类决策都要有事件，但哪些状态、哪些转移、谁有权触发、终结原因怎么记——蓝图只标了位置。本章交出这张转移表。

深潜从 run 开始，理由 §四 4.5 的动线已经给了：正常九步的第一个落盘点就是 run 记录。run 是 harness 中最重要的状态机——一次执行的其余状态，消息、调用记录、副作用的账，全部挂在 run 之下；run 的状态错了，其余一切失去坐标。本章的主张压成一句：任何 run 在任何时刻都必须处于一个可解释的状态——**"卡在 running"不是状态，是缺陷**。读完本章，手里应当多三样东西：一张七状态定义表、一张可执行的转移表（全表住工作制品 H）、一张入口到内核的 Routing Matrix。

## 5.1 没有状态机的 run 长什么样

先看不设防的系统怎么管 run 的状态，多数系统的起点都是它。`runs` 表加一个 `status` 字符串字段，代码里哪段逻辑需要改状态，就地一句 UPDATE：收尾的地方写 `completed`，catch 里写 `failed`，抢占的地方写点别的——或者什么都不写。开发期一切正常，因为正常路径只有一条，每处 UPDATE 各管各的，井水不犯河水。

失效的样子 §三 已经放过一遍现场：帧 7 的抢占改写了旧 run 的命运，没有事件；帧 8 的收尾分支跳过持久化，没有痕迹；姊妹症状里还有一群 run 永远停在 running——进程早死了，没人回来改这个字段。三种形态背后是同一个失效根因：每一处 UPDATE 都自带一个隐式状态机——它默认"此刻状态是 X，改成 Y 是合法的"——而这些散落各处的默认互不知情，谁也不检查谁。§一 1.4 在语义层见过同款病：同一种语义实现 N 份，就会漂移成 N 种；这里是它的转移层版本——同一台状态机被 N 处代码各自实现，run 的生命周期就漂移成 N 条互相冲突的路径。

设计出场只有两步。第一步，把状态集合显式枚举出来——run 允许处于哪几种状态，一个不多一个不少；第二步，把全部转移收进唯一一张表——什么事件、在什么前提下、能把 run 从哪个状态送到哪个状态。前者是 5.2 的内容，后者是 5.3 的内容。状态机是计算机科学里最老的形式化工具之一，本章做的只是把它落到 run 上，并且按 §一 的坐标系要求它可检验。

## 5.2 七个状态，每个都是被处境逼出来的

状态集合不能拍脑袋定。每个状态存在的理由，是有一类处境必须与其他处境区分开——区分不开，就有一类 run 要么被误杀、要么被谎报。逐个处境问过去，恰好七个。

一个意图通过了准入，但还不能立刻跑——同会话已有 run 在执行，或并发额度满了。这类 run 需要一个"已接受、未执行"的落点，**queued**。没有它，准入裁决无处安放，内核只剩两个坏选项：当场拒绝（用户重试成本转嫁），或当场硬跑（互斥失守）。

正在执行的 run，**running**——唯一消耗模型与工具资源的状态。

run 停下来等一个系统给不出的输入：审批、追问的回答。这类处境要与 running 分开，**waiting**，理由有两条。资源上，等人的 run 不该占模型并发额度；策略上，执行超时的尺子量不得等待——按 running 的超时杀掉一个等审批的 run，等于替用户拒绝了审批。桌面案例的摸底里有这条边界的反面实证：确认挂起没有超时，又叠着全局单 run 锁，一次没人理的确认把整个系统锁死【经验】。waiting 必须携带自己的 deadline，超时有显式归宿。

进程死了——kill -9、断电、崩溃——run 没有做完，也没有人取消它。这类处境需要一个诚实的名字，**interrupted**。没有它，恢复扫描只能在两个谎言里挑一个：标成 failed，用户以为任务本身出了错；留在 running，就是本章开头那句缺陷。§三 修复验收里实测的"[已中断]"标记，就是这个状态的界面呈现。

最后是三个终态，分开的理由是下游行为不同。**completed** 触发交付与通知；**failed** 进入归因与重试判断；**cancelled** 是"不必再跑"的记录——用户意志，或时限策略的收尾；不进失败率统计，不触发重试。三者合并成一个"ended"，下游每个消费者都得自己重新推断这个 run 究竟怎么结束的，推断口径必然漂移。

| 状态 | 回答的处境 | 停留上限与超时归宿 |
|---|---|---|
| queued | 已接受、未执行（互斥或额度） | 排队超时→cancelled（queue_expired） |
| running | 正在消耗执行资源 | 心跳超时→看门狗按基础设施失败收尾（5.8） |
| waiting | 等一个系统给不出的输入 | 自带 deadline，过期是显式终态 |
| interrupted | 进程非自愿消失，任务未完 | 由恢复裁决送往续跑或终态（§七） |
| completed / failed / cancelled | 三种结局，下游行为不同 | 终态即终点 |

（配图占位：七状态转移图——状态为节点、转移为带 event/guard 标签的有向边，三终态互不连边）

状态数的代价也直说：每多一个状态，转移表就多一组要维护的行、恢复扫描多一类裁决——所以过渡性语义能由转移的 guard 承载的，不单列状态，5.12 的业界对照会碰到一个具体例子。

一条铁律压轴：终态之间不许互转。completed 的 run 改成 failed，等于改写历史——§一 1.4 只追加纪律的转移层版本。判错了怎么办，答案与事件流一致：追加更正记录指向原状态，历史本身不动。

## 5.3 转移表：event、guard 与唯一路径

七个状态立住了，接下来管转移。一条转移由四个要素定义：触发**事件**（谁、以什么动作）、**guard**（什么前提必须先成立）、**目标状态**，以及进终态时的 **terminal reason**。全部合法转移收进一张表，每条一行。节选三行看格式，全表十七行住工作制品 H：

| 当前状态 | 触发事件 | guard | 目标状态（终结原因） |
|---|---|---|---|
| queued | 内核派发 | 同会话无活跃 run 且额度足够 | running |
| running | 新意图触发抢占 | 旧 run 半轮内容已终态化落盘 | cancelled（preempted） |
| running / waiting | 启动扫描发现进程不在 | 进程标识已消失 | interrupted |

这张表配一条执行纪律，才配得上"可执行"三个字：代码里改 `run.status` 的路径只许有一条——内核的 transition 函数，查表、验 guard、写状态、落一条 `run.*` 事件（非终态转移落 `run.state_changed`，进终态落 `run.finalized`），payload 携带触发事件、guard 结论、发起者。表外的转移直接拒绝并落 `error.raised`。这是状态层单写者纪律在转移层的重演：状态层管"谁能写这张表"，转移表管"写进去的变化是否合法"。§四 卡面上"三类决策要有事件"的承诺，由这条纪律整体兑付——抢占为什么没有事件？因为帧 7 那套系统里，抢占根本没走任何统一路径，各处 if 分支自成一体，想落事件都不知道落在哪。路径唯一了，事件才有唯一的落点。

这张表读者其实见过近亲。§二 的契约六要素——owner、trigger、guard、action、outcome、evidence——逐格对上：owner 是内核，trigger 与 guard 同名，action 是转移本身，outcome 是目标状态，evidence 是那条随行的 `run.*` 事件。转移表就是转移契约的批量登记形态：一行一条契约，整张表就是这台状态机的合同全文。

## 5.4 终结原因：四类结局分开记账

终结原因单独立一节，因为它最容易被偷懒成一个字段值。"failed 打天下"的失效方式是三方受害：排障者分不清任务错了还是网络断了；重试逻辑分不清该不该重——模型超时值得再试，策略拒绝再试是浪费，反复触发还可能是攻击信号；产品报表把用户取消算进失败率，数据从源头就脏了。根因是四类结局的下游动作不同，却被压进了同一个符号。

所以 terminal reason 至少分四类记：**业务失败**（任务本身没做成）、**基础设施失败**（模型 API、磁盘、网络）、**用户取消**、**策略拒绝**（权限、预算、政策拦截）。四类是分类框架，具体值可以更细，且每个值都要标明归属——preempted 与用户 Stop 同归用户取消（新意图出自用户之手）；queue_expired 与 hitl_expired 是时限耗尽，时限由系统策略定，挂在策略拒绝名下，终态走 cancelled——拦下的是继续等待，与 run 出错分开；unrecoverable 归基础设施失败。全表见工作制品 H，terminal_reason 列逐值挂类。分类的代价是每条终态转移多答一道归类题——这道题事故复盘时终归要答，区别只是事前答还是事后补。§三 对那条被抢占的旧 run（十帧表里的 R1）有一句追问——"R1 从 running 到消失，没有一行记录解释它"——缺的正是这一列。

## 5.5 同会话第二个意图：互斥与抢占

转移表管单个 run 的一生；并发进场，先从最日常的处境开始——同一个会话，第二个意图到了。双击发送、双标签页、scheduler 撞上手动触发、webhook 重投，来源全都不稀奇。

内核收到它，裁决空间恰好四种。**reject**：拒绝并告知原因——拒绝必须对用户可见，静默丢弃意图等于把 §三 的"假丢"搬到入口。**enqueue**：排队等当前 run 结束——队列必须持久化，内存队列刷新即丢，排进去的意图与消息享受同等的落盘待遇。**interrupt**：抢占，新意图更要紧，旧 run 让路——聊天场景的常见默认。**rollback**：把会话回退到某个检查点再接受新意图——重型选项，依赖 §七 的 checkpoint 语义，此处只登记存在。四选一是会话级策略，但裁决点只有一个：内核准入处，裁决本身落事件。

抢占展开说，因为 §三 整场事故的收尾一环正落在这里。缺口三的机制值得复述一句：旧 run 被 abort 后立即失去"当前 run"身份，收尾时 isCurrentRun 判假、跳过持久化——抢占语义单看正确，它对持久化的副作用没人问过。修复后的顺序即转移表里那行 guard：抢占必须先收尾——abort 旧 run，等待其半轮内容终态化落盘，然后新 run 才接手会话。半轮内容的归宿不再是问题：§三 的三档修复里，契约档的增量持久化已经让运行中的每一轮随时在库，抢占要做的只是把 pending 行标上终态。整个动作在表里是一行：running，经"新意图触发抢占"，guard"旧 run 半轮已落盘"，到 cancelled（preempted）——帧 7 与帧 8 两张欠条，在这一行里同时结清。

## 5.6 入口幂等：第二个请求未必是第二个意图

抢占之前还有一道更便宜的闸：这个"第二个意图"，真的是第二个吗？客户端超时重发同一个创建请求——§一 1.1 里那个重试默认值——网络层面天经地义；不设防的内核把每次请求当新意图，一次点击两个 run。

解法是入口幂等：创建请求携带 **idempotency key**，内核按 key 去重，命中时返回已有 run 的引用，接上同一条流。重试是网络的正常行为，答复它的应当是同一个 run。key 的三件细则：作用域绑定会话加客户端提交序列（或客户端生成的 UUID），跨会话不去重；保留期与 run 同寿或取滚动窗口，过期后同 key 视为新意图；冲突应答——同 key 不同 payload——返回显式冲突，这是客户端 bug 的信号，静默吞掉等于替它藏错。key 的派生纪律回指工作制品 B（Effect Ledger，副作用账本）：派生自持久化锚点，内存计数器在并发下会乱序。幂等这道闸把重复的请求挡在门外，5.5 的四种裁决从此只需面对真正的第二个意图。

## 5.7 并发原语：单机一件，多实例三件

互斥的语义定了，还剩实现它的原语。这一节把选择条件说清，深潜章不再回头讲选型。

单机单写者阶段，答案只有一件：进程内串行化。桌面案例的教训给这件事标了价：tryStart 在检查与使用之间留了缝，双标签页的两个抢占同时通过 recheck，后到者静默 abort 先到者——§二 2.7 登记过的 TOCTOU，出身就在这里。修法是把同会话的准入按 sessionId 排进 promise 链，天然串行，缝隙不存在。代价也照实记：串行化让 abort 晚一个微任务发生，两个既有测试的隐式时序假设当场失效【经验】——并发原语的变更是接口变更，涟漪要 grep 全部调用方。

多实例阶段的装备有三件，按代价递增。**乐观并发**：run 行携带 version，更新走 compare-and-swap，冲突者重读重试——适合冲突低频的短临界区。**lock/lease**：带 TTL（存活时限）的租约，持有者心跳续租，适合跨进程的长临界区——"谁是写者"从进程内事实降为协议保证，§四 状态层卡的取舍栏预告过这条迁移线。**fencing token**：租约每次授予携带单调递增的编号，状态层拒绝旧编号的写入。它防的是租约自己防不了的一种失效：进程拿着租约陷入长停顿（GC、换页、网络分区），租约过期、别人接手，它苏醒后仍自以为是持有者，带着旧授权继续写——一个不知道自己已经出局的写者。这个机制的名字出自 Kleppmann 对分布式锁的经典分析【规范/官方文档，DDIA 第 8 章与 2016 年 How to do distributed locking，终稿前回核页码】。三件的适用条件一句话：单机单写者一件都不需要——这正是 §四 部署一页"多实例再谈"的兑现处；迁移信号出现时，顺序是先乐观并发，冲突率撑不住再上租约，fencing 随租约配套，不单独存在。

## 5.8 孤儿 run：谁替消失的进程收场

并发是仍在运行的进程互相争抢；这一节处理已经消失的。kill -9、断电、OOM killer——进程连"我要退出"都来不及说。库里躺着 status=running 的行，进程已经不在，没有任何代码路径会回来改它。这就是孤儿 run，本章开头那句缺陷的最大产地。

处置的根基是一条老哲学，crash-only【评审，Candea & Fox，HotOS IX 2003】：如果系统只有"崩溃"一种停止方式、"恢复"一种启动方式，这条唯一的路径会被每一次启动反复锤炼；优雅关闭与崩溃恢复两条路并存时，后者极少被真正测试，真崩溃时必然出问题。前提是重要状态全部外置到 crash-safe 的存储——这个前提本卷已经用四章立完了。落到 run 上，恢复方案就一条：**启动扫描**。进程起来的第一件事，扫出全部 running 与 waiting 的行，逐行裁决——能续跑的交给 §七 的 resume 判据，不能的终态化为 interrupted，每一笔裁决落事件。这条逻辑天然覆盖崩溃、强杀、断电、升级重启，一条路径管全部退出方式。桌面案例修复后的验收实测过它：任务运行中退出应用，重启后那一轮带着"[已中断]"标记完整可见【经验】。

启动扫描有个盲区：它只在启动时跑。进程活得好好的、某个 run 却卡死了——工具僵住、流断在半空、模型调用永不返回——没有崩溃，就没有启动扫描。补这个盲区的是**看门狗**：周期扫描 running 的行，进程还在、run 却超过 deadline 再无活跃事件的（step/effect 事件的最近时刻即存活信号，heartbeat 的完整定义见 §七 7.6），判为卡死、终态化为 failed（infra_failure）。这与启动扫描是转移表里两条不同的行：看门狗管进程还在、run 卡死了，直接给终态；启动扫描管进程没了、run 可能还有救，收敛为 interrupted 交恢复裁决。周期扫描是一笔固定开销，买下的是启动扫描照不到的盲区。§一 1.6 的破坏实验埋过一句"超时该标 failed，交给 run manager 的看门狗"，欠条在此兑现——判定 run 死活的职责在内核，界面猜不得，也轮不到它猜。

还剩一个双重认领问题：两个进程同时扫到同一个孤儿。双实例部署、或旧进程还没死透新进程已经起来，两边同时认领、同时 resume，历史被写成两份。单机的解法在状态机之外——单实例锁（端口、pidfile），第二个进程起不来；多实例的解法就是 5.7 备好的装备——认领即取租约，写入带 fencing token，慢的那个被状态层拒之门外。谁赢都行，赢的只能有一个。

## 5.9 进程壳层：状态机的地基

启动扫描有一个没写出来的前提：进程死了，得有人把它拉起来。状态机管"拉起来之后知道干什么"，壳层管"死了有人拉起来"——两层缺一，另一层的承诺都成空文。

壳层的纪律是 supervision 的单机降维【规范/官方文档，Erlang/OTP Supervisor】。健康检查加退避重启是主体；关键在重启强度上限——时间窗内重启超过限值，停止重启，把"救不活"作为显式状态呈现给人，附诊断与重试入口。无界的自动重启比不重启更危险：救不活的进程被无限拉起，每次启动扫描都白跑一遍，故障被重启循环遮住，没人知道系统已经病了。上限的代价是把一部分本可自愈的偶发故障提前升级给人——换来的是重启循环不再遮蔽真故障。子进程同理：工具子进程的生命周期绑定父进程（进程组、Job 对象），父进程一退出、子进程随之终止，孤儿清理只是兜底手段。

退出路径要给收尾留窗口。桌面案例的托盘退出曾经先 POST shutdown、sleep 两秒、强杀进程，全程不检查是否有 run 在跑【经验】——两秒够不够收尾全凭运气，运气差的那次就是又一个帧 8。正确的顺序与状态机对齐：停止接受新意图，活跃 run 收尾或显式终态化，然后退。二次启动的杂事——端口被占、pidfile 残留——也要有归宿，处理不了就走"救不活"的呈现路径。壳层的完整故障谱（窗口管理、更新、诊断页交互）是工程细节，本章只立它与状态机的接口：每一种退出方式，最终都必须汇入启动扫描那一条恢复路径——这正是 crash-only 的操作化。

## 5.10 状态机要携带自己的版本

状态机自己也会变：加一个状态、改一条 guard、拆一个终结原因。变更上线时，库里躺着旧版本时代的 run——interrupted 的、waiting 的，等着被恢复。按哪一版语义恢复它们？不设防的答案"总按最新版"会当场制造表外转移：旧 run 停在一个新表不认识的状态里，或者要走一条新表已经删掉的转移。

所以 run 行携带 **state_machine_version**——工作制品 A（State Registry）的 run 行为它留了登记位，字段的正式收录随 State Registry 在 §六 6.0 交付；本章立起它的语义：恢复扫描先看版本，同版按表走；跨版先跑显式迁移，把旧 run 逐个映射进新表的合法状态，迁移本身落事件。规则一句话：转移表的变更就是 schema 变更，享受同等的迁移待遇。这条现在看着像过度设计，§七 的 resume、§十 的 compaction 版本、§十一 的授权重验全都要踩在它上面。

## 5.11 多入口，单执行内核

回到 §一 1.4 立下的那个决策，把细则补齐。入口清单比直觉里长：UI、API、IM 渠道、SDK/CLI，再加两个没有人在场的——scheduler/timer 与 webhook。后两个是把语义收进内核的又一重理由：无人值守的 run，它的确认、失败呈现、完成通知全走异步路径，有人与无人两种场景的差异若由各入口自行处理，同一台状态机立刻又裂成两套。

细则三条。其一，入口只做两件事：把各自形态的输入适配成统一的意图（携 idempotency key），把内核的事件流转发成各自形态的输出。其二，permission、cancel、resume、工具执行四种语义只在内核实现——任何入口的"取消"按钮按下去，走的都是转移表里同一行。其三，入口不得持有 run 状态——投影不回写的入口版，§一 1.6 已立判定口径。实现层面的旁证：对 Claude Code 的第三方源码分析显示，CLI、IDE、SDK 多个入口共用同一套核心循环与权限门【预印，arXiv:2604.14228 v2，快照 Claude Code v2.1.88，当前行为以官方文档为准】。

交付物是 **Entry-to-Kernel Routing Matrix**（工作制品 E 升 v1）：每个入口一行，六列——意图适配、流转发、permission、cancel、resume、工具执行——后四列必须指向内核，出现空格或"入口自实现"即缺口。评审时拿被评系统照表填一遍，语义分叉当场显形；桌面案例只有一个 UI 入口，尚且长出了"重载后拿本地缓存当会话真相"的恢复线分叉（§三 缺口二的一环），多入口系统的分叉只会更隐蔽。

## 5.12 业界对照：一台公开状态机的一生

自研之外，业界有一台把 run 状态机做成 API 层显式契约的著名实现，值得整段端详——连同它的退役。OpenAI 的 Assistants API（2023 年推出）把 run 的状态集合直接写进产品契约：queued、in_progress、requires_action、cancelling、cancelled、failed、completed、incomplete、expired 九个状态公开可查【规范/官方文档，终稿前回核】。对照本章：requires_action 就是 waiting；expired 是平台级看门狗的产品形态——没人管的挂起 run 由平台按超时收尾，与 5.2 "waiting 自带 deadline"同一条纪律；run 活跃期间锁定整个 thread 做互斥——5.7 的三件装备里，它选了锁。至于它那个 cancelling 过渡态，本章七状态里没有对应物：单机同步模型把取消做成一条带 guard 的原子转移（guard＝半轮已落盘），Assistants 用显式过渡态承载的"收尾中"语义，在这里由那条 guard 就地兑现——5.2 说过的"过渡性语义不单列状态"，具体例子就是它。

失效点两条，都不在状态集合本身。第一条：社区故障报告里出现过 run 长时间停在 queued、in_progress，或 requires_action 反复循环【经验，社区故障归纳，检索范围与代表性帖子终稿前补录编辑工作区】——服务端状态机再完备，客户端不配超时兜底照样卡死。状态机契约是两端的合同：服务端保证转移合法，客户端保证悬置有界，只签一端，用户看到的还是那个转不完的圈。第二条更根本：这套 API 已被 OpenAI 宣布 deprecated，计划 2026-08-26 关闭（宣布时点与关闭日期以官方文档终稿回核为准，截至本卷写作尚未关闭）【规范/官方文档】，Run 概念由 Responses 取代。一台运行了三年的公开状态机整体退役，每个依赖它的客户端都要把自己的轮询、重试、恢复逻辑迁去新语义——这是 5.10 版本问题的产品级放大：状态机是契约，契约会退役，而 run 数据活得比状态机版本久。选型结论沿 §三 3.9 与 §四 4.6 的口径：状态机这格自研成本不高、语义主权贵重，托管方案要连它的退役时间表一起买下。

## 破坏实验：四路并发与分叉

本章的破坏对象是转移表与单内核决策本身。四个场景，各按四步测量协议执行：

1. **双入口同时触发同一会话**。破坏动作：UI 与 API 各提交一条意图，间隔压到毫秒级。观测点：events 里两条意图各自的裁决事件；runs 表的活跃行数。判定：恰有一个 run 进入 running，另一个落 reject/enqueue/interrupt 三者之一的显式事件，无双写。复跑 N=3。
2. **双进程同时 resume 同一孤儿**。破坏动作：制造一个 interrupted 的 run，同时启动两个进程实例。观测点：认领事件与写入路径。判定：恰一个实例认领成功；单机形态下第二个实例应因实例锁拒绝启动，多实例形态下慢者被 fencing token 拒写且有事件。复跑 N=3。
3. **同一创建请求重发两次**。破坏动作：携带同一 idempotency key 的创建请求连发两次。观测点：runs 表计数；两次应答的 run 引用。判定：库里恰一个 run，两次应答指向同一引用；同 key 不同 payload 时返回显式冲突。复跑 N=3。
4. **入口语义分叉 contract test**。破坏动作：从每个入口对同一 run 发起 cancel。观测点：随行 `run.*` 转移事件（`run.state_changed`／`run.finalized`）的发起者与转移行。判定：全部入口路由到转移表同一行，事件里只有发起者不同；任何入口出现独立的取消路径即失败。复跑覆盖全部入口。

实证状态照实分层【经验】：桌面案例修复后，场景 1 的单入口版（抢占先收尾）有端到端集成测试，tryStart 串行化有回归测试，"[已中断]"收敛有验收实测；四场景的完整矩阵是 §十四 标准故障包（各章破坏实验 fixture 的汇编）的工单，此前按思想实验执行，判定口径先立在这里。

## L 级自检

按 §一 的成熟度尺（L1 能跑、L2 能看，全表见 §一 1.3）。本章机制的 L2 底线与 §四 卡面预期一致：转移表在、每笔转移落随行 `run.*` 事件、准入/互斥/抢占三类裁决有事件——三件齐是 L2；看门狗与四类终结原因给 L3（能评）备料，失败归因从此有了机器可读的维度。桌面案例现状照 §三 的账：增量持久化把真相侧升到了 L2，抢占决策事件仍缺，是记录在案的 L2 半格——本章的转移表就是那半格的补格工单。参考实现要到 §十四 才成形，转移表的"可执行"在那之前是规格，此处不冒充。坐标系落位补一句：本章兑现转移契约的可观测（转移即事件）与稳定（破坏实验 N=3 复跑）两格；可控押在内核唯一路径上，闭环的消融数据留给 §十四 的参考实现。

## 立即可做的一个动作（五分钟）

builder 版本：grep 自己项目里 run 状态的全部赋值点（`status =`、`UPDATE runs SET status`，名字不重要），数出来的数字就是隐式状态机的份数。然后对着 5.3 的表逐个问：这个赋值点对应表里哪一行？触发事件是什么，guard 在哪验？对不上的赋值点，就是自己系统里还没爆发的帧 7。

assessor 版本：一个问题加一条 SQL。问被评团队：一个 running 的 run 能以几种方式终结，每种的 terminal reason 叫什么——答案数对不上转移表行数的，按隐式状态机处理。再查（表名列名按被评系统的 schema 替换，语义是"活跃态但久未更新的 run"）：`SELECT count(*) FROM runs WHERE status='running' AND updated_at < 24 小时前`——这个数字大于零，本章那句主张就在这套系统里有了本地证据。

## 遗留问题

转移表通篇在重复一件事：落事件、有记录、可解释。可是这些事件记在哪张表里，谁有权写它，状态行与事件序列不一致时以谁为准，半轮消息又挂在哪个载体上——"记下来"三个字背后的归属问题，本章全部按下未表。状态、事件与持久化的完整答案，§六。
