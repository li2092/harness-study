## 〇、三章返工的根因诊断（防复发）

1. **模板不是推理链。** 九段模板规定每章"要有什么"，没规定"谁推出谁"。按模板填空，段与段之间没有"因为→所以"，任意换序仍然通顺——这就是"散"的机制。处置：九段模板降为交稿前的完备性检查单，不再充当章结构。
2. **多视图是描述法，不是推导法。** 4+1 式视图适合描述一个已存在的系统；教材需要推导——从需求逼出约束，从约束逼出结构。把组件图、时序、数据视图并列陈列，读者看到的是展品目录。处置：视图本身保留，但每个视图必须由上一步推理产生的问题引出——视图是推理的证物，不是目录项。
3. **素材驱动。** 手里证据多（MAST、23.8pp、事故报告、11 张表），写作变成"给素材找位置"。处置：反转为"节点要素材"——推理链节点需要什么才调什么，没被任何节点调用的素材不进正文。

## 一、卷级论证树

**根问题**：照入门卷把部件装齐了，为什么系统还是不可靠？

**根主张**：部件正确加不出系统正确。系统正确是一种运行时性质——在时间、故障、并发与不确定模型之下保持语义不变。本卷把这种性质拆成六类契约，逐章给出可实现、可验证的做法。

**全卷推理顺序（五步，不许倒置）**：

目标（要保住什么）→ 约束（什么在威胁它）→ 结构（谁负责挡住）→ 行为（运行时怎么走）→ 证据（怎么证明真的挡住了）

配套一条全卷硬规则：**任何结构名词（组件、表、平面、状态机）出场之前，上文必须先出现迫使它存在的问题。** 组件图是推导的终点，不是开场白。

## 三、章级 spec 模板（动笔前产出，交用户审）

半页以内。过审后正文只能沿链展开。

```
# §N 章 spec
输入问题：（一句，与问题链表一致）
本章主张：（一句，可被证伪）
推理链（3-7 个节点）：
  N1 前提/现象：……
  N2 因为 N1，所以……
  N3 但是……（张力或反例）
  N4 所以需要……（设计结论）
  N5 验证：……（时序走查／破坏实验／证据）
遗留问题：……
段落地图：
  | 节 | 挂载节点 | 读者进入时已知 | 读者离开时新知 | 调用素材（≤1 件主证据） |
边界（本章不讲）：……
```

**三条硬规则（可判定，R0 审稿逐条跑）**：

1. **连接词测试**：推理链相邻节点之间必须能填入"因为／所以／但是／否则"之一；只能填"另外／还有／同时"的，是并列不是推理——合并或砍掉。
2. **结构出场规则**：任何结构名词首次出现前，上文必须存在迫使它出现的问题（R1.5 空名词检查从开篇推广到全章）。
3. **素材配额**：一个节点至多一件主证据；正文表格每章 ≤3 张，登记表全部住 `90-artifacts.md`、正文只引用；未被任何节点调用的素材进附录或删除。
4. **因果叙事规则（2026-07-20 用户样张裁决，v2.0 审回"苍白、无前因后果"后加）**：每个设计点按"朴素做法→失效方式→失效根因→设计出场→根基→代价的理由"展开——先展示不设防的系统如何失效（失效场景尽量呼应开场怪事），根因分析到结构层，结构名词随后出场，再交代它接的是哪条老纪律、代价为什么划算。禁止"价值：／代价：／推翻条件："式冒号列点腔，取舍融进叙述。推理链保证节与节的因果，本条保证节内每段的因果。
5. **章级判据（2026-07-20 大纲 v5.4 起，v2.1 第三次审回的流程补丁）**：每章 spec 必须给出三个上限与三样带走——新概念数、前向引用数、正文表格数的上限；读者带走的一图、一句、一动作。R0 时用 grep 实测计数，超限先砍内容再动笔法。§一 定为 12／10／2。此条是 spec 层的检查器：R0-R3 只查"正文合 spec"，本条查"spec 本身装不装得下"。

## 四、§一 章 spec（worked example，v1.2 对齐大纲 v5.4 瘦身；已被 §八 v2.0 取代，留档对照）

- **输入问题**：照入门卷把部件装齐了，系统还是时好时坏——问题出在哪一层？
- **本章主张**：问题不在部件在衔接。三个本质变量（执行跨越故障边界、副作用泄向外部世界、核心组件输出不确定）逼出六类契约；契约的职责分配落成八个组件。
- **推理链**：
  - A1 现象：部件齐全的 agent 仍时好时坏。主证据一件：同一模型换 harness 差 23.8pp——问题在部件之外（方差收窄推论为卷价值辅证）。
  - A2 因为问题在部件之外，对照在线服务三个默认值（进程可弃／重试无害／行为可复现）逐个失效——三个本质变量，各配所在基础设施的失效画面。
  - A3 三个变量各划开一类口子：状态撕裂、账对不上、无从归因（MAST 佐证）。
  - A4 站到救援者位置逐类反推，得六类契约与承诺句（直接命名，不经"不变量"中转；第六类来自变量组合）。
  - A5 逐条问"谁来保它"，职责分配长出八组件（每个按朴素做法→失效方式→设计推出）；组件图为推导终点；四个承重取舍融进各自推导现场。
  - A6 一条正常时序走查（九步、落盘点加粗），立"任何机制要能在时序上标出位置"的全卷判断标准。
  - A7 六契约总览表＋分章地图收尾，遗留问题交 §二。
- **遗留问题**：承诺说"什么不能坏"，怎么判定"没坏"→§二。
- **章级判据**：新概念 ≤12、前向引用 ≤10、正文表格 ≤2（六契约总览必占一张）；带走：组件图一张、"每个状态有归宿…"一句、五分钟动作一个。
- **边界（本章不讲）**：恢复时序（§七）、实体链与全局规则（§六）、五平面与干预点（§十一）、部署（§十四）、双层控制流（§十二）、两种 graph（§八）、判据（§二）、事故细节（§三）。（编号已按 v5.5 顺移）

## 十二、§五 章 spec v1.0（状态机章·首个深潜章，随正文 v1.0 同批交审）

## 十三、§六 章 spec v1.0（状态章·统一语言冻结章，随正文 v1.0 同批交审）

**章职责**（对齐问题链 §六 行与 §五 遗留问题）：第五章的转移表通篇要求"落事件、有记录"——本章回答记在哪、谁能写、打架信谁。开场冻结全卷统一语言（实体链＋四条全局规则，v5.4 自 §一下沉），随后立"哪份状态算数"的完整答案：数据库持久状态是 SSOT，context 与 UI 都是投影。本章是"章节引用文字化"（§七.10.5）首个执行章。

- **输入问题**：状态记在哪、谁能写？
- **本章主张**：持久状态是唯一真相源；context 是一次模型调用的有损读投影，UI 是另一种投影——投影可以丢、可以错、可以重建，真相不行。

**两项结构裁决（携自 §五 批次的 Howpot vNext 素材，recommendation 随 spec 交审，用户终审时可推翻）**：

1. **Attempt 不设独立实体**。业界参照（research/volume2/11 条 28）的统一状态链为 Task→Run→Step→Attempt→Action，attempt＝同一步的网络/模型尝试。本卷裁决：实体链维持六级不加 Attempt——模型侧每次真实调用记一行 invocation（失败的调用也留档成行，invocation 即 attempt）；工具侧由 Effect Ledger 的 attempt_no 承载。理由：独立 Attempt 实体是"多层共享重试预算"系统的产物（Relay 11 次 × Agent 3 次那类），单机参考实现的重试层级不足以摊销一个新实体的登记成本。推翻条件：出现跨层共享 retry budget 需求时升格为独立实体。
2. **lease 与 run 状态机分层**。业界参照（ADR-007 素材）的 lease 有 active→stopping→terminal 三态，表面与第五章"过渡语义由 guard 承载、不单列状态"冲突。本卷裁决：分层成立——run 状态答"任务到哪了"，lease 答"谁有权提交副作用"；lease 是进程内授权对象（重启即失效，恰证其非持久状态），不进实体链、不进 State Registry；主场第八章 commit gate。第六章只在 6.0 说清"执行权不是实体链成员"一句。

**推理链**：

- N1 承接：第五章遗留四问（事件记哪张表、谁有权写、状态行与事件序列不一致信谁、半轮消息挂哪个载体）＋开场争论场景"重启之后，用户的消息还在吗"——三个工程师三个答案，根因是没有公用名词与归属表。
- N2 冻结统一语言（6.0）：实体链六级（Conversation→Run→Turn→Step→Invocation/Tool Execution）逐级由处境逼出；关键裁决四条（run 可无 conversation、subagent=child run、turn 无独立表、attempt 不设实体）＋lease 分层一句；十一张表；四条全局规则（ID/owner/correlation/version）；State Registry v1 在此交付、章末升 v2。

- N4 状态分五类（6.2）：业务/运行/对话/工作记忆/artifact，分开理由是生命周期与写者不同；作用域也是归属（跨会话泄漏反例）。

## 十六、§九 章 spec v1.0（交互章·三条时间线与四词辨析，随正文 v1.0 同批交审）

**章职责**（对齐问题链 §九 行与 §八 遗留问题）：第八章管住了系统伸向世界的手，本章管从外面伸进来的手——人的。开场即第三章那场事故的正解：用户点链接、窗口被带走（disconnect）、回来少一轮（客户端视图当了真相源）——第三章诊断了"运行中对话无 SSOT"，第五/六章立了 SSOT 与投影契约，本章补最后一环：连接会断、人会打断，交互面怎么在这些扰动下不破坏已经立好的恢复机器。兑付五张欠条：第三章十帧表帧 4-6 交互投影层（Temporal 对账时判在其边界外）；第二章 2.4 SSE evidence 空格的"接回"补全（第三章兑付了"断开安全"半边，本章补"接回"半边）；第二章交互契约反例（流无 [DONE]、UI 永远"生成中"）；工作制品 A message 行半轮归宿（§9.7 裁决）；工作制品 A approval 行挂起即持久化（§9.8）与第五章 waiting 的 HITL 语义细节。本章是 ADR-006 素材（research/volume2/11 条 12-17）主场。

- **输入问题**：流式与人机挂起怎么不破坏恢复机器？
- **本章主张**：交互面是投影，不是生命线——run 的生死只由状态机管；断流不等于断 run，UI 掉线不等于任务取消；disconnect/cancel/interrupt/suspend 是四件不同的事，混用一个就把一场断线误杀成一次取消。

**推理链**：

- N1 三条时间线（9.1）：后台 run、网络连接、客户端视图三条独立的钟。朴素做法把三条当一条（连接在＝run 在＝UI 正确），失效方式即第三章事故（连接断、UI 以为 run 没了、重问覆盖）；失效根因＝把一条易失投影当成 run 的生命线。设计出场：三条解耦，run 的生命只由第五章状态机管，连接与 UI 都是投影。
- N2 SSE 给什么缺什么（9.2）：EventSource 给单向推、自动重连、lastEventId；agent 场景常用的 POST/fetch stream（要带 body）没有这套自动语义，续传得自建。
- N3 协议层 session 不可依赖（9.3）：MCP 2026-07-28 移除 Mcp-Session-Id 即例证【规范/官方文档，RC】——续传责任落应用层：cursor/sequence、snapshot+delta、replay window；断线接回＝从游标之后补发，正是第三章"接回没做"的补法。
- N4 传输层的 silent success 与流终结（9.4）：ADR-006 主证据。HTTP 200 之后流内写 error、客户端只认 choices、无条件产出 finish → 空或半截回复以成功收场；失效根因＝finish_reason 是模型停止原因、不是传输成功提交点，把模型层"说完了"当成传输层"交付成功"。设计出场：流终结真值表——每种结尾（typed done/legacy [DONE]/typed error/EOF 无 terminal/半帧/malformed/非法 envelope）一行、全部 fail closed；终结是显式可判定的提交点。这是第二章假通过、第八章 result≠outcome 在传输层的成员。顺带熔断提交点错位（2xx headers 即 recordSuccess 清零→连续 200 后中断永不开断路器）——"成功在哪一刻算数"又一现场，与第八章提交点、第五章 lease 同构：成功在 terminal 写入下游后才提交。交付工作制品 O（流终结真值表）。
- N5 四词辨析（9.5，概念核心）：disconnect≠cancel≠interrupt≠suspend。disconnect＝连接断（不动 run）；cancel＝用户 Stop 终止 run（第五章转移）；interrupt＝新意图抢占（第五章）；suspend＝挂起等输入（waiting，第五章）。四词各落位第五章转移表哪一行，混用即第三章事故的语义根源。交付工作制品 P（交互语义表）。
- N6 取消令牌贯穿链（9.6）：真取消要贯穿 UI→server→model→tool→child process，断在任一环即上游以为取消、下游还在跑——第八章 8.8 子进程僵尸写的交互面来源。

- **本章主张**：context 是投影不是容器——不是把历史一股脑塞进 prompt，而是有来源、优先级、预算的确定性策展；压缩是事务不是随手摘要——失败要回退、边界要落盘、系统约束不进压缩范围；memory 与 artifact 要有来历，否则又成一个没人认领的真相源。

**两项结构裁决（携自工作制品 A 预告，随 spec 交审、用户终审可推翻）**：

1. **compaction 摘要不单列实体表**。工作制品 A v1 把摘要暂作 `messages` 特型行。本卷裁决：维持特型行，不立独立摘要表——摘要随 conversation 走、生命周期与消息一致；但 `compaction_version` 作为独立字段登记（挂在特型行上），resume 靠它对齐（§10.9）。推翻条件：出现"摘要需独立版本审计或跨会话复用"需求时升格独立表。
2. **memory 行从占位实化为契约形态**。工作制品 A memory 行 v1 是占位。本卷裁决：实化其字段契约（写入 provenance、TTL、撤销标记、scope），但标注单机参考实现可不实现长期 memory——实化的是"若做 memory 必须带什么"的契约，不是要求每个 runtime 都有 memory。

**推理链**：

- N1 朴素做法（10.1）：context＝把历史一股脑塞进 prompt。失效方式：撞 token 上限；attention budget／context rot（越长召回越低）。（"全量重发打断 prompt cache"是误述，已从正文删除：缓存按累积前缀哈希命中，失效条件是断点及其之前的块发生改动，不是重发本身。）失效根因：把 context 当"容器"（越全越好），而第六章立过它是投影——投影要有来源、预算、优先级，是策展不是堆积。设计出场：context assembly＝有来源／优先级／预算／去重／可信度的确定性过程。第六章投影三契约在"给模型这一侧"的落地。交付工作制品 Q。
- N2 四种手段（10.2）：撞上限的应对——compaction（压缩摘要重启窗口）、note-taking（写窗口外后续拉回）、JIT retrieval（只存轻量标识、运行时拉）、subagent（干净窗口做深活、回传浓缩）。各自适用条件。定量：Anthropic context editing +29%／memory＋context editing +39%／token −84%（100 轮 web search 评测）【规范/官方文档】；code execution MCP 把工具目录移出 context，150K→2K token【规范/官方文档】。都是 attention budget 的管理手段。
- N3 压缩是事务（10.3/10.4，本章硬核）：compaction 不是顺手摘要，是必须事务化的操作。失效三现场：压缩到一半崩溃→半压缩态（既非完整历史、也非完整摘要）；摘要漏掉系统约束（把"必须用绝对路径"压没，模型之后犯错）；配对破坏（压缩把 tool_call 留下、tool_result 压没——第六章 pop() 孤儿的压缩版）。失效根因：压缩改的是投影，但若压缩结果反向覆盖历史，就违反"投影不回写"（第六章）。设计出场：压缩事务化——失败回退不留半压缩、边界落盘（compaction_version）、系统约束不进压缩范围或压缩后重新注入、配对修复扫描。compaction×cache×resume 三方耦合：压缩打断 prompt cache 前缀（成本）、resume 必须读到与崩溃前同一 compaction 版本（否则历史对不上）。交付工作制品 R。
- N4 memory 的来历（10.5）：memory 写入不免费——污染（错记忆写进去后一直错）、过期（旧记忆该撤销）、撤销（怎么删一条及其影响）、provenance（哪来的、哪个 run 写的、基于什么）。失效根因：memory 是又一种"投影升格成真相"的风险——无来历、不可撤销的 memory 就是没人认领的真相源（主线二/主线一）。设计出场：memory 写入带 provenance／TTL／撤销标记／scope。工作制品 A memory 行实化＋交付 S（Memory Provenance）。
- N5 artifact 归位（10.6）：artifact（生成的文件、报告等工作成果）不应藏在 conversation 文本里——藏文本里会被压缩吃掉、无法独立引用、无 lineage。设计：artifact 独立登记（工作制品 A artifact 行、lineage），不混进对话流。第六章 artifact lineage 双向对账的连续性侧。
- N6 模型行为变化（10.7）：接近 context 上限时模型行为会变——Cognition 观察 Sonnet 4.5：模型对剩余 token 的自估"一贯低估、精确但错"，自认接近上限就抄近路、留未完成任务，即使余量充足【厂商实践，Cognition】。所以不能指望模型自觉管理 context，压缩／reset 要走确定性硬路径（hook／工程），不靠模型自律——接第一章"硬控制走模型外"。
- N7 invocation 的决定因素（10.8/10.9）：一次 invocation 由 model／prompt／tool／context policy 共同决定——所以 resume 必须尊重原 invocation 的 compaction 版本与 policy 版本，否则重建的 context 与当时不同，invocation 记录（第七章重放缓存）就对不上。回指第七章 invocation、第八章 Plan Lease 的 history_cursor。
- N8 隐私删除接口（10.10）：memory／context 里的隐私数据、删除要求，是第三卷数据治理的接口。本章只立接口（memory 可撤销、artifact 删除语义清晰），治理留卷三。
- 验证：破坏实验四场景四步协议（压缩中断、摘要遗漏系统约束、memory 污染、resume 读旧 policy/compaction 版本），实证分层。

- **遗留问题**：连续性守住了——但压缩、写 memory、删除这些动作谁有权做、权力持续多久？权限、身份与运行时隔离，第十一章。
- **章级判据**：新概念 ≤12、前向引用 ≤8（第十一/十三/十四章＋卷三）、正文表格 ≤3（四手段对照＋context assembly 来源表／compaction contract 必占）；带走：四手段一张、"context 是投影不是容器、压缩是事务不是摘要"一句、"查你的压缩会不会把系统约束一起压没"一个动作。
- **交付物**：Context Assembly Spec（工作制品 Q）、Compaction Contract（工作制品 R）、Memory Provenance（工作制品 S）；工作制品 A compaction_version 字段登记＋memory 行实化。
- **验收清单**：同 §八 口径（老师声部；STAR＋指向含跨章回指带背景；文字化引用零 §；工作制品引用带名称；业界对照 ≥1 家带失效点——Anthropic memory tool 给机制不给治理＋code execution MCP 隐私换重建；破坏实验四步协议＋实证分层；L 级自检＋坐标系落位；双读者动作；R1 红线；四维评审四路 opus）。

## 十八、§十一 章 spec v1.0（权限章·授权有边界有期限、恢复≠恢复授权，随正文 v1.0 同批交审）

**章职责**（对齐问题链 §十一行与 §十 遗留问题）：本章是 authority lifecycle 主线（主线五）的收口章。第五章的 lease、第六章 6.11 的三生命周期分离与 lease 分层、第七章 7.8"state continuity 推不出 authority continuity（完整展开第十一章）"、第八章 8.3 的 committed_under、第九章 9.8 的挂起授权重验、第十章的"压缩/memory/删除谁有权做"——六张授权欠条在此收口成完整规则。同时接大纲下沉件：五平面与三干预点（11.0，自 §一 3.1-3.6/3.13 下沉）。本章是权限素材主场（Codex execpolicy/分层沙箱、Anthropic permission 六步序/hooks、Lingering Authority 论文、Howpot vNext 条 24-27）。

- **输入问题**：这些动作（工具执行、压缩、写 memory、删除）谁有权做，权力持续多久？
- **本章主张**：prompt 里写"你不许做 X"不是安全边界——权限是运行时在模型之外强制的机制；授权有边界（谁、对什么、到哪）且有期限（到何时、随什么失效），恢复状态不等于恢复授权：resume/fork/replay 不得让旧授权随状态静默复活。

**一项结构裁决（携自工作制品预告，随 spec 交审）**：**policy decision 是否独立表**——工作制品 A 预告"并入 events 待 §十一裁决"。本卷裁决：维持并入 events（type=policy.decided），不单列实体表——policy decision 是事件流上的一类事件，随 run 走、生命周期与事件一致;但强制字段（principal、规则、输入摘要、决定、依据、enforcement point）作为该事件类型的必带负载登记。推翻条件：需对授权决策做独立于事件流的合规审计/长期保留时升格。

**推理链**：

- N1 朴素做法（开场/11.5）：prompt 里写"你不许 rm -rf""只读这些文件"当安全边界。失效方式：模型被 prompt 注入绕过、幻觉无视、或就是没读到——prompt 是对模型的请求，不是对系统的约束。失效根因：把软提示当硬边界。设计出场：权限是运行时机制，在模型之外强制执行。这是第一章"硬控制走模型外"（第二章 T4 落点）在权限域的主场。approval 是风险决策点，不是通用安全边界（高风险动作请人签字，不是每个动作都拦）。
- N2 principal 与委托链（11.1-11.3）：谁在行使权力（principal：user/agent/subagent/tool·service/operator）;权力从谁委托来（delegation chain：授予者/scope/期限/再委托/撤销）;agent 是用户代理还是独立身份——决定权力从哪继承、到哪为止。交付 Principal & Delegation Registry（工作制品 T）。
- N3 硬软层级（11.6，本章硬核之一）：permission/sandbox 是硬边界（模型外强制），hook/classifier/prompt 是软提示（best-effort、可绕）。Anthropic 官方明说 hook 是 best-effort、要硬 allow/deny 用 permission 系统;permission 六步序 deny 恒胜、bypass 也拦不住 deny。Codex execpolicy 三档 allow/prompt/forbidden、shell-escalation Run/Escalate/Deny 是实例。别把软层当硬层——把 prompt/hook 当安全边界是最常见的假边界。
- N4 least privilege/agency + subagent 收窄（11.4/11.8）：默认收窄、显式升级、升级留痕;least privilege（能做的最少）加 least agency（自主度最低）。subagent 权限默认收窄、不继承 bypass——subagent 继承父 bypass 且无法逐个覆盖（Anthropic 官方文档明标的风险点）是反例；Lingering Authority（arXiv:2606.22504）说的是另一类：子目标关闭后未回收的临时资源／副作用能力，时间维残留，论文全文不涉 subagent／继承。Howpot skill 激活状态跨会话泄漏（注释称 session scope 实按 projectPath 缓存共享）是同族。
- N5 隔离四类（11.7/11.9）：filesystem/process/network·egress/secret 四类隔离接口;bubblewrap 默认整盘只读＋按路径分层覆盖。关键失效：Howpot"只读"集合藏网络外发（web_search/fetch 跑在 policy 前）——read-only ≠ 无副作用，信息外流也是副作用;PII vault 跨请求共享可变状态（隔离边界失效，映射表不能共享）。tool output/文件/网页/memory 带信任标签（外来内容默认不可信）。交付 Runtime Trust Boundary（工作制品 D 填充）。
- N6 common-mode failure（11.11，本章硬核之二）：defense-in-depth 只在执行点与失效模式独立时成立。"有四层"不等于四层独立——四层若共享一个 parser/classifier，一个坏了全塌。hook 静默 fail-open（Howpot：非 0/非 2xx/网络失败默认放行且缺审计）是反例。控制记录必带六项：enforcement point、failure mode、shared dependency、fail-open/closed、fallback、evidence，不能用"有四层"代替 common-mode 分析。交付 Common-mode Failure Matrix（工作制品 V）。
- N7 authority 不随状态恢复（11.12，主线五收口）：resume/fork/replay 不得静默恢复旧 approval、session-scoped permission、delegation token、credential;确需持久化的 authority 显式列入契约，并在上下文/主体/版本变化后重验。第七章 7.8 铁律、第九章 9.8 挂起恢复、第六章 Lifetime Matrix approval 行、第八章 committed_under 在此收口成完整规则。交付 Authority Lifecycle Matrix（工作制品 U）。
- N8 五平面与三干预点（11.0，下沉件）：八组件按持有权分五平面（Interaction/Control/Execution/State/Evidence），各配"绝不持有"清单;四条依赖禁令（Interaction 不写 State、Execution 不直连 Interaction、Control 决策必落 Evidence、State 不依赖任何平面）;三干预点 assemble/model/execute 平面归属与三处分别留证（assemble 细节第十章）。runtime 必须产出 policy decision 与权限证据（11.10）。交付 Intervention Point Map（工作制品 F 填充）＋五平面落位表（并入正文，另供第十五章）。

## 十九、§十二 章 spec v1.0（多 agent 章·subagent=child run、契约沿父链继承，随正文 v1.0 同批交审）

**章职责**（对齐问题链 §十二行与 §十一遗留问题）：前十一章立的是单 agent 的六契约；本章回答"agent 派出分身、多个 agent 并行协作时，这六契约怎么不被破坏"。核心动作是把 run 的概念递归一层——subagent 不是新物种，是 child run，前面立过的状态机（第五章）、child run 实体（第六章 6.0 裁决）、权限收窄（第十一章）沿父链继承适用。兑付第十一章结尾四张欠条：父子权限收窄传递、几个 agent 抢写同一份 artifact、子任务失败不拖垮全局、subagent 回传结果凭什么因"内部"就可信。接大纲下沉件：双层控制流（12.0，节点内 loop vs 跨节点编排 graph；与第八章 8.12"两种 graph 之辨"是不同分层，须区分不撞）。本章外部素材最新最厚：2026 上半年多 agent 编排集中落地（Codex 桌面端 02-02、Devin parallel sessions 02、Cursor 3.0 04-02、MS Agent Framework GA 04-03、Build 06-03 立 Harness 为一等概念），正好做业界对照。

- **输入问题**：子 agent 与并行怎么不破坏六契约？
- **本章主张**：subagent＝child run，契约沿父链继承——多 agent 不引入新契约，是同一套六契约在父子与并行下的组合；组合的失败点不在单个 agent 的智能，在接口、边界、终止条件、handoff 保真度（MAST v3 图 1 三大类失效 44.2% 规格/32.3% inter-agent 错位/23.5% 验证印证）。

**一项命名裁决（随 spec 交审）**：**双层控制流**指"节点内 agentic loop（单 agent 的 tool 循环，Vercel stopWhen/prepareStep、ADK event loop 的层）"与"跨节点 orchestration（多 agent 编排调度，LangGraph superstep、Inngest Networks+Router、Codex/Devin 的父调度层）"两层控制流的分离。与第八章 8.12"两种 graph 之辨"（workflow graph vs world-state graph，讲的是计划表示）正交：8.12 分的是"计划画成什么"，本章分的是"控制权在自治层还是编排层"。正文首现处一句话交代二者不同，防读者混。

**推理链**：

- N1 朴素做法（12.1）：把多 agent 当"更多智能"——spawn 几个 agent 各干各的、把结果拼起来就行。失效方式：MAST 分析 7 框架 1642 条 trace，失效三大类里协调面占七成六（规格设计 44.2%＋inter-agent 错位 32.3%），远超单 agent 能力问题；典型是 infinite handoff loop（A→B→C→A，没有一个 agent own 这个任务、每跳重新规划、context 逐跳丢失）。失效根因：多 agent 引入的第一位不是智能，是协调面——每多一个 agent，多一组"接口/边界/终止/信任"要维护；把协调面当免费的，就把系统正确赌在了最不可靠的一环上。设计出场：subagent＝child run——不新造物种，是 run 的递归；第五章 run 状态机、第六章 child run 实体与 correlation 规则、第十一章权限收窄，全部沿父链继承适用。根基：crash-only 与单一真相源不因层数改变。代价：递归意味着父要为每个 child 承担一份生命周期管理（起、管、收、验），child 越多父越重——这也是"能不用多 agent 就别用"的第一条理由。
- N2 双层控制流（12.2，下沉件）：节点内 agentic loop（单 agent 自主决定下一步调什么工具、何时停——Vercel stopWhen/prepareStep、ADK event loop）与跨节点 orchestration（父决定 spawn 谁、等谁、怎么合——LangGraph superstep、Inngest Router）是两层不同的控制流。失效方式："graph 取代 loop"的混淆——把自治层的不确定当编排层的确定，或反过来把该自治的步骤硬编码成图。失效根因：两层的正确性判据不同（loop 层判"该不该再调一次工具"，图层判"该不该 spawn 下一个 agent"），混一层就用错判据。设计出场：显式分层——2026 框架共识（MS Agent vs Workflow、ADK LlmAgent vs Sequential/Parallel/Loop、CrewAI Crew 嵌 Flow、LangGraph 节点内 loop vs graph superstep 四家殊途同归）。根基：workflow vs agent 决策梯度（第一章复杂度前置）的多 agent 版。代价：显式分层要求先想清楚"这段该自治还是该编排"，把设计负担前移；换来的是可追踪——编排层确定则失败可定位，全自治则不可。
- N3 何时上多 agent（12.3，决策梯度＋止损线）：Anthropic 决策梯度（单调用→workflow→agent→multi-agent，每级换更高延迟/成本/复合错误风险）；orchestrator-worker 在 read-heavy 研究任务比单 agent Opus +90.2%，代价 15x token（单 agent 约 4x），token 用量单独解释 80% 方差；读写不对称——并行只读可扩展、并行写产冲突决策、收敛必须单点写。反例：同等 token 预算下单 agent 常胜多 agent（arXiv 2604.02460/2604.27891，标反主流、量级参考）。判据：多 agent 是成本换质量、不是免费扩展；只有可切成独立只读子任务、且收敛点单一时才值。代价：上多 agent 就上了 15x token 与协调开销，止损线画错就是纯烧钱（40% pilot 半年内下线，单来源量级参考）。
- N4 父子权限传递（12.4，兑付欠条一，回指第十一章）：契约沿父链继承在权限域＝权限取交集——有效权限＝agent 权限 ∩ user 权限，绝不取并集；subagent 默认收窄、不继承父的 bypass（第十一章 subagent 继承父 bypass 反例）。正面形态：Codex 子 agent 继承的是父的收窄沙箱＋网络规则（v0.115.0，继承限制不是继承放大）；Claude Code 的收窄钉在定义处——subagent 继承主会话工具池，由 frontmatter 的 `tools` 白名单／`disallowedTools` 黑名单裁，后台 subagent 再过一道。注意它只钉住"能调哪些工具"，没钉住"调用时要不要问"：父处在 `bypassPermissions` 或 `acceptEdits` 时压过子且不可覆盖（官方 sub-agents 文档；"spawn 前逐一预批＋运行时 auto-deny 未预批"是误述，auto-deny 系 v2.1.186 前的旧行为，现行为权限提示上浮主会话）。反面：Cross-Agent Privilege Escalation（2025-09 演示，两个 agent 互改对方配置自我提权）。失效根因：把委派当权力的透传而非收窄，每次委派都成 confused deputy。代价：取交集意味着 child 常常权不够、要回父要权，任务被升级请求切碎——与第十一章"收过头添乱"同一权衡，刻度是"完成子任务的最小集"。
- N5 并发写冲突（12.5，兑付欠条二）：几个 agent 抢写同一份 artifact。2026 通用答案是 git worktree 隔离（Codex/Devin/Cursor 都用）——每个 child 独立工作目录与分支、共享一个 .git，执行期互不冲突。但隔离不是协调：worktree 各改各的分支，冲突只是推迟到 merge。真正共享 state 的并发写要显式合并语义——LangGraph 并行写同一 key 抛 INVALID_CONCURRENT_GRAPH_UPDATE、要 reducer 函数告诉图怎么合、checkpointer 用 base checkpoint id 做乐观并发（失效点：高吞吐下重试抖动、烧 CPU/LLM）。回指第六章单一写者、第八章幂等。失效根因：把并行写当并行读，冲突决策无声地互相覆盖。设计出场：写路径单点化或显式 reducer 合并；worktree 隔离＋父在 merge 点做唯一收敛。代价：隔离换来执行期零冲突，也换来"没有共享真相"——worktree 里的 child 看不见彼此，一切协调压到父身上，父成瓶颈。
- N6 partial failure 收敛（12.6，兑付欠条三）：一组并行 subagent 有的成功有的失败，结果怎么收敛。LangGraph superstep 事务性（并行分支任一抛异常，则整个 superstep 的 state 更新全不落）＋RetryPolicy 只重试失败分支、重试前清该 task 的 writes（防失败尝试的部分写污染）；Anthropic 同步执行瓶颈（lead 同步等一批 subagent 跑完才继续，慢 subagent 阻塞、无法中途纠偏——半途设计的诚实实证）。缺口：语义级"带部分结果的优雅降级"框架不给、仍是应用层——谁来收敛、收敛成什么、几个成功算够，是父的职责。回指第五章终结原因四类、第八章 unknown 是合法终态。设计出场：父显式定义收敛判据（全成功/多数成功/关键子任务成功）与失败处置（重试/降级/整批放弃）。代价：事务性收敛意味着一个 child 失败可能让整批白跑，要在"整批原子"与"部分交付"之间按任务选，选错一头是浪费一头是脏数据。
- N7 subagent 输出可信度（12.7，兑付欠条四，本章硬核）：主 agent 凭什么信子 agent 的回传——不因它来自"内部"就可信。tool result 是执行方的报告（第八章 result≠outcome），subagent 回传同样是报告、不是外部世界的独立证据。校验层：OpenAI guardrails（input/output，与执行并行跑、tripwire 即断）、Anthropic 独立 citation pass（单独一步校验引用）、Devin verifier agent（专职对齐 spec）、确定性检查（schema/长度/安全过滤，零成本全量兜底）。MAST 验证类失效仍占 23.5%，是独立且被低估的一类。失效根因：把"内部产出"默认当可信，等于第二章"检查器信任被检查者"的多 agent 版。设计出场：subagent 回传默认不可信、经独立校验方采信；校验器与被校验者不共享同一判断源（避免 common-mode，回指第十一章 11.5）。代价：校验是又一次 LLM 调用与成本，全量校验贵、抽样校验漏——判官偏差（高置信错误）与覆盖率之间没有免费解。
- N8 六契约的多 agent 组合（12.8，收口）：逐契约问"父子/并行下怎么继承"——真相（child run 状态挂父、单一真相源不因分身改变）、转移（child 状态机独立但父可观测、terminal 回报父）、副作用（child 的 effect 账挂父链、幂等 key 派生带父 run_id）、交互（child 无直接交互面、progress 经父投影）、权限（取交集收窄）、证据（child 的 trace 以父 run_id 关联、跨 agent 因果链可重建——留第十三章）。结论：多 agent 不新增第七类契约，是六契约的递归应用；本章把"契约沿父链继承"从主张证成规则。
- 验证：破坏实验四场景四步协议（越权 subagent 提权/两 child 并发写同一 artifact/慢 subagent 阻塞整批收敛/恶意 subagent 回传注入结果），实证分层。

- **遗留问题**：契约沿父链继承、并发单点写、子任务独立校验——这些规则怎么证明真的发生了？child run 的 trace 怎么关联父、跨 agent 的因果链断在哪一跳怎么查？证据面，第十三章。

**推理链**：

- N1 朴素做法（13.1）：出了事去翻日志、临时加 print、读对话记录还原现场。失效方式即第三章事故现场——十帧时序全靠事后读代码重构，因为该在热路径写下的事件当时没写；日志是给人读的散文、不是可对账的事实；对话记录是投影、不是真相（第六章）。失效根因：把"给人看的日志"当"可追溯的证据"，证据面从没作为一层被设计出来。设计出场：evidence plane——证据是一层独立平面（第四章五平面的证据面），只装不可争议的事实、只追加、与执行面分离。根基：append-only 事件溯源与单一真相（第六章）。代价：每个关键动作多一次写、存储只涨不删、热路径省不掉这一步——拿"永远多一笔开销"换"出事时讲得清"。
- N2 事实与解释分账（13.2/13.4）：证据五载体——原始 event（append-only 事实、真相）、trajectory（评测视图）、trace（诊断视图）、transcript（完整历史）、metric（聚合），后四种都是从 event 派生的投影。热路径只写事实，解释离线由 reducer 从事件重建——"Observe First, Interpret Later"（业界 rollout-trace 口径）。失效根因：把易错的解释塞进不可回滚的热路径，解释一错就污染了事实。设计出场：写事实与做解释分两条路，事实进 append-only，解释可重算。代价：解释不是实时的、要离线重跑；换来的是解释错了能重来、事实不被动过。
- N3 全量关联链（13.3，兑付第十二章欠条）：correlation 八级——tenant／conversation／run／turn／step／invocation／effect／artifact（conversation 即第六章统一语言实体链顶层，Claude Code 侧称 session）——全量冗余写进每一条事件，允许为空的层显式置空。这正是第十二章那句"child trace 以父 run_id 关联、跨 agent 因果链能拼回来"的兑现：断一级，因果链就断在那一跳——第十二章 infinite handoff loop 之所以查不清谁 own 任务，根子就是 correlation 没贯穿。设计出场：每条事件带全链（工作制品 C 信封字段）。代价：每条事件冗余八个 ID，拿存储换"任意一条事件都能定位到它属于哪个 run 的哪一步"。
- N4 只追加纪律（13.x，工作制品 C 四纪律主场）：append-only 永不 UPDATE，记错了追加 correction.appended 指向原事件、不改历史；粒度到 step／消息完成、不逐 token（token delta 走流式投影、无恢复价值不入账）；append-only≠crash-safe，崩溃按最后一个完整事件截断、丢尾行不算损坏。失效根因：证据一旦能改，就不再是证据——能改的证据等于没有。代价：记错的也留着、再追加更正，历史臃肿换不可抵赖。
- N5 决策与完成的证据（13.5／13.6／13.10，兑付第八/十一章）：policy.decided 记"谁在何时因何规则允许或拒绝"（第十一章权限证据成链）；被拒的写入落 zombie trace（第八章消费处）；artifact lineage 与 verifier evidence（第六/十章）；completion claim 必须连到 outcome evidence——声称完成要有外部世界的独立证据，这是第八章"result≠outcome"在证据层的形态，也是第二章"检查器不能信任被检查者"的又一次现身。失效根因：完成声明不连 outcome，就是拿自述当事实。代价：每个完成都要留取证、慢一步，换"声称完成"与"真的完成"不再混为一谈。
- N6 两类沉默失败（13.8／13.9，本章硬核，收口第二章）：证据面自己会有两种空——其一，absence-of-event，该发生的事件没发生（第一章假落地诊断的证据层形态：机制有名字、trajectory 里没有它的事件），靠声明态与运行态对账查出来；其二，检测器自己失效，报警器坏了不会响。失效根因：没有报警器的报警器——检查证据的东西自己不被检查，是第二章判据自欺在证据面的终极形态。设计出场：absence 检测（期望出现的事件缺席即告警）＋sabotage validation（定期给检测器喂已知坏样本、验证它真的会触发，结果记进检测器测试记录）。代价：要专门测"没发生的事"和"检测器还活着"，是额外一层验证；但这是证据面唯一能自证不空的办法——不测，就永远不知道那层账是真在记还是在装。
- N7 content 是敏感数据（13.7）：证据里的 content——对话、工具输入输出、抓来的网页——默认按敏感数据处理；生产可观测监控的是决策模式与交互结构、不是对话内容（业界隐私口径）；"tracing is not telemetry"，采集深度要单独授权，保留与合规治理移交第三卷。失效根因：证据面为了可诊断，最容易顺手把所有 content 全留下，留成一个隐私地雷。代价：隐私换可观测的深度，细粒度 content 采集要显式授权、按敏感数据管。
- N8 可执行信念的证据边与 Model Certificate（13.11／13.12，Schema Harness/MODA 载体）：对可执行的 Belief/World Model（第六章 6.12），证据面补七条认识论边——observation grounds model、model predicts transition、history certifies model、counterexample refutes model、plan derived_from model、commit realizes plan、mismatch invalidates remaining_plan——回答"系统为什么相信当前模型、什么证据推翻了它"，补在工作制品 X 那四条本卷新立的对账边之上、不另造平行图谱（入门卷 §八那十条边是跨件跨 cell 的可观测关系，与本卷两组互补，非继承）。关键：certifies 必须带 scope——完整历史 backtest 只证 retrodictive consistency（解释了已见样本），不证未见状态上的 generalization；Model Certificate 至少并列记 full-history replay／prospective prediction／held-out／invariant／planner-adversarial 五类测试＋scope／history cursor／生成 provenance（模型／提示／工具版本）／已知反例，不能只写 backtest=green。素材：一个公开 model-based harness 项目的轨迹统计（9 次误预测后均重新建模、提交）证明"预测错即计划失效"是实机制。MODA 五层去语境后作本章闭环载体。代价：建 certificate 是额外工程，只在"可显式建模"的域（状态紧凑、转移大体确定、真实动作昂贵、仿真便宜）值得，不要求每个任务都建 simulator。
- 验证：破坏实验四场景四步协议（吞掉一个错误看 absence 检测报不报／关掉一个检测器看有没有人发现／制造"成功但无 artifact"看 completion-outcome 对账拦不拦／注入历史外的新转移＋一个 planner 会利用的模型漏洞，验证 certificate 不被误当全局正确、counterexample 吊销模型与剩余计划），实证分层。

- **遗留问题**：六契约、五平面、证据面——纸上全推完了，能不能真造出来？从零构造一个最小但完整的 runtime，第十四章。
- **章级判据**：新概念 ≤12（evidence plane、五载体、correlation 八级、Observe First Interpret Later、correction 事件、absence-of-event、sabotage validation、completion-outcome 对账、认识论七边、Model Certificate scope、tracing≠telemetry、MODA 闭环载体）、前向引用 ≤8（第十四/十五＋卷三）、正文表格 ≤3（五载体对照＋correlation 八级＋认识论边，全表住工作制品 C/X）；带走：证据五载体与 correlation 链一图、"证据面只追加＋全量关联链，检测器必须证明自己会触发"一句、"关掉一个检测器、看多久有人发现"一个动作。

## 二十一、§十四 章 spec v1.0（构造章·可运行骨架逐步点亮六契约、标准故障包全绿，随正文 v1.0 同批交审）

**章职责**（对齐问题链 §十四行与 §十三遗留问题）：前十三章把六契约、五平面、证据面在纸上推完了，但没有证明它们合起来能跑。本章从零构造一个最小但完整的 runtime——按依赖顺序逐步点亮六契约，每步给最小数据结构、关键伪代码、一条正常 trajectory、一条失败 trajectory、验证证据。兑付欠条：前面各章累积的九个"第十四章工单"fixture（第五章 contract test、第六章 atomicity、第七章 replay、第八章 reconciliation、第九章 cancel propagation、第十章 compaction、第十一章 permission、第十二章 multi-agent coordination、第十三章 detector/certificate）在此汇编成标准故障包，作为验收 SSOT。接大纲下沉件：部署基线（单机 vs 服务、组件切换信号，自 §一 3.9 下沉）、双层控制流最小实现（node-local loop → 最小 graph workflow，步骤 2，回指第十二章）、可显式建模案例（步骤 10，回指第十三章、第六章 6.12）。

- **输入问题**：最小但完整的 runtime 长什么样？
- **本章主张**：以可运行骨架逐步点亮六契约——构造的顺序不是随意的，是依赖顺序；点亮一份契约的判据不是 happy path 跑通，是它对应的失败 trajectory 被守住；全卷的验收不是"能跑"，是标准故障包全绿。底线交付是一份语言无关的 executable spec，让方法不被某一种实现的进度阻塞。

**推理链**：

- N1 朴素做法（14.1）：把前十三章的机制各自实现、拼到一起，happy path 跑通就算完成。失效方式：各契约单独成立、合起来打架——permission 挂在还没建的 principal 上、resume 读到还没定义版本的 checkpoint、subagent 关联到还没有 correlation 的事件流；集成失败是"部件正确加不出系统正确"（第一章）在构造层的最后一次现身。失效根因：没有把依赖顺序当成构造纪律，也没有把失败 trajectory 当成完成判据。设计出场：按依赖顺序逐步构造，每步交五样（数据结构／伪代码／正常 trajectory／失败 trajectory／验证）。根基：写一个测一个＋破坏一次（全卷破坏实验协议）在构造上的合流。代价：从零走一遍比改现有系统慢，但省掉的是集成期才暴露、最难查的契约打架。
- N2 构造顺序＝依赖顺序（14.2）：十四步按依赖铺——实体／ID／State Registry 先立（一切挂靠点），然后 Execution Kernel＋run 状态机，再 model invocation、tool intent/result/outcome、event stream、cancel/HITL、checkpoint/resume/timer、permission/authority、context/compaction、可建模案例、parent/child、Evidence Plane、meter/limit/version、标准故障包。跳步的失效：任一步依赖前一步的产物，倒置就落空（permission 无 principal、resume 无版本）。设计：依赖拓扑排序，每步只依赖已点亮的契约。代价：顺序被锁死，想先做看得见的功能（工具、UI）得等地基先立——地基不先立，功能就是空中楼阁。
- N3 每步五样与"点亮"判据（14.3）：一份契约算不算点亮，判据是它的失败 trajectory 被守住，不是正常 trajectory 跑通。每步展示最小数据结构（够用就行、不预支灵活性）、关键伪代码、正常 trajectory、失败 trajectory（注入该契约对应的扰动）、验证证据。失效根因：只演正常路径，等于只证明了不出错时能跑、没证明契约。设计：每步配一条失败 trajectory 与判定。代价：每步都要写失败场景、比只写 happy path 多一倍工作——但这一倍正是点亮契约和演示 demo 的分界。
- N4 双层控制流的最小实现（14.4，步骤 2，回指第十二章）：先实现 node-local loop（单 agent 的 tool 循环），再加一个含 branch/join 的最小 graph workflow（跨节点编排）。这是第十二章双层控制流从原则落到骨架——两层都要有，先立自治层、再立编排层。失效：把该自治的一步硬编进图，或把该确定的分派丢给 loop 里的模型自由发挥（层向对齐第十二章 12.2）。代价：最小 graph 也是额外一层实现，单 agent 任务用不上——但没有它，多 agent 就没有骨架挂靠。
- N5 可显式建模案例（14.5，步骤 10，回指第十三章/第六章）：在一个状态紧凑、转移可观察的案例里实现 world model → history replay certificate → search/dry-run → guarded commit → counterexample/replan 闭环。这是第十三章认识论七边、第六章 6.12 信念工件从纸面到可运行的一次落地。关键边界：该路径是显式可建模任务的扩展，不要求所有 agent 任务都构造完整 simulator。代价：建 simulator 是重投入，只在可建模的域值得（第十三章已立此边界）。
- N6 标准故障包＝验收 SSOT（14.6，本章方法论核心）：前十三章每章的破坏实验都留了一个"第十四章工单"fixture，九个 fixture 在此汇编成标准故障包。验收判据从此不是能跑，是标准故障包全绿——每份契约都有对应的故障场景，包全绿才算六契约都被守住。失效根因：拿 happy path 当验收，是全卷开篇批评的"能跑就不要动"在构造层的复发。设计：标准故障包作为 executable spec 与 reference implementation 共用的验收套件。代价：维护一套故障包是持续成本，但它是这套 runtime 真的守住了六契约的唯一可复算证据。
- N7 交付物分层（14.7）：底线交付是一份语言无关的 executable spec——数据结构、状态转移、事件 schema、故障包判定，可被任意语言实现；加分交付是一个可运行参考实现。分层的理由：方法（spec）可迁移、不被某一种实现的进度阻塞；实现是加分的验证、不是方法本身。第三卷接口清单以 executable spec 为准。代价：写一份严谨的语言无关 spec 比直接写代码更费神——换来的是方法不绑定实现、可被任何团队照着造。
- N8 部署基线与切换信号（14.8，自 §一 3.9 下沉）：先立单机基线（SQLite、单例、进程内任务／广播），再给多实例迁移的切换信号——SQLite→Postgres（多写者／备份不够用）、单例→分布式锁或 lease（多实例）、进程内任务→worker queue、进程内广播→事件总线。逻辑架构不变，只按信号换组件。代价：单机基线看着像玩具，但它是把逻辑架构和部署形态解耦的前提——先证明逻辑对，再谈规模。
- 验证：本章的破坏实验就是标准故障包本身——九个 fixture 逐一跑（实证分层：哪些是 executable spec 的判定、哪些有 reference implementation 实跑）。

- **遗留问题**：能从零造出来了——可现实里更多时候是拿到一个已经在跑、来历不明的系统。怎么审它？Runtime 架构评审，第十五章。
- **章级判据**：新概念 ≤10（可运行骨架、依赖顺序构造、五样、点亮判据＝失败 trajectory、最小 graph workflow、标准故障包、executable spec vs reference impl、部署基线与切换信号）、前向引用 ≤6（第十五章＋卷三）、正文表格 ≤3（十四步构造序＋标准故障包 fixture×契约映射＋部署切换信号，必占两张）；带走：十四步构造序与标准故障包一图、"点亮契约看失败 trajectory 不看 happy path，验收看故障包全绿"一句、"给系统跑一遍某个故障 fixture、看它绿不绿"一个动作。
- **交付物**：语言无关 executable spec（底线，数据结构/转移/事件 schema/故障包判定）；可运行参考实现（加分）；标准故障包（九 fixture×契约映射，正文表，验收 SSOT、第十五章评审取用）。
- **验收清单**：同 §八 口径（老师声部;STAR＋指向;文字化引用零 §;工作制品引用带名称——本章大量回指 A-Z 全套;业界对照 ≥1 家带失效点——checkpoint 框架只给存档点不给失败检测/恢复触发/跨实例协调，回指第七章 Diagrid 批评与选型信号;破坏实验＝标准故障包＋实证分层;L 级自检＋坐标系落位;双读者动作;R1 红线;四维评审四路 opus）。
- **边界（本章不讲）**：评审现存系统的清单（第十五章）、生产运维/SLO/成本/安全治理（第三卷）、具体语言的实现细节（executable spec 语言无关、参考实现是加分不展开）、prospective/held-out 测试测量学（第三卷）。

## 二十二、§十五 章 spec v1.0（评审章·卷级出口：拿登记表逐项提问、产出残余风险清单不是判决，随正文 v1.0 同批交审）

**章职责**（对齐问题链 §十五行与 §十四遗留问题）：第十四章从零造出一套 runtime，可现实里更多是接手既成系统。本章把全卷方法压缩成一套能带走的评审工具——五件工具、一个 90 分钟流程、两条文化判定线，用来在有限时间里审出任何既成系统的残余风险。本章是卷级出口，也是双读者里 assessor 近道的终点，收束全卷。五件工具全部复用前面章节的工作制品（Component Register＝工作制品 G、State Registry＝A、Effect Ledger＝B、Runtime Trust Boundary＝D、Runtime Contract Matrix＝六契约×五审查维度），破坏实验那一步取第十四章标准故障包，不新增 A-Z 工作制品。

- **输入问题**：现存系统怎么评审？
- **本章主张**：评审不是给一个通过/不通过的判决，是拿全卷的登记表（工作制品）对被评系统逐项提问，产出一张有 owner 的残余风险清单——每条风险落到哪份契约、哪个场景、谁负责、什么时候补。评审的终极问题只有一句：这个 runtime 知不知道自己发生了什么。

**推理链**：

- N1 朴素做法（15.1）：评审一个既成系统＝通读代码、问架构师、看它跑得稳不稳，给一个"能用／不能用"的结论。失效方式：代码读不完，架构师的叙述是投影不是真相（第六章），"跑得稳"只是 happy path 的观察（第十四章）；给出通过/不通过，把一堆"通过但有已知残余风险"压成一个二元判决。失效根因：把评审当成门禁（gate），而评审真正的产出是"哪些契约没守住、谁负责补"。设计出场：评审＝拿全卷登记表逐项提问，产出有 owner 的残余风险清单。根基：全卷的六契约＋工作制品＝现成的提问清单。代价：逐项提问比"看一眼给结论"慢，但省掉的是被二元判决掩盖、事后才炸的结构性风险。
- N2 五件工具＝前面章节登记表的评审用法（15.2）：Component Register（工作制品 G，§四）逐张对位被评系统自画的组件图、对不上即标红，用在流程第一步；State Registry（工作制品 A）问状态的 owner/存储/版本/读写者；Effect Ledger（工作制品 B）问副作用的意图/权限/执行/幂等/outcome/调和；Runtime Trust Boundary（工作制品 D）问进程/网络/身份/工具/信任边界；Runtime Contract Matrix（六契约×正确性/可靠性/安全/用户反馈/可测试性）问契约承诺。五件不是新发明，是全卷工作制品的评审形态。13×13 机制矩阵留作"热点交叉发现表"、不要求填满，三元交叉/用户行为/时间漂移用场景卡另列。代价：被评系统得拿得出对应的登记——拿不出本身就是第一个发现。
- N3 90 分钟流程八步（15.3）：对组件图→画边界→登记状态→登记副作用→检查六契约承诺→选高风险场景→指定破坏实验（取第十四章标准故障包）→明确残余风险及第三卷 owner。首步系 2026-07-26 用户裁决补入：Component Register 原只在 15.2 被称"开场标尺"、七步里没有对应步骤，配图逼出这个正文缺口，裁决为"七步补一步"而非"15.3 加一句说明"。时间盒是设计：评审不是无限深挖，是在有限时间里定位结构性风险。代价：90 分钟只到结构层，深挖留给后续；换来的是评审可复制、可安排，不依赖一个专家的灵光。
- N4 产出是残余风险清单＋owner，不是判决（15.4，本章方法论核心）：评审的价值不在判决，在把隐性风险显性化并指派 owner——每条残余风险记清哪份契约、哪个场景、谁负责、何时补，直接成为第三卷生产化的起点。失效根因：通过/不通过是二元判决，掩盖了"通过但有 N 个已知残余风险"。设计：残余风险清单模板（契约/场景/owner/期限）。代价：清单比判决难消化、要有人认领，但只有它是可行动的。
- N5 两条文化判定线（15.5，超越技术清单，§一反格言操作化）：技术清单查不出的两件事——其一，framework 思维还是 harness 思维：团队是把 harness 当"接个框架就行"，还是当"得自己守六契约的运行时"；其二，敢不敢动自己的 core：看该团队最近一次对 core 的测试/调优/局部重构发生在什么时候、有没有配套测量数据。停在"第一天智能水平"、只在外围打补丁的系统，按高残余风险记。这是第一章 1.3 节那条反格言（"能跑"不再是"不动"的理由；敢动的前提是检验体系）在评审场景的操作化。代价：这两条靠访谈与历史、不如登记表硬，但它们预测的是系统会不会持续退化——比任何一次快照都重要。
- N6 收束（15.6，卷终）：模型可以不确定，runtime 不能不知道自己发生了什么。这是全卷压成的一句话——不确定性是模型的本质，但 runtime 的职责是让不确定性之外的一切（状态、副作用、权限、证据）都可知、可查、可复算。评审的终极问题，就是这一句：这个 runtime 知不知道自己发生了什么。回扣全卷：六契约是"要知道什么"，检验坐标系是"怎么确认知道了"，假落地诊断是"以为知道其实不知道"，本章是"拿这套去审别人的系统"。
- 验证：本章的破坏实验＝用五件工具＋90 分钟流程审一个真实系统，产出一张残余风险清单示例（实证分层：哪些是真审出来的、哪些是流程示范）。

- **遗留问题**：（卷终）残余风险清单的每个 owner 落到生产化、运维、安全、成本治理——那是第三卷。
- **章级判据**：新概念 ≤8（评审即逐项提问、五件工具、热点交叉发现表、90 分钟八步流程、残余风险清单、两条文化判定线、harness vs framework 思维、敢不敢动 core）、前向引用 ≤6（第三卷）、正文表格 ≤3（五件工具＋Runtime Contract Matrix＋90 分钟流程/残余风险清单模板，必占两张）；带走：五件工具与 90 分钟流程一图、"评审产出是残余风险清单不是判决；模型可以不确定，runtime 不能不知道自己发生了什么"一句、"拿五件工具审自己的系统一次"一个动作。
