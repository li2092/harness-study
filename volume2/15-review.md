# 十五、Runtime 架构评审

> v1.0 · 2026-07-24 · 依据 SPEC.md §二十二 章 spec（评审章·卷级出口：评审＝拿登记表逐项提问、产出残余风险清单＋owner 非判决＋五件工具复用工作制品 G/A/B/D＋Runtime Contract Matrix＋90 分钟七步流程＋两条文化判定线＋收束回扣全卷）· 四维评审四路已落实，待用户审
> （本版本注与"审稿日志""引用来源"两节同属编辑工作区，出版前整体删除。）

第十四章教的是从零造一套 runtime。可拿到手的系统，十有八九是接手来的：别人造的，在线上跑着，没人说得全它守没守住哪几份契约。全卷走到这里，该把前十四章压成一件能带走的东西：一套评审法，用来在九十分钟里，审出任何一个既成系统的残余风险。

主张先立：评审不发"通过还是不通过"的判决。它拿全卷的登记表，对着被评系统逐项提问，产出一张有 owner 的残余风险清单——每条风险落到哪份契约、哪个场景、谁负责、什么时候补。而所有提问最后收敛成一句，也是这一卷的收束：模型可以不确定，runtime 不能不知道自己发生了什么。读完本章，手里应当多五件评审工具、一个九十分钟流程、一张残余风险清单模板。

## 15.1 评审是一次逐项提问

先纠一个最常见的评审姿势。

拿到一个既成系统，最朴素的评审是：通读代码、找架构师问一圈、看它跑得稳不稳，最后给一句"能用"或"不能用"。三处都靠不住——代码读不完，只能抽样；架构师讲的是他脑子里的系统，那是一层投影，隔着线上真相还有一层——第六章那条"投影可以错、真相只有一份"，套在人脑这份投影上一样成立；"跑得稳"是 happy path 的观察，故障下守不守得住，看一眼看不出来（第十四章立过这条）。而最伤的是那句结论本身：一个"能用"，把系统里一堆"能用、但有已知残余风险"的真实状态，压成了一个二元判决。

失效根因是把评审当成了门禁——过还是不过。可评审真正该产出的，是"哪些契约没守住、谁负责补"。所以设计上换一套做法：评审是拿全卷那套登记表，对被评系统逐项提问，产出一张有 owner 的残余风险清单。它的根基现成——六契约是要问的问题，前面各章的工作制品是问题的清单格式。代价是逐项提问比"看一眼给个结论"慢，一次要占足九十分钟；但省掉的，是被那句二元判决盖住、上线之后才兑现成事故的结构性风险。

## 15.2 五件工具：全卷登记表的评审用法

逐项提问，得有清单。五件工具就是全卷工作制品的评审形态，每一件问一类问题：

| 工具 | 出处 | 评审时逐项问 | 对不上意味着 |
|---|---|---|---|
| Component Register（工作制品 G） | 第四章 | 八张组件卡逐张对位被评系统自画的组件图 | 缺了哪个组件、哪份契约没人守——开场标尺 |
| State Registry（工作制品 A） | 第六章 | 每个状态的 owner／存储／版本／读写者 | 状态无主、多写者互相覆盖、无版本可回滚 |
| Effect Ledger（工作制品 B） | 第八章 | 每个副作用的意图／权限／执行／幂等／outcome／调和 | 副作用没账、没幂等、拿 result 当 outcome |
| Runtime Trust Boundary（工作制品 D） | 第十一章 | 进程／网络／身份／工具／信任边界怎么跨、怎么对账 | 边界糊、软提示当硬边界用 |
| Runtime Contract Matrix | 六契约横轴承自第一章（六契约立于 1.2 节）；五审查维度是本章新起的评审镜 | 六契约 × 正确性／可靠性／安全／用户反馈／可测试性 | 哪一格空着、哪份契约根本没有检验 |

第一件是开场标尺：拿第四章那八张组件卡，逐张去对被评系统自己画的组件图，对不上的地方当场标红——少一个组件，往往就少一份没人认领的契约。最后一件是收口尺：Runtime Contract Matrix 把六契约摆成横轴、把正确性/可靠性/安全/用户反馈/可测试性摆成纵轴，每一格问"这份契约的这个维度，靠什么保证"。六契约横轴是第一章检验矩阵的原轴，五审查维度则是评审专用的一层新镜——把第一章那套四问坐标系，换成审别人系统时更顺手的五个追问面。这张表不要求当场填满三十格，空着的格子本身就是发现。中间三件（State Registry、Effect Ledger、Runtime Trust Boundary）是三本账，问的是状态、副作用、边界这三样最容易糊的东西各自记清了没有。至于本卷附录里那张 13×13 机制矩阵，评审时留作"热点交叉发现表"，专挑几个高风险交叉看，不要求填满；三元交叉、用户行为、时间漂移这类跨维风险，用场景卡另外列。

这五件工具有个前提——被评系统得拿得出对应的登记。拿不出，恰恰是第一个、也往往是最大的发现：一个连状态 owner 都列不出的系统，谈不上守住真相契约。更硬的代价在覆盖面：把那张 13×13 机制矩阵和整套 A–Z 工作制品，压成这五件单维登记，是拿"查得全"换"九十分钟跑得完"——三元交叉、用户行为耦合、时间漂移这类跨维风险，五件工具逐件都照不到，只能靠热点交叉发现表和场景卡另补。评审者要记住这层系统性盲区，别把"五件都对上"读成"全查过"。

## 15.3 九十分钟，七步走完

工具备齐，还缺一个能安排、能复制的流程——评审得能排进日程、靠一套固定步骤走完，不依赖一个专家的临场灵光。九十分钟，七步：

1. **画边界**——先用 Runtime Trust Boundary 把进程、网络、身份、工具、信任边界画出来，圈定评审范围；
2. **登记状态**——用 State Registry 把关键状态的 owner、存储、版本过一遍；
3. **登记副作用**——用 Effect Ledger 把高风险副作用的账法过一遍；
4. **检查六契约承诺**——拿 Runtime Contract Matrix 逐格问契约守没守；
5. **选高风险场景**——从对不上的格子里，挑两三个最可能出事的场景；
6. **指定破坏实验**——给选中的场景，从第十四章标准故障包里挑对应的 fixture，当场设计怎么破坏、怎么判定；
7. **明确残余风险及 owner**——把审出来的每条风险，连同负责人和期限，落进残余风险清单。

时间盒是有意的：九十分钟只够到结构层，够定位"哪几份契约有结构性风险"，不够深挖每一个 bug。深挖是后续的事。代价是这套流程审不出实现细节里的小错，那些得靠测试和第十四章的标准故障包实跑去兜；但它换来的是评审可复制、可排进日程，不必等一个稀缺专家有空。

## 15.4 产出是一张有 owner 的残余风险清单

评审的价值，全压在最后一步的产出物上。

它产出的不是判决，是一张残余风险清单——每条风险记清四样：踩的是哪份契约、在哪个场景下暴露、谁负责补、什么时候补。

| 残余风险 | 契约 | 触发场景 | owner | 期限 |
|---|---|---|---|---|
| 工具超时后重试，远端已成功 | 副作用 | reconciliation fixture | （第三卷 owner） | — |
| subagent 继承父的全放行 | 权限 | permission fixture | （第三卷 owner） | — |
| 某检测器从未验证过会触发 | 证据 | detector/certificate fixture | （第三卷 owner） | — |

15.1 已说过二元判决抹掉了 N；这一步补另一半，也顺带回一个真问题——上不上线终究要有人拍板，清单是不是取消了拍板？没有。它换掉的是拍板时的盲：一句"通过"让人闭着眼发车，一张挂了 owner、带了期限的清单，让同一个发车决定睁着眼做——N 条风险摆在桌上，谁签字谁认这 N 条。清单直接成为第三卷生产化的起点。代价是它比一句"通过"难消化，还得有人真的认领每一条；而一张没有 owner 的清单，和"通过"其实一样，只是把风险留在原地，区别不过是多列了一张更长的单子给自己看。

## 15.5 两条查不出来的线：harness 思维，敢不敢动 core

前面五件工具查的都是系统里有什么。可有两件最能预测系统未来的事，任何登记表都查不出来——它们藏在团队的做法里。

第一条：这个团队是 framework 思维，还是 harness 思维？framework 思维把可靠性当成"接一个框架就有了"的现成品；harness 思维知道六契约得自己一份份守，框架只是给了几块料。一个把 durable execution 框架接上就以为万事大吉、从不自己对账的团队，评审时要按高风险记。第七章引过一条竞争方厂商的批评（利益相关、非中立结论）：这类框架只给存档点，失败检测、恢复触发、跨实例协调三件留给使用者自接。出处之争先放一边，评审真正要当场问的是这一句——这三件，是框架替这个团队做了，还是它自己有代码对账？答"框架都管了"的按高风险记。

第二条，也是更重的一条：这个团队敢不敢动自己的 core？看它最近一次对核心的测试、调优、局部重构发生在什么时候，有没有留下配套的测量数据。这是第一章 1.3 节那条反格言的操作化——"能跑"在 agent 时代不再是"不动"的理由，敢动的前提是有一套检验体系兜底。一个停在"第一天智能水平"、只敢在外围打补丁、碰都不敢碰 core 的系统，无论当下跑得多稳，都要按高残余风险记：它只会随模型和需求的漂移慢慢退化，当下跑得再稳也拦不住。

代价是这两条靠访谈和历史记录，不像登记表那么硬、那么可复算；但它们预测的，是这套系统会不会持续退化——比任何一次快照都重要。评审要是只查了登记表、漏了这两条，等于只给系统拍了张快照，没问它往后会不会退化。

## 15.6 收束：模型可以不确定，runtime 不能不知道自己发生了什么

全卷十五章，到这里收成一句话：**模型可以不确定，runtime 不能不知道自己发生了什么。**

不确定性是模型的本质，逼它确定既不可能、也不必要。但 runtime 的职责，是让不确定性之外的一切——状态在哪、副作用发没发生、谁批的权限、留没留证据——都可知、可查、可复算。这一卷的每一章，都是这句话的一个切面：六契约是"要知道哪几样"，检验坐标系是"怎么确认真知道了"，假落地诊断是"以为知道、其实不知道"的那道暗门，而本章，是拿这整套眼光去审别人的系统。这也是检验坐标系在全卷的最后一次转手：前十四章它是建设者手里的尺，量的是自己造的系统做没做对；到本章它换进评审者手里，去量任何一套接手来的既成系统。尺没变，握尺的人从造者变成了审者。

所以评审到最后，无论查了多少格、列了多长的清单，都收敛到同一个问题上：这个 runtime，知不知道自己发生了什么？答得出，它就守得住；答不出，剩下的都是运气。

## 破坏实验：审一个真实系统

本章的破坏实验是一套可执行规格、外部复跑待补：拿五件工具＋九十分钟流程去审一个真实系统，看它产不产得出一张站得住的残余风险清单。

判定口径：通过＝七步走完、每步都从对应工作制品问出至少一条可落 owner 的残余风险，清单每条挂得上契约与场景；失败＝审完只给出一句"能用/不能用"，或残余风险没有 owner、没有期限、挂不到具体契约。

实证状态照实分层【经验】：本流程属思想实验层的可执行规格——七步、五件工具、判定口径都写明，可照着走；第三章那次九路内部摸底在形态上与本流程同构——先摸底不动刀、逐项对照、产出带修复项的清单，是本流程的现实近亲；但把它规整成"五件工具＋九十分钟＋残余风险清单"这套标准形态、并在外部系统上复跑，是本章的待补项，照实记，不粉饰成"已在多个系统上跑通"。

## L 级自检

按第一章的成熟度尺（L1 能跑、L2 能看，全表见第一章 1.3 节）。评审这件事本身也要过这把尺：一次评审算不算数，判据是它有没有落成一张可复算的清单——有名字、有 owner、有契约归属（L2 能看）；只停在参与者脑子里的印象，连 L1 都不算。套第一章那条假落地诊断的评审版：一个团队声称"每季度做架构评审"（有名字），可拿不出上一次评审的残余风险清单和 owner 落实记录（无证据），这套评审就按未接线嫌疑处理——评审自己也会假落地。

四问落位：本章是全卷检验坐标系的终极应用——可观测对应五件工具把系统摊开、可控对应残余风险清单挂 owner、稳定对应指定破坏实验、闭环对应"审出风险→落 owner→第三卷补→回审"这条跨卷的环；但这条环眼下只画到设计、一圈都还没闭合过——回审依赖尚不存在的第三卷生产化，本章交的是环的前半段规格，不是一条跑通过的闭环。坐标系落位补一句：前十四章立的是"怎么把一套 runtime 做对、并知道它做对了"，本章立的是"拿这套眼光去审任何一套既成 runtime"，检验坐标系这次从建设者的尺转到评审者的尺（收束段已展开）。这套评审法的现状照实记账：五件工具与九十分钟流程作为可执行规格已成形（L1），但标准形态在外部系统上的复跑、残余风险清单模板的沉淀都还没接齐（L2 缺），不粉饰成半格；实战打磨与第三卷的生产化治理同步展开。

## 立即可做的一个动作（五分钟）

builder 版本：拿五件工具里最简单的 State Registry，只做一件事——把自己系统里叫得出名字的关键状态列出来，逐个填 owner、存储、版本。填不满的那几行，就是真相契约上的残余风险，当场记下来、挂个负责人。五分钟填不完，说明状态归属这一格，比想象中糊。

assessor 版本：问被评团队两个问题——"你们最近一次改动 core 本身、给它做过测试或重构，是什么时候？改完有没有测量数据证明它变好了？"两个都答不上来的，按本章两条判定线的第二条记：这套系统停在了第一天的智能水平，是记在账上的高残余风险。
