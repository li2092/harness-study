第五章交出了转移表，也留下四个没答的问题：每笔转移要落的事件，记在哪张表里？谁有权写它？状态行与事件序列不一致时，以谁为准？还有那条被抢占的半轮消息，究竟挂在哪个载体上。四个问题其实是同一个问题——状态的归属。

先把这个问题放回它最日常的形态。设想评审桌上有人问："进程重启之后，用户刚发的那条消息还在吗？"三个工程师给出三个答案。前端说在——界面状态里明明显示着；后端说在——run 的上下文里拿得到；数据库说不在——落库点还没走到。三个人都没说错，系统错了。第三章解剖的那次数据丢失事故已经演过这场对话的事故版：一条消息从键盘到磁盘途经五个载体、前四个易失，"消息在吗"的答案取决于问的是哪个载体。病根在语言之前就埋下了：每个人嘴里的"消息"指着不同的东西，而系统从没规定过哪份算数、每样东西叫什么。

所以本章先做全卷欠着的一件事：冻结统一语言——六级实体链、十一张表、四条全局规则——然后回答"哪份算数"。答案压成一句，也是本章的主张：**context 是投影，不是真相**。持久状态是唯一真相源；context 是一次模型调用的有损读投影，界面是给人看的另一种投影。投影可以丢、可以错、可以重建；真相必须唯一，必须活到最后。读完本章，手里应当多四样东西：一条实体链、一份 State Registry v2、一纸投影契约、一张三生命周期矩阵。

## 6.0 统一语言：六级实体链与四条全局规则

对话产品的直觉词汇只有两个："会话"和"消息"。这两个词撑不住一个运行时——第五章整章讲的 run 在这套词汇里没有位置，第八章要对账的工具执行更没有。运行时的实体链有六级，每一级都由一类必须区分的东西逼出来：

| 级 | 实体 | 一句定义 | 关键裁决 |
|---|---|---|---|
| 1 | Conversation | 用户视角的持续对话，消息的归属容器 | 可以没有——scheduler/webhook 触发的 run 不挂会话 |
| 2 | Run | 一次触发到终态的执行（第五章的主角） | subagent 归为 child run（parent_run_id），非独立实体 |
| 3 | Turn | 一次用户意图之内的完整交互回合 | 不设独立表——messages/steps 上的 turn_no 单调递增 |
| 4 | Step | 一次模型决策及其工具结果的闭环 | 恢复粒度锚点：从最后完整 step 之后继续（第七章） |
| 5a | Invocation | 一次真实发生的模型调用 | 每次调用一行，失败的调用也留档——invocation 即 attempt |
| 5b | Tool Execution | 一次工具副作用（Effect Ledger 一行） | 重试记在 attempt_no 上，不另立实体 |

![](figures/t1-layered-6.0-entity-chain.png)

*图 6.0 · 六级实体链：全卷共用的一份词表*

第五级的两条裁决合起来是一项结构决定，来路要交代。本卷的桌面案例项目在后续一轮内部工程审计里，把统一状态链写成 Task→Run→Step→Attempt→Action——attempt 承载同一步的多次网络或模型尝试，立的约束是失败尝试的输出不得混入下一次尝试【经验，桌面案例项目内部审计，2026-07】。这条约束本卷全盘接受，承载方式不同：模型侧每次真实调用记一行 invocation，失败的调用也成行，序号与状态就是尝试的账；工具侧由 Effect Ledger 的 attempt_no 承载，"尝试可多次、结果只记一次"在工作制品 B 里早已是不变量——记账在 invocation，"失败输出不混入下一尝试"的执行约束则由 step 域的 context 组装承载。

独立的 Attempt 实体是多层共享重试预算系统的产物。那份审计所在的系统正是这种结构——中继层重试十一次、agent 层再重试三次，没有 attempt 实体就无法跨层对账；单机参考实现的重试层级撑不起这个登记成本，所以同一条约束、两种承载。推翻条件写明在案：出现跨层共享 retry budget 的需求时，attempt 升独立实体。

还有一样东西刻意不在链上：执行权。第五章 5.7 节的租约、第八章将展开的副作用许可，都是授权对象——它们答"谁现在有权动手"，实体链答的是"发生过什么、归谁所有"，两本分开记的账。分层的判准是账目归属：持久与否只是实现属性——单机阶段租约驻内存、重启即失效；多实例阶段租约降为协议保证，连同 fencing 编号的高水位一起落进授权账的持久存储——那仍是授权账的内部事务，不进 run 的七状态，也不进 State Registry 的实体链。分层的代价直说：要同时追两条线，授权账的生效、停止中、已收回，与 run 的七状态，谁也不映射谁。推翻条件同样写明：一旦需要对执行权的授予与收回做完整历史审计，授权就不再只是账内事务，届时在 Registry 另立一行。这条分层第八章会拿桌面案例项目的一次工程改造说透，fencing 高水位落在状态层的哪一处也在那里交代。

六级实体落成十一张表：conversations、runs、messages、steps、invocations、effects、checkpoints、artifacts、approvals、timers、events——全表与逐行归属住工作制品 A（State Registry，状态注册表）。数目背后还有三条"不设表"的裁决：turn 不设，字段承载；compaction 摘要暂作 messages 特型行，是否独立成表由第十章裁决；policy decision 并入 events，是否独立由第十一章裁决。表可以少，归属不能糊：Registry 每行都要答满四列——谁是唯一写者、谁在读、删除意味着什么、进程在写它半路被杀之后它处于什么状态。

最后是四条全局规则，全部持久对象一体适用。第一，ID 与顺序：每行带前缀 ID，顺序的真相是数据库自增序号，不信 ID 里的时间戳——拿毫秒时间戳当序号的碰撞，第三章的复审续集里真实出过事故。第二，owner：每行有唯一写者组件，第一章的单写者纪律落到行级。第三，correlation：除顶层（conversation）外每行携带完整父链外键，允许为空的层级显式置空——event 行以全量冗余的关联链承载（工作制品 C，Event Schema）——一行数据能顺着链爬回它的 run 与会话。第四，version：每行带 schema_version——第五章给状态机立的版本规则是它的特例，这里全局化：读旧行先看版本，迁移显式做、落事件。

State Registry v1 至此交付（工作制品 A），本章末尾随信念工件升 v2。这一节手里多了全卷的名词表：从此"消息在吗"这类问题，先问的是"哪一级、哪张表、哪个 scope"。开场那条被抢占的半轮消息也有了答案：messages 表里的一行，run_id 加 turn_no 定位——它当初的"消失"，只因为它只活在内存投影里，从未落到自己的载体上（6.3 节）。

## 6.1 真相的载体：两种极端之间

名词定了，看真相怎么存。只存当前态的失效第五章 5.1 节演过：状态行就地更新，库里只有现在、没有来路，排障与恢复都无从下手——那里的解法是把散落的 UPDATE 收进转移表，每笔转移随行落事件。往另一头走到底，是纯粹形态的事件溯源：当前态一概不存，全部状态靠重放事件导出。对 agent runtime 这是过度设计：工具副作用是外部世界的改变，重放内存事件重建不出磁盘上的文件。事件溯源的经典论述也说了用它得图个回报——审计日志、可停可倒带的重放式排障，是最常被点到的两样。但它真正的提醒是反方向的：这套账本极难事后补装到当初没按它建的系统上，所以但凡日后有合理可能用得着，就该现在建，别留给以后重构【规范/官方文档，Fowler，Event Sourcing，When to Use It 节】。

本卷落在两端之间的双轨上：状态行答"现在是什么"，事件表答"怎么来的"——第五章的转移表正是双轨的第一个用户。上面那条提醒本卷接下了：事件表从第一天起就是权威账本。按 Fowler 自己的分法，这条双轨仍在事件溯源门内——他另设 Application State Storage 一节，说存下当前态只是加速手段，权威记录选事件日志还是选当前态由建系统的人定；本卷躲开的只是纯粹形态那一条，事件 schema 版本化的成本（6.0 节第四条）照付。双轨引出一条必须先立的仲裁规则：状态行与事件序列不一致时，以事件序列重建为准。工作制品 B 给 effect 立过这条（不变量五），本章把它升为全局：事件是账本，状态行是余额；对不上时重算余额，不改账本。这条仲裁只裁逻辑不一致；事件表自身的物理完整性是另一回事，由数据库文件层与备份担保，下一段交代。

事务边界一句话：一个逻辑操作一个事务——run 记录与 run.created 同事务落地，消息与 message.appended 同事务落地。再往下的崩溃一致性交给数据库文件层，应用层守两件事：事务边界，和写的顺序。文件层的坑第二章 2.3 节演过——备份只拷主库文件、不带 WAL 边车，最近的写入静默丢失——本章不重讲，只指认它属于"文件层的契约也要读完"这一类。双轨与仲裁立完，第一章那份真相契约（状态可归属）就从承诺句落成了表结构——本章通篇做的正是这份契约的登记形态。

## 6.2 状态分五类，作用域也是归属

十一张表里住着五类性格不同的状态：业务状态（任务定义、评审结论）、运行状态（run、step、effect）、对话状态（messages）、工作记忆（notes、memory——可错、可丢、可重建）、artifact（工作成果）。分类的依据是三样东西都不同：写者不同、生命周期不同、删除语义不同。混住的失效第二章的摸底给过标本：运行状态装进全局单例、不按会话隔离，切换会话就串台【经验】。

归属还有一个维度容易漏：作用域。同一份状态，活在会话范围、项目范围还是全局范围，行为天差地别。反例来自桌面案例项目后续一轮代码复核：技能激活状态的注释声称按会话隔离，实现却按项目路径缓存，激活状态跨会话共享，一个会话开的技能在另一个会话里静默生效【经验】。注释与实现分叉是第二章点过的隐式假设三形态之一，这里的教训更进一步：scope 是登记项，进 Registry 的行，与 owner 并列——"这份状态活在哪个范围"要能核对，不能靠注释自述。

## 6.3 context 是投影，界面是另一种投影

第一章的九步时序有一步刻意不落盘：步 4，agent loop 组装 context。现在能把理由说全了。context 是从持久状态组装出来的**读投影**：从消息、摘要、记忆各取一部分，按预算拼给这一次模型调用——有损（装不下全部历史）、瞬时（下一次调用重新组装）、可重建（丢了不心疼）。界面同理，是给人看的另一种投影；第一章 1.6 节的破坏实验给它立过判定口径：投影不回写。

投影的完整契约三条，交付为工作制品 J（Projection Contract，投影契约）。**有来源**：投影的每个成分都能指回某个持久对象——组装是选材，不是创作。**可重建**：任何投影都能从持久态再生，不携带独家信息——独家信息一旦住进投影，投影就升格成了没人认领的真相源，agent loop 内存里攒半轮成果正是这条的违约形态（第一章立的"内存即易失"约束，从这里看就是投影契约的第二条）。**不回写**：投影侧的任何聪明——缓存、猜测、超时标记——不得进入真相；违约现场第一章 1.6 节与第三章缺口二都放过。三条齐了，"哪份算数"才算答完：真相一份，投影任意多份，多出来的每一份"真相"都是未来的事故。

## 6.4 完整历史与三种视图

投影答了"这一次给模型看什么"，还剩历史本身怎么放。历史一直增长，窗口始终有限，完整历史与模型视图必然分家——分家之后各自要有名字，混叫会修错层。**transcript**（也作 rollout）：append-mostly 的完整历史，审计与恢复的底账。**trajectory**：面向评测与证据的视图，带判定锚点。**trace**：面向诊断的视图。三者同源，是同一串事件的不同投影——入门卷的 trajectory 部件在本卷拆成事件流与证据存储（第四章的接线段交代过），这里补的是读法上的分离：模型不必每次看见完整历史，但完整历史必须存在。这条分离是压缩合法性的前提——压缩改的是视图，历史原封不动，6.6 节展开。

## 6.5 checkpoint 保存什么、明确不保存什么

恢复要有锚点，锚点就是 checkpoint。对它的朴素想象是"把一切存下来"；一切存不下来，因为有几样东西根本不归数据库管。清单直接给：

| 保存 | 明确不保存（及理由） |
|---|---|
| 消息游标、最后完整 step 序号 | 文件系统与外部副作用——另有账本（第八章），回滚是另一件事 |
| compaction 版本与摘要引用 | 授权——approval、delegation 不随 checkpoint 走，安全默认不隐式恢复（6.11 节） |
| state_machine_version 等版本钉 | 模型内部状态——不可得，invocation 记录代之 |
| 包含物清单本身 | ——每个 checkpoint 自述包含什么；不完整的 checkpoint 必须可识别、必须丢弃 |

业界有一套值得端详的产品契约。Anthropic 的 Agent SDK 把"状态存哪、怎么恢复"写成了文档：session 以 jsonl 追加落盘，continue、resume、fork 三种恢复语义齐备；官方一句定性把边界划得很诚实——"session 持久化的是对话，不是文件系统"【规范/官方文档，Agent SDK 文档 2026-07 版】。

契约诚实，缝也真实，两条。其一，session 按工作目录编码存储，换个目录 resume，得到的是一个空会话——"哪份状态算数"带着一把隐式的环境钥匙；契约没坏，踩上的人却以为状态丢了。隐式键是投影契约"有来源"的边界情形：来源里藏着没写进文档标题的条件。其二，文件改动另有一套独立 checkpoint，且明说只追踪经编辑工具的改动——经 shell 命令写下的文件不被捕获，文件回滚也不回滚对话【规范/官方文档，同上】。两套 checkpoint 各自诚实，缝在中间：对话状态与文件系统状态是两本账，恢复时各查各的。这道缝是 6.9 节那条根本限制在产品层的现身，与这家产品的实现质量无关。

## 6.6 压缩边界：改视图，不改历史

窗口逼近上限，压缩必须发生——机制与策略是第十章的主场，本章只立两条边界性质，因为它们属于"状态的归属"。第一，压缩改变的是下一次 invocation 看见的视图，不反向覆盖完整历史：transcript 里原文还在，摘要是新增的行，随行登记 provenance——由哪些消息压成、边界落在哪个序号。第二，读时投影：组装 context 时按登记的 compaction 边界取"摘要＋边界之后的原文"，边界是记录在案的序号；resume 时必须尊重压缩版本，读到旧边界的恢复会把压缩前的全量历史重新交给模型——这条规则的完整形态在第十章。

## 6.7 配对不变量与半压缩禁令

模型视图里有一对必须成双出现的东西：tool_call 与 tool_result。孤儿 tool_call 会直接触发模型 API 报错——这是少数"违约会当场炸"的不变量，但炸点在下一次调用，写坏的那一刻是无声的。两个失效现场。压缩压掉一半：摘要吞了 result、留下 call，即半压缩状态。回滚弹错了东西：桌面案例项目的异常回滚曾按数组末尾弹出，多步失败时可能弹掉 tool result、留下孤儿 call【经验，后续复核】；修法是按 step 序号回滚到登记的检查点——弹多少由登记决定，数组尾巴说了不算。禁令一句：配对是原子单位——压缩、回滚、重放，谁都不许把它拆成两半。

## 6.8 artifact 的来历

工作成果不该藏在对话文本里——那是第十章的呈现问题；本章管登记，因为不登记的失效方式有名字：孤证。文件躺在磁盘上，问"谁把它改成这样"，对话里翻不到那次 effect，排障与合规都无处落脚。artifact 行因此携带 lineage：创建与修改它的 effect、输入引用、verifier 结论引用。对账是双向的：文件在而登记缺，来历不明；登记在而文件缺，账上有名无实。两向都要扫，扫描作业在第十三章。

## 6.9 数据库说成功，外部世界另有一本账

本章反复扩张持久层的权威，这一节给它划终点。effects 表里 result=success，只是工具的一面之词落了库；外部世界是否真的变成了那样，数据库无从担保。第二章的四档确定性在这里落位：库里的 result 至多是"记录在案的声称"，outcome 那一格要独立证据。第一章的 hard gate 拿 git 对账、6.5 节那套产品把 shell 副作用明确排除在捕获范围外，都是同一条边界的表现：持久层的权威止于自己的写路径。写路径之外的世界怎么对账、恢复时哪些动作能重放哪些不能，是第七章与第八章的全部内容——本章只负责把这条线画清楚，免得 Registry 的整洁给人"一切尽在掌握"的错觉。

## 6.10 删除是三件事

"删掉这个会话"在系统里是三个不同的动作。删会话：用户可见的容器消失，派生物（run、消息、摘要）按登记的传播规则走。删运行记录：审计与合规的对象，是否保留副本是治理决策，进第三卷。撤销外部动作：数据库做不到——发出去的邮件、改过的文件，撤销是一次新的副作用，走第八章的补偿路径。三件事混进一个"删除"按钮，用户以为世界回到了从前，系统只是删掉了自己的账本。落位：Registry 每行的删除语义列逐行作答；隐私与保留策略留接口给第三卷。

## 6.11 三条生命周期：状态、执行、授权

resume 一个 interrupted 的 run，恢复的是什么？朴素答案"恢复一切"的失效形态在授权上最疼：崩溃前批过的高危操作审批，恢复后还算数吗——上下文可能已变、批准者早已离场；恢复旧授权，等于把一次性的信任变成永久的。根因是三样东西的寿命天然不等，却被一个 resume 混着恢复：**状态生命周期**（数据活多久——最长）、**执行生命周期**（run 从生到死，第五章）、**授权生命周期**（权力何时生效何时过期——最短，第十一章）。

落法是把"恢复什么"从默认改成逐项声明：approval、delegation、credential 各自是否随 checkpoint 保存、是否随 resume 恢复、恢复前是否重验——每项显式写进 Lifetime Matrix（交付工作制品 I），安全默认值是不隐式恢复。第五章转移表里 waiting 回到 running 那行 guard 写着"授权仍有效（需重验）"，埋的就是这条；完整规则在第十一章 11.6 节。

## 6.12 信念工件：可执行、可版本、可反驳

最后一类状态最容易僭越。agent 对世界的理解——"这个 API 的行为规律""这个代码库的结构"——传统上是 prompt 里的隐式文字。近期一个公开保留轨迹的 model-based harness 项目把它升格为可执行工件：把当前信念写成程序，每次规划前用完整交互历史回测这个模型，真实动作后逐步比较预测与观察，一旦不符立即废止剩余计划、把差异当反例回到建模【预印/公开工件，项目自述】。这个方向本卷分两处消化——guarded commit 与计划失效在第八章，证据边与 Model Certificate 在第十三章；本章只立归属问题：这份"理解"是什么状态、归谁、能信到什么程度。

裁决：world model 是版本化的 **derived mutable artifact**，与真相分层记账。event history 记已发生的事实——append-only，真相本体；world model 记当前信念——可变、可错、可反驳；notes 记工作假设——可变、非权威；plan 是从特定模型版本派生的临时工件。信念的每个版本必须携带四样东西：history cursor（基于哪段历史生成）、生成 provenance（模型、提示、工具版本）、certificate scope（历史回测只证明解释了已见样本，不证明未见状态上的泛化）、已知反例清单。任何情况下不覆盖原始 observation：信念修正产生新版本，历史一个字不动。

信念工件还有一个专属的失效方式，值得单独破坏一次：状态表示本身漏了变量。转移规则再怎么修，如果 state representation 根本没记录那个决定未来的量，模型只能永远靠补丁追赶。所以本章破坏实验的第二个场景是：故意遗漏一个决定未来的状态变量，看新反例能不能触发状态表示与转移规则的**共同**修订——只会在 notes 里打补丁的系统，这一问答不出。Registry 落位：belief/world model 行入工作制品 A（State Registry）v2，登记模板住工作制品 K（Belief/World Model Registry）。

## 破坏实验：三处写入之间强杀，外加一次故意失忆

两个场景，各按四步测量协议执行：

1. **三处写入之间 kill -9**。破坏动作：在同一轮里制造三次相邻写入——消息落库、compaction 摘要写入、artifact 登记——分别在两两之间强杀进程，共三杀。观测点：重启后各表内容与事件表截断点；配对不变量扫描（孤儿 tool_call、半压缩）；checkpoint 完整性标记；第五章启动扫描对 run 的裁决。判定：每一杀之后，已提交事务完整可见、未提交不留半行；事件表按最后完整行截断，状态行可由事件序列重建；配对不变量零违例；不完整 checkpoint 被识别并丢弃——任何一处出现"半份状态说不清来路"，该杀判失败。复跑：每个切点 N=3。
2. **故意遗漏状态变量**（6.12 的反例驱动实验）。破坏动作：在 world model 的状态表示里删去一个决定转移结果的变量，继续运行至反例出现。观测点：反例事件之后，修订发生在哪一层——只改 notes、只改转移规则、还是状态表示与规则共同修订；新模型版本的 history cursor 与反例登记。判定：通过＝表示层被触及且旧版本连同反例留档；失败＝反例被 notes 吸收、模型版本不变。复跑：换三个不同变量各来一次。

实证状态照实分层【经验】：场景 1 为思想实验，完整矩阵是第十四章标准故障包的工单——"消息落库"切点有桌面案例项目修复后的验收实测（第三章记过），另两个切点未自动化；场景 2 依赖 world model 机制，参考实现落地前属读者侧作业，判定口径先立在这里。

## L 级自检

本章交付的是登记表与契约，L 尺照量机制（L1 能跑、L2 能看，全表见第一章 1.3 节）。L2 底线沿第四章状态层组件卡：每个持久对象的状态变化落事件——Registry 每行的"崩溃后归宿"列填得出、对应事件类型在工作制品 C 里找得到，才算账实相符。假落地公式的本章形态：表在 schema 里有名字，行为在事件里无痕迹，该表按未接线处理。桌面案例现状照第三章的账：增量持久化后消息侧已到 L2；memory 与 world model 两行在 v1 是占位——占位照实标注，不冒充已实现。坐标系落位补一句：本章是真相契约的主场，兑现它的可观测（状态变化落事件、每行崩溃后归宿可查）与可控（唯一写者，其余只读投影）两格；扰动下的并发消融与撕裂类事故的闭环数据，留给第十四章参考实现。

## 立即可做的一个动作（五分钟）

builder 版本：对自己的系统问本章开场那个问题——"重启之后，用户刚发的那条消息还在吗？"——然后逐载体追下去：它此刻存在于几个地方？每个地方是谁写的？哪份算数？"算数"的答案超过一份，State Registry 的第一行工单就有了。

assessor 版本：把工作制品 A 的表头（状态对象／owner／存储／读者／删除语义／崩溃后归宿）发给被评团队，请对方填自己系统的前五行。填不出 owner 的行、"崩溃后归宿"写着"不确定"的行，逐行记入风险清单。这张半小时的空表，往往比一天的架构访谈更接近实情。

## 遗留问题

账本立全了：状态有归属，事件有秩序，投影有契约，信念有版本。可是进程崩溃重启之后，具体怎么接着跑？事件表的最后完整行怎么定位，已经付过钱的模型调用怎么不再付第二次，"重放记录"与"重新执行"差在哪里，两个 worker 同时来恢复怎么办——从最后一个完整点继续的全部语义，第七章。
