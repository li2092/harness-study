第九章守住了交互面：连接会断但 run 不断，人能打断但打断有账。可它把一个前提留给了本章——那份被投影给用户、被打断、被恢复的上下文，本身得完整且一致。而多轮长跑的任务终将撞上 context 窗口的上限：窗口有上界，历史却一直在长。一个跑了两百步的编码任务，把两百步的对话、工具输出、报错原文全塞进下一次 prompt，要么超限被拒，要么模型在一大堆旧信息里找不到重点。

撞上上限之后要压缩、要把东西挪到窗口外、要跨 run 把状态接起来——这些动作彼此干扰：压缩可能崩在一半，摘要可能把"必须用绝对路径"这条系统约束一起压没，恢复可能读到崩溃前的旧版本。本章的主张压成一句：**context 是投影，不是容器**——投影按来源、优先级、预算确定性地组装一份视图；压缩这件事，是事务不是随手摘要，失败要回退、边界要落盘。读完本章，手里应当多一张压缩契约、一份 memory 的来历规则。

## 10.1 context 是投影，不是容器

先看不设防的做法：把 conversation 从头到尾拼进 prompt，能塞多少塞多少。开发期一切正常，因为对话还短。任务一长，三种失效同时来：撞上 token 硬上限，请求直接被拒；就算没撞上，模型也会在长上下文里丢准确率——Anthropic 把这两件事称作 attention budget 与 context rot：token 越多、准确召回越低，每个新 token 又都在摊薄有限的注意力预算【规范/官方文档，Anthropic context engineering】；再就是成本，每次把增长的全量历史重发一遍，账单按 token 涨。缓存不在这笔账里——只追加不改写已有前缀，prompt 缓存照旧命中；打断前缀的是压缩改写历史那一下（10.3 节）。

失效根因是一个心智模型的错位：把 context 当成"容器"——越全越好，塞满为止。可第六章已经立过，context 是持久真相的一份投影，给某一次模型调用看的读视图。投影的纪律是策展：每个成分要能指回一个持久对象（有来源）、按重要性排序（有优先级）、总量卡在一个预算内（有预算），重复的去掉、来路不明的降权。这就是 context assembly——把"塞历史"换成"确定性地组装一份视图"，交付为工作制品 Q（Context Assembly Spec，上下文组装规格）。第六章投影三契约（有来源/可重建/不回写）在给模型这一侧的落地，就是这张规格。策展不是白来的：每个成分要挂着来源、优先级、预算三样登记，组装逻辑比"全塞进去"复杂，预算还可能把本该在的一条挤出窗口。可对面是撞上限被拒、context rot 丢准确率——这份确定性成本换的是模型每次都看到该看的，划算。

## 10.2 撞上限的四种手段

预算有限，历史无限，早晚要给窗口腾地方。给窗口腾地方的动作空间其实只有三类：压掉已有的、把内容移出窗口再按需拉回、分流到另一个干净窗口。业界把它细分成四种手段，落点各不同，但共用 10.1 那把尺——省下的注意力预算，要花在高信号的 token 上【规范/官方文档，Anthropic context engineering】。

- **compaction（压缩）**：接近上限时把一段历史摘要成短文，用摘要重启窗口——"压掉已有的"，适合线性长对话。
- **note-taking（记笔记）**：把要长期记住的写进窗口外的笔记（如一份 NOTES 文件），后续按需拉回——"移出再拉回"，适合跨越多轮的任务状态。
- **JIT retrieval（按需检索）**：上下文里只存轻量标识（文件路径、查询、链接），运行时才把正文拉进来——同属"移出再拉回"，适合大语料。
- **subagent（子代理）**：让一个子代理用干净窗口做一段深活，只回传一两千 token 的浓缩结论——"分流到另一窗口"，适合能切分的深探。

这些手段的收益是可量的。Anthropic 的 context editing 加 memory 工具，在内部 agentic search 评测里比 baseline 把表现抬了 39%（官方口径是 performance，未拆到具体指标）；而在一个百轮 web 检索评测里，仅 context editing 就让原本会因 context 耗尽而失败的工作流跑完、把 token 消耗压了 84%【规范/官方文档，Managing context】。把 MCP 工具目录从"全量预载进 context"改成"按需从代码环境发现"，一个跨系统工作流的 token 从十五万降到两千——省是省了，代价换了个地方：agent 生成的代码得跑在带沙箱、资源限额与监控的执行环境里，多一层运维与安全开销；中间结果默认留在那个环境、不进 context，跨步骤要复用、崩溃后要恢复，就得自己往文件里落【规范/官方文档，Code execution with MCP】。省下的注意力预算没有一样白得——压缩担着崩溃与缓存的账，移出窗口担着重建成本，分流担着子代理的往返。

四种手段里，压缩是最凶险的一种——它动的是历史本身。下一节单说它。

## 10.3 压缩是一个事务，不是一次摘要

把 compaction 当"顺手让模型总结一下前面"，是这一章要拆掉的第二个错位。摘要这个动作看着轻，可它嵌在三件事的交叉点上，任何一件出岔都留下难查的坏账。

第一重耦合是崩溃。压缩要读一大段历史、生成摘要、写回、再裁掉原文——这中间进程崩了，就可能停在半压缩态：摘要写了一半，原文裁了一部分，剩下的既不是完整历史、也不是完整摘要。

第二重是缓存。prompt 缓存靠前缀完全一致命中，压缩一旦改写了前缀，缓存前缀断裂，之后每次调用回到全价——压缩省了窗口，却可能悄悄抬了成本，这笔账要算进压缩时机的决策。

第三重是恢复。第七章的 resume 要重建崩溃前那一刻的 context，可如果压缩版本对不上——恢复时读了一个更早或更晚的压缩边界——重建出来的视图就和当时模型真正看到的不是同一份，invocation 记录（第七章的重放缓存）与它对不上账。

三重耦合之下还压着一条更硬的底线：摘要是新增的行，绝不许写回去盖掉原文——一旦反向覆盖，压缩就从"改投影"滑成"改真相"，撞上第六章那句投影不回写。事务化正是为守住这条底线：压缩必须像数据库事务一样处理——要么完整生效，要么完整回退，不留中间态。它交付为工作制品 R（Compaction Contract，压缩契约）。

## 10.4 压缩契约的四条纪律

把"事务化"落成四条可检查的纪律，正是压缩契约的内容。

**失败回退**：压缩是一个原子操作，中途失败就整体回退到压缩前，绝不留半压缩态。这是第六章"改视图不改历史"在崩溃面的兑现——原文在事务提交前一步都不能裁。

**边界落盘**：每次压缩登记一个 compaction 版本号（字段 compaction_version）与边界序号——摘要由哪些消息压成、边界落在哪一条。组装 context 时按登记的边界取"摘要＋边界之后的原文"，恢复时认准同一个版本号（10.8 节）。

**约束不入压缩**：这是最容易漏、后果最隐蔽的一条。系统约束——"必须用绝对路径""不许碰生产库"这类——一旦被摘要吞掉，模型在之后的步骤里就会像从没被告知过一样犯错，而且没有任何报错，它只是安静地违反了一条它再也看不见的规矩。契约的做法：系统约束不放进可压缩的历史段，或压缩后无条件重新注入，让它每次都在窗口里。

**配对修复**：第六章 6.7 节立过 tool_call 与 tool_result 必须成双，压缩不许把一对拆成两半（摘要吞了 result、留下孤儿 call，下一次模型调用会当场报错）。契约要求压缩后扫一遍配对，落单的要么一起压、要么一起留。第六章那个按数组末尾 pop() 弹掉 tool result 的反例，是回滚版；压缩版的病根一样，药也一样——配对是原子单位，谁都不许拆。

## 10.5 memory 要有来历

compaction 管一次任务内的窗口，memory 管跨任务、跨会话的长期记忆——把这次学到的东西留给下次。可 memory 写入不是免费的往罐子里塞东西，它有四种一旦发生就难收拾的失效。

污染：一条错的记忆写进去，之后每次都被拉出来用，错误自我延续。过期：旧的偏好、旧的事实该失效，却一直生效。撤销：想删掉一条记忆，却发现它已经影响了一串下游判断，删得不干净。而这三种的共同根子是第四种——没有来历。

一条没有 provenance 的记忆，说不清是哪个 run、基于什么写下的，就成了又一个没人认领的真相源：第六章那句"多出来的每一份'真相'都是未来的事故"，在 memory 这里换了张脸。

契约因此要求 memory 每条带四样：provenance（哪个 run、基于什么事件写的）、TTL（有效期）、撤销标记（能被显式作废且作废可追溯）、scope（会话／项目／全局，作用域即归属）。这交付为工作制品 S（Memory Provenance，记忆来历登记），也把工作制品 A（State Registry，状态注册表）里一直占位的 memory 行实化成契约形态。代价是每条记忆都背上登记、判活、追销三重开销，读取时还要按 scope 过滤；但比起一条错记忆自我延续、想删又删不干净的事故，这点登记开销是小钱——这正是它值得做成契约的理由。业界给了机制却把治理留了空档——Anthropic 的 memory 工具提供跨会话的文件式持久，存储后端由开发者管理，何时写、写什么、何时失效则不在工具职责内【规范/官方文档，Managing context】——这道空档正是本节补的：有持久，还得有来历。

## 10.6 artifact 不藏在对话文本里

工作成果——生成的文件、一份报告、一段代码——不该塞在 conversation 文本里当普通消息。藏在文本里有三重代价：它会被压缩当普通历史吃掉；它无法被别的地方独立引用；它没有 lineage，出了问题查不到是哪次动作产出的。

正解是 artifact 独立登记，走自己的载体，不混进对话流。第六章 6.8 节立过 artifact 行携带 lineage（创建与修改它的 effect、输入引用、verifier 结论），并要求双向对账——文件在而登记缺是来历不明，登记在而文件缺是有名无实。那一章管的是登记，本节管的是呈现：连续性的要求是，artifact 从产出那一刻就活在对话之外，压缩动不到它、恢复能找回它、引用能指到它。独立载体的代价是要持续做这份双向对账扫描、artifact 与对话的关联得显式维护，不能再靠"反正在对话里"兜着；换来的是成果压不没、每次改动都追得到来历——长任务里这笔对账开销远小于一份查不到来路的孤证。conversation 记的是"做了什么"，artifact 是"做出来的东西"，两者分开存，长任务才不会把成果连同旧对话一起压没。

## 10.7 模型会在临界点抄近路

前面几节都在讲工程怎么管 context，还剩一个不受工程直接控制的变量：模型自己。压缩、reset 这些动作能不能交给模型自觉去做？一手证据说不能。

编码代理产品 Devin 的团队 Cognition 报告过一个具体行为：他们见到的第一个"对自己 context window 有感知"的模型（Sonnet 4.5），这份感知反而改变了它的行为——模型自认为快到窗口上限时会抄近路、把任务草草收尾留下未完成的部分，即使实际余量还很充足；而它对剩余 token 的自估"一贯低估，很精确却是错的"（原文：consistently underestimates how many tokens it has left—and it's very precise about these wrong estimates）【厂商实践，Cognition】。换句话说，模型对"我还剩多少空间"的判断既稳定又系统性偏悲观，于是提前收了手。

这条观察把 context 管理钉死在一侧：不能指望模型自觉。压缩何时发生、reset 何时触发，要走确定性的硬路径——由工程按登记的预算和边界决定，用 hook 一类模型外的机制执行——不交给模型的自我感觉。这正是 Anthropic context engineering 反复强调的那条总纲在 context 这一域的复现：硬控制走模型之外、别把软层当硬层，模型的自律只当参考、不当机制。

## 10.8 恢复要认准同一个版本

第七章立过：invocation 记录就是重放缓存（7.2 节），resume 要按登记的 compaction 边界重组 context 投影（7.10 节第五步）。而一次 invocation 看见的视图，由 model、prompt、暴露的工具与 context 组装策略共同定——所以恢复有一条硬要求：resume 必须尊重原 invocation 的 compaction 版本与组装策略版本。

失效场景很直接：崩溃前模型看的是压缩到版本三的视图，恢复时若按版本二的边界重建，就把已经压掉的一大段原文又全量塞了回去——重建的 context 和当时模型真正看到的不是同一份，第七章那条"invocation 留档即重放缓存、恢复时复用"的账就对不上了，重放出来的是另一个版本的历史。第八章 Plan Lease 里的 history_cursor 是同一件事在计划层的形态：计划只对某个历史光标有效，光标一动，计划失效。恢复的纪律统一成一句：认准崩溃前那一刻的版本号——compaction 版本、policy 版本、history cursor——按同一个版本重建，不多塞也不少给。两类时变成分不在这套版本坐标里——带 TTL 的 memory 随时间失效，JIT retrieval 拉进来的外部正文随源头改动。它们不参与 replay 一致性："同一份"承诺的范围，是版本坐标覆盖得到的那部分。

## 10.9 隐私与删除：留给卷三的接口

memory 和 context 里会沉淀隐私数据，也会收到"删除我的数据"这类要求。这些的完整治理——数据保留期、合规删除、审计——是第三卷数据治理的内容，本章不展开。

本章只把接口留好，让卷三能接上：memory 每条可撤销且撤销可追溯（10.5 节的撤销标记）；artifact 的删除语义清晰（第六章 6.10 节删除三义，删除 artifact 不等于撤销产出它的外部动作）。接口立在这里，治理搬去卷三——本卷管"一次运行里怎么保持一致"，跨越时间的数据怎么留、怎么删，是长期运行的题目。

## 破坏实验：压、漏、脏、错版本四场景

按四步测量协议执行，四场景共用观测点：压缩前后的 transcript 与摘要行、compaction 版本号、配对不变量扫描、memory 的 provenance 与 scope、恢复时读取的版本。

1. **压缩中断**：压缩写摘要、裁原文的中途 kill -9。判定：通过＝整体回退到压缩前、无半压缩态，原文完整；失败＝摘要写了一半、原文裁了一截，两不着。
2. **摘要遗漏系统约束**：让压缩把一条系统约束（如"只写绝对路径"）纳入摘要范围。判定：通过＝约束不进压缩段或压缩后被重新注入、模型后续仍遵守；失败＝约束被摘掉、模型之后无声违反。
3. **memory 污染**：写入一条错误 memory，观察它能否被定位与撤销。判定：通过＝该条带 provenance 可溯源、可显式作废且作废留痕；失败＝无来历、删不干净、下游继续用。
4. **resume 读错版本**：崩溃前压缩到版本三，恢复时故意按版本二重建。判定：通过＝恢复认准版本三、context 与崩溃前一致；失败＝按旧版本重建、全量原文回灌、invocation 对不上账。

复跑 N=3。实证状态照实分层【经验】：本章四场景均为思想实验，判定口径先立——参考实现与完整矩阵是第十四章 context assembly 工单；第六章那个 pop() 弹掉 tool result 的配对破坏，是场景 1/4 在桌面案例项目里的已见近亲（回滚版），压缩版按同一口径处置。

## L 级自检

按第一章的成熟度尺（L1 能跑、L2 能看，全表见第一章 1.3 节）。本章机制的 L2 底线：压缩与 memory 写入都要在账本上留痕——每次压缩落 compaction.committed 事件带版本号与边界，每条 memory 写入落带 provenance 的事件，否则"这段历史什么时候被压的、这条记忆哪来的"事后无从查起。套第一章那条假落地诊断：系统里有压缩功能（L1 在）、可 trajectory 里查不到压缩事件与版本号（L2 缺），按未接线嫌疑处理——最容易缺的就是压缩边界的登记，因为压缩常被当成一次性动作、做完就忘。

四问落位：可观测由压缩与 memory 事件落账兑现；可控押在 context assembly 的确定性——组装走登记的来源与预算、压缩走契约的四条纪律，不由模型临场发挥；稳定兑现在"改视图不改历史"——压、漏、脏、错版本四类扰动打进来，完整历史一格不动；闭环落在压缩事务本身——压缩执行后、事务提交前扫一遍完整性与配对，任一处不齐就整体回退到压缩前，检测（配对与完整性扫描）到纠正（回退）在一个事务里合拢，这是压缩这一域的反馈环。（resume 认版本重建是另一件事，管的是跨 run 把真相接回来，闭合的是第七章那个恢复环，不算进压缩环的验证腿。）

坐标系落位补一句：本章守的是真相契约在时间轴上的延伸——第六章管"哪份状态算数"，本章管"这份状态被压缩、被记忆、被跨 run 恢复时怎么还算数"；第一章 1.3 节矩阵里真相契约那格，从"某一刻的真相"延伸到"跨越 turn 与 run 的真相"，在此落地。

桌面案例现状照实记账：增量持久化（第三章）给的是运行中状态可查，落不到压缩版本登记与 memory provenance 这两件本章核心机制上——这两格基本是空的，不粉饰成半格；补格工单第十四章。

## 立即可做的一个动作（五分钟）

builder 版本：找到系统里做压缩／摘要的那段代码，问三件事——压到一半崩了会留下什么？系统约束（那些"必须／不许"）会不会被摘要吞掉？压完还认得出 tool_call 和 tool_result 是成对的吗？三问有一问答不出，就照工作制品 R 补一条纪律；尤其第二问答不出的，去 transcript 里搜一次系统约束在压缩后还在不在。

assessor 版本：问被评团队一个问题——"这套 agent 跑长任务时，context 怎么控制？"听回答里有没有"压缩／摘要"。有的话追一句："压缩崩在一半会怎样，压完的版本恢复时对得上吗？"答不出版本与回退的，按本章的账记：压缩没有事务化，半压缩态与错版本恢复是两处记在账上的隐患。

## 遗留问题

连续性守住了：context 是策展出来的投影，压缩是能回退的事务，memory 有来历，artifact 活在对话之外。可这一整套动作——压缩谁触发、memory 谁能写、artifact 谁能删——都还没问过一个问题：谁有权做这些动作，这份权力持续多久？第九章挂起恢复时已经碰到一次"授权不随状态自动恢复"，那还只是接口。权限、身份与运行时隔离的完整规则，第十一章。
