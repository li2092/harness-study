# 十一、运行环境与 prompt 组织

这一章收两类横切问题：harness 之外的环境因素（网络、进程、前端框架），以及 prompt 内容本身怎样组织。

它们看起来不相干，共同点是**都不在 agent 的主流程里，但都能让主流程失效**。

## 11.1 国内接口强制直连

系统配置了代理时，发往国内模型服务的请求也被转入了代理。

一次测量中，请求延迟从约 10 秒升到了 123 秒，慢了十多倍：请求先绕到代理出口，再回到国内的服务端。这个故障最难的地方是它不报错。请求最终成功了，只是慢，于是容易被归因为"这家模型响应慢"，进而做出错误的选型决定。

试过的无效做法是设置免代理的环境变量（`NO_PROXY` / `no_proxy`）。这个做法不可靠：各家 HTTP 库对免代理规则的解释不同，通配符、网段、端口、前导点各有各的处理；有的库只读大写或只读小写的那个变量；有的运行时默认不读环境变量里的代理设置；容器和子进程的环境也未必继承。

有效做法是在客户端初始化时按域名清单强制直连，不依赖环境变量。清单维护成本很低，国内主流厂商的域名只有十来个。但清单要定期核对：厂商启用新域名后，发往新域名的请求会重新落回代理，症状和本节开头一样，只是变慢而不报错。可以对这些厂商请求的延迟设一条告警，异常升高时就回头检查清单。

**环境变量是约定，不是保证。** 需要保证的地方，要在代码里显式设定。

## 11.2 后台服务要真正脱离父控制台和作业

按类 Unix 的经验，用后台方式启动一个服务，就算脱离了终端。

在 Windows 上这个假设不成立，而且问题不在父子进程关系，而在两处继承：

- 子进程默认共享父进程的控制台。控制台关闭时，其中所有进程都会收到关闭事件。
- 父进程如果在一个设置了 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`（作业关闭即终止其中所有进程）的作业对象（Job Object）里，子进程默认也加入这个作业。

表现是长任务运行到一半，依赖的后端服务突然消失，而这个后端明明是按后台常驻方式启动的。一次实测里，五十个任务的评测运行到中途整批失败，排查了很久才定位到进程的启动方式。

有效做法是在该平台上用原生的脱离方式启动，逐项处理上面两处继承：不继承控制台（`DETACHED_PROCESS`）、新建进程组（`CREATE_NEW_PROCESS_GROUP`）、脱离所在的作业（`CREATE_BREAKAWAY_FROM_JOB`，前提是该作业允许脱离）。

类 Unix 上用 `&` 放到后台同样不算脱离：终端挂断时，会话内的进程会收到 SIGHUP。要用 `setsid` 新开一个会话，或用 `nohup` 忽略这个信号。

**跨平台的进程管理不能靠经验迁移。** 每个平台上"后台"的含义都要单独验证一次。办法很简单：启动之后关掉父终端，看服务还在不在。

## 11.3 副作用要经得起重复执行

React 的 StrictMode 在开发模式下会刻意重复执行一些代码：每个 Effect 会经历一次"挂载、卸载、再挂载"，状态更新函数（传给 setState 的函数）等也会被调用两次，用来暴露不能安全重复执行的代码。

这个机制会把本来"看起来正常"的缺陷暴露出来：消息被追加两次，事件监听器注册两次导致每个事件被处理两次，初始化请求发两遍。

有效做法是先判断这件事的正确频次：每次挂载执行一次，还是整个应用加载只执行一次。

- **每次挂载一次**：订阅、事件监听、连接、定时器都属于这一类。正确做法是写清理函数，卸载时把这一次的注册撤销，让"装、卸、再装"与"装一次"对用户没有区别。用一个标志位（例如 ref）挡住第二次执行，是 React 官方文档明确反对的做法：它只让开发模式下的重复消失，真实的泄漏一个也没修好，组件被正常重新挂载时还会漏掉注册。
- **整个应用只执行一次**：一次性初始化、启动时上报属于这一类。只有它们才用模块级的一次性标志位来防重复。

无论哪一类，都不要把副作用写在状态更新函数里，因为开发模式下这个函数同样会被调用两次。

**框架的重复执行不是缺陷，而是检测手段。它暴露出来的问题在生产环境同样存在**，只是触发条件更隐蔽。

## 11.4 触发工具调用的 prompt 要短

触发工具调用的那条指令写得越长、夹带的背景越多，部分模型越倾向于直接用文字作答，而不去调用工具：指令里的信息看起来已经"够用"，模型就跳过了查询这一步。

表现是流程里本该发生的工具调用消失了，模型给出一段看起来合理的回答，而那段回答没有事实依据，因为它根本没有去查。

有效做法分两步。流程里必须发生的调用，先用 API 的 `tool_choice` 参数强制模型调用工具（前提是模型支持；第六章 6.5 处理空转时也用到了这个参数）。仍要靠模型自主决定的调用，把触发它的指令写短，只说要做什么、该查什么，背景材料拆到别处或分步给出。短到什么程度要对所用模型实测（中文可以从 200 字左右起试，这是经验起点，不是通用阈值）；测出的结论连同模型标识与测试日期一起记录，模型换版本就重测。

入门卷 §7 把这类对模型行为的探测整理成了一套方法（书中称"把脉"，即行为探测），主张动手搭之前先运行一组探针摸清楚：这家模型在什么条件下不调工具、在什么格式上会出错、指令遵循的边界在哪里。本节这条就是探针能测出来的典型结论之一。

**模型的行为边界要实测，不能靠推理。**

## 11.5 明确的业务规则直接写死

有个项目的业务规则里，各项因素的权重已经确定（甲占四成、乙占三成……），实现时却把"综合权衡"交给模型去做。

结果是同一个输入每次给出的打分都不同，也得不出确定的结论。采样本身有随机性，模型也不会严格按给定权重做算术：你要它综合，它就真的每次重新综合一遍。这类任务模型做不好，也不该交给它做。

有效做法是把能计算的部分放进代码：权重求和由代码做完，模型只拿到结果去表述；不能计算的业务规则才写进 prompt，并且写成规则原文。

入门卷 §5.5.6 列出的常见错误之一是"把业务规则全堆进 system prompt"，本节是这个错误的一个具体案例。**该由代码保证的确定性，不要交给模型的一致性。**

## 11.6 多语言 prompt 用注册表管理

多语言支持的第一版，通常是在代码里按语言写条件分支。

分支很快就不止语言一个维度：语言、业务类型、章节、输出格式，四个维度相乘，每加一个维度，分支数就要乘以这个维度的取值数。到某个点上没人敢改，因为改一个分支不知道会影响哪些组合。

有效做法是建立按键索引的 prompt 注册表：全部组合的文本放在配置里管理，代码只按键取用。注册表还要支持逐级回退：找不到"语言 + 业务 + 章节 + 格式"的专门文本时，退到更通用的键；否则组合数照样会膨胀，只是从代码搬进了配置。入门卷 §5.5.4 讲的多语种抽象就是这件事，本节补的是不做会演变成什么状态。

## 11.7 prompt 修订由失败日志驱动

按理论流程设计的七个分析维度，上线后有三成真实输入在某些维度上完全没有内容。

模型的反应是对着空维度硬写。它不会说"这一项没有材料"，而是生成一段通顺的文字把结构填满。产出看起来完整，实际没有依据。

有效做法有两步：建立失败日志并按原因分类，定期据此修订 prompt；除了正常流程，还要给模型写明常见的异常输入形态及处理方式，明确告诉它某一项没有材料时就写明没有，不要推测。

**prompt 要覆盖异常输入，不能只写正常流程。** 只写正常流程的 prompt，遇到异常输入时，模型会自己补出一个正常流程来。

## 11.8 模型会误判自己所处的环境

有一类现象只在真实运行中才会遇到：**模型表现得像是身处模拟环境，执行得很敷衍。**

表现是它给出"如果真的执行，将会……"这类假设性回答，或者用明显简化的方式处理任务，而它明明有完整的工具可用。

有效做法很朴素：在环境说明里明确告知这是真实环境，有真实的执行能力和网络访问，动作会产生真实后果。

还有两种相关的形态。一种是反过来的：外部内容已经被抓取并放进了上下文，模型仍然回答"我无法访问互联网"。处理方式同样是在 prompt 里显式声明这些内容已经取到，要当作已知信息使用并注明来源。另一种是工具结果里出现的环境描述，例如"这是测试环境""网络不可用"，被模型当成了事实。这一种属于第十章 10.7 的范围：外部数据不能改写模型对自身环境的认知。

**模型对自身处境的认知，也是一项需要管理的输入。** 它不会自动知道自己能做什么。

## 11.9 prompt 里的禁令是一份事故清单

这一节讲的不是一个故障，而是一种读法。

成熟的 agent 产品，system prompt 里往往有大量"不要……""绝不……"。禁令不会凭空出现，多数都对应着模型真做过的事，所以一份 prompt 的禁令列表，本质上是这个团队的模型行为事故清单。

这类禁令里反复出现的有下面几类：

**改动范围类**：不要改与任务无关的代码，不要过度抽象，不要加没被要求的错误处理，不要为凑数写只断言显然成立的测试。这几条与很多团队自己的协作规范高度重合，说明它们也是人类开发者的常见问题，模型同样会犯。

**编排类**：不要把中小任务激进地拆成一堆并行 agent。同一条禁令在不同位置出现两次、措辞不同，我们推测是加了一次没有效果；另一种可能是两处各针对一个场景。

**不可逆操作类**：不要推送，不要强制推送，不要修改已有提交，不要切换当前分支，不要合并，不要提交可能含密钥的文件。还有一条形态特别：不要使用交互式参数，因为交互会让流程停下来等待输入。

**文件与工具幻觉类**：不要为了有东西可引用而凭空创建文件，不要发明不存在的工具，不要为一个文件建一个目录。

**语气升级本身也是信号**：当一条规则从普通提醒升级到全大写，再加上感叹号，说明前面所有温和的措辞都没有效果。这时该做的不是再加一个感叹号，而是问它能不能下沉到 schema 或校验层（第四章 4.9）。

能下沉的不止 schema，还有运行时检测。上面那条"不要使用交互式参数"就可以做成检测：命令执行器同时盯两个信号，一是长时间没有任何输出（参考值两分钟），二是进程正在等待交互输入；命中就终止，并给出明确的提示，说清它停在等待输入上。检测到位之后，那条禁令的作用只剩提前避免一次浪费。

再往下一层是直接约束：子进程的标准输入接到空设备（`/dev/null`），多数交互式命令读到文件结束就会立即失败退出，连检测都不用等。例外是直接读终端的程序，例如 `ssh`、`sudo` 的密码提示；它们还需要配合不分配终端运行，或设置 `GIT_TERMINAL_PROMPT=0` 这类开关。

**读别人的 prompt 禁令，等于拿到一份别人的失败清单。** 写自己的 prompt 时也要意识到，每加一条禁令都是在记录一次事故，值得回头问一句：这条为什么不能用机制解决。
