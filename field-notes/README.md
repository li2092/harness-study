# Harness 实战笔记

《Harness Study》的实践卷，横切全书、不占主线卷号。十四章，按顺序阅读。

> 本卷 2026 年 9 月修订，读过旧版的读者请先看[修订记录](00-revision-notes.md)。

## 主线

**agent = 模型 + harness。模型是核心，而模型的全部能力只能经由上下文被调用；harness 的工作是通过有效的上下文管理，最大限度释放这个能力，并让它在可控的环境下完成任务。**

这句话拆成三件事，正好是全卷的编排依据（与第十四章末尾的归类一致）：

- **上下文管理**：决定模型每一轮看到什么（第三、四、七章）
- **释放能力上限**：不要用不必要的限制削减模型本来能做到的事（第二、五章，以及第六章的误判防护）
- **可控的环境**：边界由代码保证，不靠 prompt 请求（第六、八、九、十、十一章）

第一章是一条消息经过 harness 的全流程总图，不单归其中哪一项。第十二到十四章不属于这三件事，它们是判断这三件事做得好不好的手段。

## 与前两卷的关系

入门卷讲每个机制的定义与原理，第二卷讲机制怎么组装成语义正确的 runtime，本卷讲真实项目里的故障与验证。第二到十三章末尾各有一节"本章与前两卷的对应"，逐条标出哪些做法在前两卷已有更系统的版本，哪些是本卷补的。

比对之后，两卷未覆盖、可作后续修订素材的内容：

- **限制类配置的五类数字**（第二章）：输出 token 上限、步数上限、工具结果截断、窗口预留、各层超时。这五项在前两卷都只作为参数出现，没有讲设错时的表现，而它们制造的故障往往表现为"模型能力不足"
- **上下文改写的成本侧**（3.9、3.10、7.3）：前缀缓存的经济性怎么进入压缩决策、工具调用记录降级为文本会引发工具调用幻觉、追加进上下文的内容要在注入点同时写好清理点
- **副作用租约**（9.4）：运行被停止之后尚未返回的工具仍会写，单机场景同样需要在提交点（副作用发出前的最后一刻）校验写入许可
- **评测的可追溯性**（12.7）：语料指纹与代码指纹、用例来源四项必填、机制型检查要分开报"是否触发"与"触发后是否通过"
- **评测系统自身制造假阴性的一类问题**（第十二章后半）：回放数据不一致、信任机制静默拦截、配置不随工作区、被测服务进程托管
- **评测设计的两个选择**（12.8、12.9）：模拟用户双轨选型、"做对事还要报告事"的多维指标案例
- **工具结果空值语义**（4.7）：null 与空对象的判定混淆
- **工具清单每轮刷新**（4.8）：与入门卷"schema 禁止热改"的边界辨析
- **开发者侧的迭代规则**（13.4）：每轮只改一处；同一问题连修两轮无效就停；修复须通过编译（或构建）、测试和类型检查三项；"完成"要分级定义
- **一批平台特定判例**：外置存储保存顺序、转发头伪造、字典容量、会话多路径同步、动态注册资源持久化、正则状态复用、前端框架重复副作用、Windows 进程托管

还有三项，入门卷第 11 章的实施 Spec 只用一句话提到、正文没有展开，本卷各有一节细讲：循环重复检测与消息暂存队列（Spec §1.5，见 6.2、6.4）、命令参数数组执行（§1.3，见 10.2）、国内 API 强制直连（§1.1，见 11.1：发往国内模型服务的请求在代码里按域名清单绕过系统代理，不依赖环境变量）。

反过来，也有前两卷讲得更系统、本卷只简要提及的内容：schema 规范化失败的工具不注册（启动期快速失败，fail-fast，见 4.2）、消融的统计功效与配对检验（13.1、12.10）、复跑不独立的对策（第十二章末）、模型行为探测（11.4）。需要细节时请看前两卷。
