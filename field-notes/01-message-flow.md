# 一、一条消息经过 harness 的全过程

## 本卷的主线

本书说的 harness，指包在模型外面、负责上下文、工具、执行、权限与留痕的那一层程序。模型接收一段输入、返回一段输出；其余工作，包括决定模型看到什么、模型的输出如何被执行、执行结果如何回到模型，都由 harness 完成。

在这个定义下，本卷的主线是一句话：**agent = 模型 + harness。模型是核心，而模型的全部能力只能经由上下文被调用；harness 的工作是通过有效的上下文管理，最大限度释放这个能力，并让它在可控的环境下完成任务。**

前半句是入门卷第一章提出的分解公式，后半句是本卷要交代的内容。两者之间有一个容易被跳过的事实：**模型 API 是无状态的，运行中也不更新权重。** 在模型版本固定的前提下，模型这一轮的行为只由这一轮送进窗口的内容和这一次调用的参数决定，没有第三个来源。harness 能影响模型的位置，就是这两处。

这句话可以拆成三件事，对应本卷十四章的分工：

**上下文管理**：决定模型每一轮看到什么。压缩、工具清单、协议解析、提醒注入都属于这件事（第三、四、五、七章）。做得差，模型的能力用不出来；做得过头，模型的能力被自己限制住。

**释放能力上限**：不要用不必要的限制去削减模型本来能做到的事。输出长度上限设得过紧、步数上限设得过小、工具结果直接截断，这三类设置都会让一个有能力完成任务的模型交出半成品（第二章）。

**可控的环境**：在能力被释放的同时，边界要由代码保证。循环要能停（第六章），动作要能取消（第九章），权限要收窄（第十章），崩溃要能恢复（第八章）。

![](../diagrams/fn-layered-01-thesis.png)

*图 1.1 · 三件事的分工：管理上下文、释放上限、约束环境*

入门卷把 harness 拆成八个 runtime 机制加一个 Safety 控制面，§5.10 用一轮调用走完全部机制的协作。本章是同一件事的另一种切法，按代码的执行顺序排，便于后面把每个故障定位到具体的步骤编号上。

先约定本卷几个计数单位的用法：

- **轮**（turn）：一次模型调用，加上它触发的工具执行。与 OpenAI Agents SDK、Claude Agent SDK 中 `max_turns` 的计数方式一致。第二章说的"步数"也按轮计。
- **回合**：从一条用户消息开始，到模型给出最终回复为止。一个回合包含多轮。本章走的"一条消息的全过程"就是一个回合。
- **run**（运行）：一次任务从开始到终态（完成、失败、取消）的全过程，可以跨越多个回合。

## 十三个步骤

流程分四个阶段、十三个步骤：

| 阶段 | 步骤 | 内容 |
|---|---|---|
| 组装输入 | 1-5 | 装配上下文、预算检查、压缩、筛选工具清单、注入提醒 |
| 模型调用 | 6-7 | 发送请求、拆分推理与回复 |
| 工具执行 | 8-10 | 调用前校验、执行、结果处理 |
| 回写与循环 | 11-13 | 回写上下文、循环判定、收尾 |

先读这张表建立整体结构，再看每一步的细节。读完本章会得到一个结论：模型只在步骤 6 做决策，其余十二步都是 harness 的代码；压缩与记忆抽取也会调模型，那是 harness 发起的辅助调用，不产生动作。

## 阶段一：组装输入

### 步骤 1 · 装配上下文

**模型 API 是无状态的**：每次请求都要把模型需要知道的全部信息重新发送一遍，服务端不保留上一次的对话。这个事实是后面所有成本问题和管理问题的来源。部分服务提供服务端会话或服务端压缩，把这份工作挪到服务端；本卷讨论的是客户端全量重发的形态，第三章的决定都在这个前提下成立。

因此收到用户消息后，harness 的第一件事是装配本次请求的完整输入，这份输入称为**上下文**（context），由四部分构成：

1. system prompt：角色定义、行为规则、约束条件
2. 历史消息：之前各轮的用户消息、模型回复、工具调用记录
3. 当前这条新消息
4. 工具清单：本次允许模型调用的工具及各自的参数定义

上下文越长，请求越贵、响应越慢、模型出错率越高。后面四个步骤从不同方向控制它：步骤 2、3 管长度，步骤 4 减少干扰，步骤 5 保住关键规则。

装配还有一条约束与长度无关：**前缀的稳定性**。多数模型服务按 token 前缀复用最近写过的相同输入，命中的那段按远低于正常价的费率计费；有的服务要在请求里声明缓存断点或开启自动缓存才生效，缓存本身有几分钟到一小时的存活期，写入还有溢价。复用要求前缀逐 token 相同，实践上按逐字节相同来维护。所以每一轮重新拼装时，哪些内容放在前面、顺序稳不稳定，本身就影响成本。第三章 3.10 讲这条约束怎么进入压缩决策。

第二卷 §10.1 对上下文的定义是：context 是投影，不是容器。投影（projection）一词借自事件溯源，指由持久记录推导出来的只读视图。本卷据此区分两个词：

- **历史**：持久化保存的完整消息与事件记录，是真相源。
- **上下文**：每一轮由历史算出来、实际发给模型的那一份，即由历史派生的视图，每一轮都可以重算。

第三章讲的压缩之所以只能改上下文、不能改历史，原因在这里。

### 步骤 2 · 预算检查

每个模型有上下文长度上限，称为**上下文窗口**（context window），以 token（模型处理文本的最小单位）计量。上限之内并非同等可用，这里有两个不同的现象：

- **上下文腐化**（context rot）：上下文整体变长时，模型表现随之下降。
- **中段遗失**（lost in the middle）：Liu et al. 2023 在多文档问答中发现，关键信息位于长上下文中部时，模型的准确率低于放在头尾（U 形曲线），降幅可超过 20 个百分点；较新的模型上这一效应有所减弱。

所以 harness 在每轮装配后检查占用率，并分级处理。常见设置（经验值，按场景调整）：60% 起给出提示，70% 左右触发压缩；历史越过它能占用的上限就必须先压缩再发请求，否则当前轮会超限失败。

这个上限由另一个量决定：给当前这一轮预留多少空间。模型这一轮要思考、要读工具结果、要输出，这些都占窗口。入门卷 §5.4 给的经验值是：200K 窗口下预留约三到四成；窗口更大时按绝对量预留，不按比例放大。预算检查算的是历史，预留管的是当前轮，两个数要一起定：窗口减去预留量，就是历史能占用的上限，压缩触发线不能高于它。预留三成，触发线就不能高于七成（第三章 3.2 按工作模式分层设触发线时，遵守的也是这条关系）。第二章 2.4 讲预留量设错时的具体后果。

### 步骤 3 · 压缩

压缩指把上下文里的历史消息替换为更短的形式，为后续轮次腾出空间。

常见的错误做法是只按时间压缩：保留近期消息，删除早期消息。错误在于时间只是价值的一个维度，决定去留的主要是内容本身。同样是十轮之前的两条消息，一条是用户设定的约束（"只订经济舱"），一条是某工具返回的 500KB 查询结果。删掉前者，模型下一轮就会违反约束；保留后者，只是持续占用空间。

正确做法是按内容价值分级，时间是其中一个因素（下表中"最近几轮对话"就是按时间给的高分）：

| 分级 | 内容类型 | 处理 |
|---|---|---|
| 最高 | 任务目标、用户设定的约束 | 完整保留 |
| 高 | 最近几轮对话 | 保留原文 |
| 低 | 早期的工具返回结果 | 替换为摘要 |
| 最低 | 过程性内容、重复信息 | 删除 |

价值之外还有第二条轴：**可复现性**。同样是早期的工具返回结果，一次本地读文件重跑一遍就能拿回原样，一次联网抓取重跑要花钱且内容可能已经变了，一次写操作根本不能重跑。这条轴决定的是清除的手段：可本地重跑的清成一行模板，要花钱重跑的走摘要保信息，不可重跑的不清。这条轴的标记在步骤 10 摄入时打，步骤 3 只读标记。

还有一类内容不按上表处理：**工具调用记录**。它的作用是留下调用记录，证明那次调用确实发生过。把它概括成一句叙述，模型会照着叙述的形态办事，下一轮改用文字描述工具执行，而不再发起调用。第三章 3.9 讲这种情况：工具调用与结果只能整对留或整对删。

一句话概括：**按价值压缩；时间只是价值的一个维度，不能单独决定去留。**

*图 1.3 · 三条同龄消息在两种压缩策略下的不同去向*

压缩不止"选谁留下"这一个决定。它有触发时机、有产物、有失败路径、有自身的预算，还是一处安全约束容易丢失的位置。它本身也有代价：改写上下文里已经发送过的前缀，会让前缀缓存从改动点起失效。第三章整章讲这些问题。

第二卷 §10.3 把压缩定义为一个事务而不是一次摘要。这里的事务借用数据库事务的原子性：压缩要么完整生效，要么完整回退，不留半压缩的中间状态。§10.4 据此给出四条压缩规则：

1. **失败回退**：中途失败就整体回退到压缩前。
2. **边界登记**：每次压缩登记版本号与边界位置，组装和恢复都按同一个版本取。
3. **约束不入压缩**：系统约束不放进可压缩的历史段，或压缩后无条件重新注入。
4. **配对修复**：工具调用与工具结果成对保留或成对删除，不拆开。

这四条在第三章的每一个故障里都有对应的失效位置。

### 步骤 4 · 筛选工具清单

工具清单进入上下文，模型据此决定调用哪个工具。清单越长，模型选错的概率越高：一个客服场景若把 40 个工具全部列出，其中只有 8 个与本场景相关，其余 32 个都在制造干扰（第十三章 13.2 估算过另一个场景：收窄工具清单这一项，按失败任务归因约贡献 1 个百分点，不到一个任务，没有做开关对比，只能当方向线索）。

所以 harness 按场景筛选清单，只把当前任务需要的工具给模型。工具在系统中注册，和工具出现在本次清单里，是两个独立的决定。入门卷 §5.3.8 把这件事做成机制，称为按查询取动态子集（业界常称工具检索，tool retrieval）。

还有一种做法是把目录与定义分开：清单里常驻的只有工具名与一句话描述，完整的参数定义等模型检索之后再加载进来。代价是多一轮检索，收益是几十个第三方工具的定义不占前缀；延迟加载的定义追加在上下文末尾，前缀不动，这是它比常驻清单省钱的第二个原因。

筛选还有一个与准确率无关的影响：在部分服务上，工具清单位于缓存的最前段（例如 Anthropic 的提示词缓存按工具清单、system prompt、消息的顺序排列），清单的成员、顺序、任何一条定义的文本变了，整份缓存从头失效。所以下发之前要做一次稳定排序，筛选带来的收益也要减去清单变动的代价。

### 步骤 5 · 注入提醒

发送请求之前还有一步：在特定条件满足时，向上下文追加一条临时规则提醒。执行这类插入逻辑的机制称为 **hook**：注册在流程固定位置、条件触发的一段代码。

以订票场景为例：业务规则要求取消订单前核对四个条件。这条规则写进 system prompt 的效果差：上下文越长，模型对开头那段规则的遵循率越低；而摘要或近期消息里如果有一句相反的转述，它离当前轮很近。两边都看得到时，模型更倚重靠近末尾的那句，这种近因偏好（recency bias）在实践中常见，程度因模型而异。

有效做法是让 hook 盯住取消调用本身。hook 看不到模型的意图，只能看已经发生的事；模型已经发出取消调用、harness 还没执行它的那一刻，是 hook 能看到的最确定的信号，不需要推测意图。第一次出现取消调用时先不执行，把四个条件作为这次调用的结果返回，模型核对之后重新发起才放行（提醒挂在工具结果上，载体的选法见第七章 7.2）。一次实践里用的是更弱的版本：取消照常执行，四个条件追加在这次调用的结果末尾。它对同一对话里后面的取消有效，第一笔已经来不及，只能靠 system prompt 里的常驻规则。**规则出现的位置离使用它的时刻越近，被遵循的概率越高。**

## 阶段二：模型调用

### 步骤 6 · 发送请求

上下文、工具清单、注入的提醒打包发出。模型的返回有三种形态，harness 必须分别处理：

1. 纯文本回复：直接进入阶段四
2. 工具调用请求：模型声明要调用某个工具及参数，进入阶段三
3. 推理内容加上述二者之一：开启深度推理模式的模型会先输出一段推理过程，再给出回复或工具调用

这一步还有一个请求参数要定：单次输出的 token 上限。与它相邻的步数上限由 harness 自己计数，不进请求。这两个数设错会直接削减模型的产出，第二章 2.1、2.2 单独讲。

### 步骤 7 · 拆分推理与回复

推理内容需要与最终回复分开处理。推理过程包含中间计算、被放弃的方案、自我修正，可能还有不宜外泄的信息。处置有三个去向：界面上折叠展示或不展示；写入日志供排查；写不写回消息历史，按第五章 5.3 的规则决定（取决于本次请求是否带工具清单，各家要求不同）。

有一种情况必须严格剥离：这条输出的接收方是另一个 LLM。评测系统里扮演用户的模拟程序（user simulator）、流水线里的下游 agent 都属于这种情况。推理内容如果原样传过去，接收方会把推理文字当作正式回复来理解，后续对话随之偏离。

推理内容还有另一类问题：训练格式的残留会混进正文，第五章 5.4 讲怎么识别和丢弃。

## 阶段三：工具执行

### 步骤 8 · 调用前校验

模型请求的工具调用不能直接执行，先过一串检查。我们的实现里这串检查有七道，顺序固定（部署时还可以再挂两道可选检查：必要信息是否齐全、用户是否明确要求了这项修改）：

1. 参数能否解析成一个对象
2. 参数是否符合该工具的 schema（参数的结构定义，含字段名、类型、取值范围）
3. 本次调用是否在权限范围内，需要确认的先问用户
4. 前置 hook 是否放行
5. 工具名是否存在
6. 动作层校验（例如写一个本会话没读过的文件）
7. 策略层校验

进入检查之前先按名字取工具定义，取不到就跳过第 2 道，到第 5 道被拒绝。

前两条顺序有依据。参数检查排在权限确认之前，因为一次畸形参数不该消耗用户的一次确认；schema 校验排在 hook 之前，是为了让 hook 看到的永远是一份合法参数。

工具存在性检查排在第 5 道，却推不出同样的好处。让"这个工具不存在"和"这个工具你不能用"回给模型两条不同的信息，只需要两种不同的错误类型，不需要特定的顺序；而排在权限之后，一个不存在的工具反倒可能先弹出一次用户确认，违背了第一条理由。按上面的逻辑，存在性检查应当提前：取不到工具定义就直接拒绝，不再进入后面的检查。实现里排在第 5 道是历史遗留：最初它排在所有检查之后，后来只往前挪过一步。另一个商用实现先查存在性，拒绝文案里列出可用的工具名。

校验要应对的一个高频现象：模型会生成 schema 里没有的参数。例如给只接受订单号的取消接口传入 `reason="health"`。直接透传，业务 API 报错，模型看到报错再试一次，一来一回消耗掉多轮预算。处置办法在第四章展开。

第二卷 §8.11 把工具契约定成 schema、语义、编排三层校验，本章的步骤 8 是前两层的入口；权限判定属第二卷第十一章，结果的可信边界属第二卷 8.10，分别对应本卷第十章（权限与安全）和第五章（模型协议与输出解析）。

### 步骤 9 · 执行

校验通过后执行。工具可能是 HTTP 接口、数据库查询、文件读写，也可能是另一个 agent。这是整个流程中唯一对外部世界产生真实影响的步骤，因此有三条硬约束：

- 超时控制：单个工具卡住不能拖垮整个流程。
- 错误语义明确：失败必须返回可识别的错误标记。模型误把失败当成功，后续每一步都建立在错误前提上。
- 中断语义明确：用户中止时，哪些工具该立刻停、哪些该让它跑完，要按工具分别决定；而且"派发之前被中断"和"派发之后被中断"必须记成两个不同的结果，因为它决定了事后能不能判断这个动作有没有发生过。

第二卷第八章整章讲这一步的记录：意图、授权、执行、结果四段各自留痕。崩溃之后，重复与丢失只能二选一：不确定就重做，动作可能执行两次，这是至少一次（at-least-once）；不确定就不做，动作可能一次也没执行，这是至多一次（at-most-once）。恰好一次（exactly-once）在投递层做不到，只能靠幂等让处理结果在效果上只发生一次。第九章（并发、取消与中断）会给出这条契约在中断和崩溃场景下的实际失效方式。

### 步骤 10 · 结果处理

工具结果在回到模型之前先做三类处理：

1. 体积控制：大结果做摘要或外置。500KB 的 JSON 原样放进上下文，几轮之内窗口耗尽
2. 外置存储：完整结果存入独立存储，上下文里只放摘要和一个引用标识，模型需要细节时通过标识再取
3. 脱敏：结果中的手机号、证件号等敏感字段先遮罩

两种做法的对比：原样返回 1000 条记录，模型无法有效处理；返回"共 1000 条，前 3 条如下，完整结果的引用标识为 abc123"，模型掌握了规模，需要时再取细节。入门卷 §5.6 把这个结构称为 stub 与 body 分离，并给了 stub 的经验体量：200 字符上下。

外置有一条容易漏的配套要求：**取回的入口必须写在模型看得见的位置**，否则存了也取不回。具体写在哪几处，以及一次存储从上线起没被读过的实际失败，见第三章 3.9。

还有一个时机问题：体积控制在结果摄入的那一刻做，不等压缩。等到压缩再处理，这条结果已经完整进过一次上下文，也已经计过一次费。

这里有一个常见的错误处理方式：不做摘要，直接按长度截断。它的代价比看上去大，第二章 2.3 单独讲：截断会截在结构中间、截掉最重要的结尾，而模型不知道自己看到的是残缺内容。

## 阶段四：回写与循环

### 步骤 11 · 回写上下文

处理后的结果作为工具结果消息追加进上下文。此处有一个格式问题：各家模型对工具结果的消息格式要求不同，有的要求携带调用标识字段做关联，有的要求 JSON，有的要求纯文本。harness 在此做协议适配，把结果转换成当前模型要求的格式。助手消息原样回写，含推理内容时按第五章 5.3 的规则处理。回写后要保住配对：助手消息里每个工具调用都要有对应的结果消息（第二卷第六章 6.7）。

这一层的差异比看上去大，第五章会说明为什么"一套适配层通吃各家"的目标要放弃。

### 步骤 12 · 循环判定

结果回写后，harness 判断下一步走向，常规出口有四个：

1. 继续：再次调用模型，回到步骤 6，模型基于工具结果决定后续动作。
2. 本轮不再请求工具：模型这一轮只给出文本回复，没有发起新的工具调用，这个回合结束，回复交给用户。它不等于任务完成，模型也可能是在提问或卡住了。
3. 转人工：模型发起移交请求。
4. 强制终止：达到轮数上限（第二章称为步数上限）。

此外还有两个异常出口，同样要有明确的去向：

5. 中断：用户按了停止，或上层取消了这次 run。
6. 出错：模型调用或工具执行遇到不可恢复的错误。

出口 1 构成的循环有一个通用名称：**ReAct**，取自推理（Reason）与行动（Act），循环里还有第三步观察。模型推理后发起工具调用，harness 执行并回写结果，模型观察结果再推理。循环持续到其他出口中的某一个被触发。

![](../diagrams/fn-flow-01-react-loop.png)

*图 1.5 · 循环判定的四个出口与 ReAct 循环*

入门卷 §5.1 强调 Agent Loop 是模型的思考结构，而不是一段 while 代码；并指出在生产实现里，循环在哪些位置决定继续下一轮、在哪些位置终止，都是需要单独设计的部分。第六章讲的就是这些出口不完备时会发生什么：循环停不下来、空转、卡住。出口 4 的阈值设小了会有另一类后果：任务在半途被硬停，见第二章 2.2。出口 5、6 的收尾见步骤 13 和第九章。

### 步骤 13 · 收尾

流程终止后的四件事：

1. 记忆抽取：从这一回合的对话中提取值得长期保存的信息，写入持久记忆
2. 审计：全部工具调用的参数、结果、时间戳写入日志
3. 状态保存：完整消息历史与当前状态存入数据库，供后续恢复
4. 资源清理：关闭文件句柄，终止残留子进程

这四件事之间有顺序，也会停在中间。检查点已经写入磁盘而审计记录追加失败，是一种要单独定义错误类型的状态。把它当成普通异常吞掉，事后既看不出这次收尾做到哪一步，也判断不出该按已完成还是未完成恢复。

这一步最容易被省略，而事后排查问题依赖的正是这里留下的记录。更要紧的是：**它同样要在异常退出的路径上执行**。第九章会说明为什么"用户按停止"和"进程崩溃"这两条路径上的收尾，比正常结束时的收尾更重要。

## 全卷地图

回看全程：**模型只在步骤 6 做决策，其余十二步全部由 harness 的代码承担。** 同一个模型，harness 不同，任务通过率会有明显差距。第十三章 13.2 的航空客服场景里，同一个模型、同样开着推理模式，按默认配置直接运行通过率是 72%，加上整套 harness 机制升到 92%。13.2 会说明这 20 个百分点不能全记在机制名下，能归到机制的那部分，就产生在这十二步的质量上。
