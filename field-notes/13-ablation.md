# 十三、消融、负贡献与迭代

评测给出总分，回答不了"这个分数里每个机制占多少"。要归因，用消融。

这一章讲三件事：怎么用有限的实验次数摸清全部机制的贡献；怎么找出那些看着有用、实际有害的机制；以及多轮优化要遵守哪几条规则。

入门卷 §7.4 把消融组织成三个阶段，并给出统计上的基本要求。本章是那套方法的实践记录，重点在它最该产出的一类结论：**代码正确、系统效果有害的机制**。

## 13.1 三轮消融摸清整套机制

消融（ablation）的定义很简单：关掉一个机制、其余不动、重跑评测，开关前后的分数差就是这个机制的贡献值。正的说明有效，负的说明有害，接近零说明可有可无，但要先排除它与别的机制互相替代（冗余，见 13.2）。本章的贡献值都按留一消融（leave-one-out ablation）的口径定义，即其余机制都开着时关掉这一个造成的损失。机器学习里的"留一法"通常指留一交叉验证（LOOCV），与这里不是一回事。从零开始逐个加入（add-one）得到的是另一组数，两者不能混用。

机制有几十个，全组合是二的 n 次方次实验，运行不完。按三轮缩减：

**第一轮按大类整组关。** 上下文管理一组、工具编排一组、安全策略一组、行为规范一组，整组开关，先确定哪些大类有影响。这一轮只需要几次实验，产出的是方向，不是精度。整组关掉分数不变，还有一种解释是组内正负抵消，这样的组第二轮不能跳过。安全策略组不按通过率计算，它的指标是拦截率与误伤率，按通过率算多半是负数。

**第二轮在有影响的大类内逐个关。** 无影响的大类整组跳过，省下的实验就用在这里。这一轮运行几十次。

**第三轮测两两交互。** 前两轮假设机制之间互不影响、效果可以相加，实际未必。甲和乙一起开的效果可能高于两者单独贡献之和，这是正交互（协同）；也可能低于，这是负交互。挑贡献最大的几个两两组合验证，这一轮十几次。

三轮合计几十次实验，可以对整套机制做一遍粗筛：大类整组筛过，有影响的大类逐个测过，交互只测了贡献最大的少数几对。产出是一张贡献排序表，处置规则如下：

- 正贡献保留，并精调参数；
- 负贡献关闭或修改；
- 接近零的，按维护成本决定去留。

处置后重跑、重排，直到分数在这批样本能分辨的范围内不再提升为止。这里的"收敛"只是停止条件，不保证找到了最优组合。

还有一条关于开关本身的准入规则。能力开关表是可以单独关闭、关闭后系统仍能完成同一类任务的机制清单，只有这类机制适合做消融。例如调用前规则注入、工具清单收窄，关掉之后 agent 仍在做同一件事，只是少了一项辅助，可以放进表里。反过来，关掉之后系统的性质就变了的机制（比如会话持久化、工具调用循环本身），不要做成开关：它没法消融，因为消融要求开关前后的两个版本可比。

入门卷 §7.4 对这套流程有两处补充值得照做：

- 第三轮的组合数按平方增长，十六个机制就是一百二十对，成本高到必须先用筛选设计（screening design，例如部分析因设计）排掉明显无交互的对。
- 贡献值是否显著，要用配对检验判断（同一批任务开关前后的结果逐一配对；二元的通过/失败结果用 McNemar 检验，或用配对 bootstrap），不要看固定的百分点阈值。小样本下的两个百分点可能只是噪声。

## 13.2 贡献分解：总量实测，分项估算

航空客服场景的实测，评测集为五十个任务，每个任务运行一次。有三个数可以对照：模型按默认配置直接运行，通过率 72%，这一配置下推理模式由服务商默认开着；公开榜单上同一模型开启推理模式的成绩是 82%；加上整套 harness 机制，通过率 92%。

这三个数连不成一条"先加推理、再加机制"的提升链。82% 是榜单提交方用另一套设置跑出来的：扮演用户的模型不同，每个任务跑四次取平均，只能当参照。72% 与 92% 是同一批五十个任务上的两次运行，推理模式都开着。逐个任务配对，十个任务由失败转为通过，没有一个反向翻转，配对检验下这 20 个百分点是显著的。两次运行走的是两套评测管线，扮演用户的模型默认不同，轮数上限的算法也不一样，所以这 20 个百分点是整套配置变化的结果，不能全记在机制名下。

各机制在其中占多少，没有逐项开关重跑。下表是按失败任务归因的估算：对照修复前后由失败转为通过的任务，逐个判断是哪项改动修好的，再折算成"从完整配置里去掉这一项会损失多少"，口径与留一消融相同。

| 机制 | 估算贡献（百分点） |
|---|---|
| 工具协议修复（第四章 4.2 的 schema 引用内联） | 约 +10 |
| 调用前规则注入（第七章 7.1） | +2 到 +3 |
| prompt 执行规则（强制数字回复等） | +1 到 +2 |
| 工具清单收窄 | 约 +1 |

工具协议修复一项有直接记录：修复前，三个写工具的调用一次都没有成功；修复前后由失败转为通过的任务里，有六个只能归到这一项。其余三项都在一到三个百分点，相当于五十个任务里的一两个任务。按 12.10 的功效估算，五十个任务各跑一次，最小可检测效应（MDE）约二十个百分点，这三项就算做了开关重跑也分辨不出来，只能当方向线索。几项估算也不能相加：归因时，一个任务可能同时记在几项改动名下。

![](../diagrams/fn-comparison-13-waterfall.png)

*图 13.2 · 通过率的来源：总量实测，分项估算*

真做了逐项开关，贡献值加起来也往往不等于总提升，这是留一消融本身的性质。留一消融量的是"其余机制都开着时，再关掉这一个损失多少"。同一批任务可能同时依赖几个机制：既要工具协议正确，又要规则在调用前注入，缺任何一个都过不去。逐个关的时候，这批任务在每个机制的账上各算一次，加起来就会超过总提升。超出的部分来自机制之间的交互效应（interaction effect）。两个机制的情形下，交互项等于 f(甲乙) + f(空) − f(甲) − f(乙)，其中 f 是只开括号里那些机制时的通过率：为正是正交互（协同），为零是可加，为负是负交互。

方向不要弄反。负交互会压低贡献和，它有两种来源：

- **冗余（互相替代）**：两个机制各自都能救同一批任务，关掉任一个，另一个仍然接住，两个贡献互相遮蔽而变小。举个数：10 个任务，甲修好 1 到 6 号，乙修好 4 到 9 号，一起开通过 9 个；关甲掉到 6，关乙也掉到 6，两个贡献各 3，和是 6，而总提升是 9。
- **干扰（互相冲突）**：两个机制一起开时互相妨碍，比如两条注入的规则给出矛盾的要求，单开各自有效，同开反而变差。

正交互抬高贡献和，负交互压低贡献和。

工具协议修复还有一层特殊地位：它是其余机制起作用的前提。schema 坏掉时，三个写工具的调用全部失败，调用前注入的规则再对，也没有一次正确的调用可以保护。这类前置机制一旦失效，建立在它上面的收益跟着归零，所以它需要单点监控和回归用例。要把这种依赖测出来，得补测"关掉工具协议修复、只开某一项"的组合。

反过来，如果所有贡献值之和恰好等于总提升，说明这几个机制在测得的精度上表现为可加；这不能证明它们互不影响，正交互和负交互也可能恰好抵消，要确认得补测两两组合。

**贡献值之和高于总提升，说明以正交互（机制互相依赖）为主；低于总提升，说明以负交互（冗余或干扰）为主。两种都正常，先分清是哪一种再读数。**

## 13.3 负贡献：代码正确，效果有害

消融最有价值的产出是负贡献，即关掉之后分数反而上升的机制。负贡献分两类，判断依据是关掉前后结果翻转的那些任务的失败轨迹：

- 失败集中在机制的某一个分支上，是实现缺陷，修好再测；
- 失败均匀分布在它覆盖的全部任务上，是设计本身有害，删掉。

下面三个案例都来自工程记录与复盘，没有做开关对比，给不出贡献值；列在这里是因为它们是同一种形态。

**参数容错。** 模型传来的工具参数解析失败时，代码把它换成空对象，照常调用工具；解析成功但不符合 schema 时，也不做校验。这段写法看起来是个周到的容错设计，在代码里留了四个多月，直到一次专项代码审计才被发现。

它的害处是遮蔽了模型本该收到的错误信号。模型传错参数，调用照样执行，返回一个表面合理、实际错误的结果；模型收不到报错，也就不会修正，错误一路持续到任务结束。修法是把两种情况都作为错误回给模型，写明哪个字段、期望什么、收到什么，并在权限确认和执行之前拦下。报错回到模型手里，模型能自己修正：一次评测里，预订工具的调用先后三次因缺必填字段被拒，模型按报错逐个补齐，第四次调用成功。第四章 4.4 规定缺失的值不代填、报错回给模型，依据是这条工程记录。

![](../diagrams/fn-flow-13-autocomplete.png)

*图 13.3 · 参数容错开与关的两条路径*

**覆盖全生命周期的 hook 体系。** 第七章 7.7 提到的过度设计。工程记录显示：排查成本明显上升，而在评测上看不出收益。这一例没有做开关对比，结论来自工程记录，不是消融测得。

**前端状态缓存。** 第八章 8.3 的快照问题：为性能加的缓存带来一致性故障，用户看到过期状态。工程复盘的结论是得不偿失；这一例同样不是消融测得。

三个案例的共同点是：**代码逻辑正确，系统效果有害。**

这类问题单元测试发现不了，日常代码评审也容易放过。单元测试验证的是"代码逻辑符合设计"，消融验证的是"这个设计在真实系统里有益"，两个命题不同，第一个成立不蕴含第二个成立。

发现负贡献最可靠的办法，是在真实模型、真实工具链、真实任务上做消融。工程复盘和专项审计能发现一部分（如上面三例），但要给出贡献值，仍要回到开关对比。

由此得到一个对全部工程经验的重新定位：**前面十一章的每一条有效做法，本质上都是一条待验证的假设。** 参数容错在被审计发现之前，同样被当作合理设计留在代码里。一套积累下来的经验条目里，通常混着若干条这样的"假阳性"：被判为有效，实际有害（沿用评测中以"判为通过"为阳性的约定）。不做消融，它们会一直当作最佳实践传下去。

## 13.4 迭代中的规则

消融给出单轮结论，多轮优化还需要几条组织规则。这些规则看起来像洁癖，实际都有硬理由。

**每轮只改一个变量。** 常见的破坏方式是顺带修改：改甲时发现乙也有问题，一并改了。同时改两处，分数变化无法归因到任何一处，整套消融框架失去前提。每轮只改一处，是为了避免混杂（confounding），即两处改动的效应搅在一起、无法分开；确实要同时评估几处改动时，就做析因设计（factorial design），不要只比全开和全关两组。范围之外的发现记录下来，本轮不动手。语料指纹与代码指纹（12.7 给每次运行记录的溯源信息）是这条规则的机器证据：两轮之间语料指纹应当不变，代码指纹的差异应当恰好是本轮那一处改动。多出任何别的差异，这一轮的对比就不成立。

**调参只看开发集，留出集只做对照。** 反复对着同一套用例调 prompt 和规则，分数越调越高，上线后问题却很多，这就是入门卷附录 F 列出的反模式"对固定测试集过拟合"（AP20）。做法是把用例分成开发集和留出集：日常迭代、消融、调参只看开发集；留出集不参与任何调参决策，每次改动前后都跑，只用来检查开发集上的提升是否还在。线上新出现的失败按 12.7 登记来源，回流为判例，补进开发集。

**同一问题修两轮仍失败就停。** 连续修四五轮的常见结局是改动越来越乱，最后发现原因在完全不同的位置。两轮无效就停下来，重新提出原因假设，换方向验证。注意与第六章 6.1 对重复失败工具调用的熔断区分（借用熔断器的说法，只有打开，没有冷却后的半开试探）：那是 agent 的运行时机制，这条是开发者对自己的约束。两者依据的其实是同一条经验：**同样的动作重复两三次仍无进展，说明假设错了，而不是力度不够。**

**修复必须通过编译（或构建）、测试、类型检查三项。** 三项全部通过才算修复完成。在"改完了应该能运行"的状态下宣布完成，是缺陷报告的主要来源。

**完成要分级定义。** 做完了分四级：结构完成、数据填充完成、格式验证通过、可交付。每级有检查项，报告进度时报到级别。缺了分级，"完成"一词在不同人口中含义不同。agent 身上也是一样：模型说的"完成"是结构完成，用户理解的是可交付，打开演示文稿发现三张图没生成、五处格式错，两边说的都是"完成"。

**用结构代替提醒。** 以上规则写在文档里会被遗忘，这和规则写在 system prompt 里被模型遗忘是同一个现象。可靠的形式是结构性约束：埋点、配额、超时、CI 门禁，让违反规则的路径在机制上走不通。

最后这条值得多说一句。本卷反复出现的一个对称是：**对模型有效的办法，对人也有效；对人无效的办法，对模型也无效。** 写在开头的规则会被遗忘、语气加重没有效果、要在使用的那一刻给出提示、能用机制约束的不要只靠自觉。这几条在第四章讲工具描述、第七章讲提醒注入、这一章讲迭代规则时，是同一句话的三个版本。

## 本章与前两卷的对应

入门卷 §7 的 Harness Lab（本书对"用评测、消融、调参迭代改进 harness 的外层工作台"的命名）把优化循环组织成观测、打分、消融、调参、迭代五层，本章是其中消融与迭代两层的实践。§7.4 的三阶段消融、交互项、统计上的基本要求在 13.1 全部对应；本卷补的是贡献和与总提升不相等时怎么读：高于总提升以正交互为主，低于以负交互为主。§7 里"局部正确、全局有害"的判断，在 13.3 有三个工程案例。

入门卷 §11 的实施 Spec 里有一项机制准入检查，每个进默认配置的机制都要过一遍。13.3 强调了其中一条准入项：**它在端到端消融里是正贡献吗**。代码正确、测试通过、评审通过，都不能替这条回答。

入门卷 §9 的控制论四原则收束全书，13.4 的迭代规则是它在开发流程上的对应做法：控制变量、有反馈、有边界、可收敛。

第二卷 §14 讲从零构造一个最小但完整的 runtime，并要求验收看的是标准故障包（一组预设的故障用例，用于逐项判定 runtime 是否满足契约）全部通过，而不是"能运行"。13.3 说明这份故障包还该加一类用例：**那些代码正确但系统有害的设计**。它们不会在故障包里失败，要靠消融或专项审计才显现。
