# 八、状态、持久化与崩溃恢复

这一章讲状态的三个问题：它有几份、崩溃之后能不能接着运行、恢复出来的内容对不对。

第二卷第六、七两章是这个主题的完整论述——状态分五类、真相只有一份、checkpoint 保存什么和明确不保存什么、恢复的七步时序。本章不重复那套结构，只给八个具体的失效方式，多数都对应那套结构里的一条判据。

## 8.1 会话状态的全部字段要走同一个同步函数

会话状态不是一个值，是一组：会话标识、工作目录、配置文件位置、元数据。

切换会话的代码路径通常不止一条——从列表点选、新建、以及某些副作用触发的自动切换。一个真实的缺陷是三条路径里有一条只同步了会话标识，没同步工作目录。后果是切换之后 agent 仍在读上一个会话的配置，而界面显示的是新会话。这类失效完全静默：没有报错，功能都在，只是行为对不上，用户以为是模型不听指令。

同类问题还有一种形态：为任务创建独立工作目录时没有把配置文件一并复制过去，于是推理模式、工具禁用清单这些设置整轮未生效。测出来的结果和预想的配置无关，而日志里看不出任何异常——**你以为在测配置 A，实际运行的是默认配置**。

有效做法是把会话状态的全部字段收进一个同步函数，所有切换路径调用同一个函数；工作目录初始化时显式复制配置，并验证生效。

判据：**状态是一组的时候，同步入口必须只有一个。** 第二卷 90-artifacts 的状态登记表（A）要求逐项登记每份状态的属主与作用域，这条缺陷的原因正是没有一份清单说明切换会话要同步哪几样东西。

## 8.2 恢复会话时要重建 system prompt

保存会话时对 system prompt 做过处理——脱敏、裁剪、按当时的环境拼装。

恢复时如果直接加载保存的那份，agent 拿到的是一份残缺或过时的 prompt：脱敏掉的部分没恢复、当时的环境信息已经变了。它照常工作，决策却建立在错误的前提上。

有效做法是脱敏与恢复配对设计，恢复路径显式用当前版本替换 system prompt 或首条塑形消息，而不是沿用存档。

第二卷 §10.8 讲恢复要按崩溃前模型实际看到的压缩版本重建历史；本节是同一判据的另一半——塑形片段也要按崩溃前的版本恢复，而这一半那里没有展开。§11.6 讲恢复状态不等于恢复授权。三条合起来正好覆盖本节：**恢复的是状态，不是当时的上下文，更不是当时的权限。**

## 8.3 状态以后端为唯一权威

前端为省一次请求，把状态快照缓存在本地。

切换页面或标签之后快照过期，界面停留在旧状态。最典型的表现是长任务：用户切走再切回来，看到的是"生成中"，而后端那一轮早就结束了。用户会一直等，或者以为系统挂了去重启。

这个缓存在第十三章的消融里被定性为负贡献——为性能加的机制带来了一致性故障，收益远小于代价。

有效做法是后端为状态的唯一权威来源，前端每次进入都重新拉取，后端维护足够的字段（最近消息、待处理输入、是否运行中）让前端能一次取全。

判据：**多处持有同一份状态时，性能优化的代价是一致性。** 第二卷 §1.6 的真相源分叉破坏实验，测的就是这类设计。

## 8.4 运行时注册的资源要持久化

运行中动态注册的工具、动态加载的能力，通常只存在于内存。

进程重启后它们消失，而依赖它们的会话被恢复了。于是出现一个矛盾状态：历史里有对某个工具的调用记录，当前清单里没有这个工具，模型看到自己上一轮用过的工具不在了。

有效做法是会话元数据预留结构化字段，把运行时注册的内容一并持久化，恢复时重新注册。

这条有一个对偶：同样要明确列出不该跟着备份或迁移走的状态，而且要按路径分。去重用的随机数，重启与迁移都不带，带上会把正常请求误判成重复；待履行的投递义务与待唤醒记录，同一实例重启后必须恢复，复制到另一个实例时不带——原实例还活着，两边都会投递。持久化清单与排除清单要一起维护，排除清单按路径写两列。

判据：**凡是运行时才产生的东西，都要问它在重启之后还在不在。**

## 8.5 长流程要逐环节存档

多环节的流水线任务如果不存中间结果，前期一处小错就要整体重跑。

一个真实场景是九个环节的文档生成流程，中间某一步的输入有个错别字，发现时已经运行到第七步，只能从头再来两小时。这类返工的代价不只是时间，还有 API 花费和用户的耐心。

有效做法是每个环节的产出落盘，重跑时跳过已完成环节；单环节失败降级处理（例如图表生成失败改为文字说明）而不是整体失败。

第二卷第七章把这件事讲成了两条技术路线——存档点与账本重放，并给出它们各自不管的部分。本节只是那两条路线里最朴素的一种，但它解决的是最常见的问题。

## 8.6 崩溃后要重建工具调用的配对

前面五节讲的是恢复得对不对，这一节讲能不能恢复。

场景：模型发起了工具调用，工具还没返回结果，进程崩溃。重启后恢复会话，历史里留下一条孤立的工具调用消息，没有对应的结果消息。

后果不是体验问题，**是可用性问题**：下一次推理请求会因为消息结构非法被 API 直接拒绝。这个会话从此发不出任何请求，用户重试多少次都一样，除非删掉整个会话。

有效做法是从持久化的原始消息里重建缺失的工具结果消息，按三级降级：能找到真实结果就用真实结果；只有部分输出就用部分输出并标注不完整；什么都没有就合成一条错误说明，告诉模型这次调用因中断未完成。

判据：**恢复的第一要求是恢复出的消息序列合法。** 内容对不对是第二位的——内容不对模型还能继续工作，结构不对连请求都发不出去。

## 8.7 读到不完整状态就沿用旧值

写文件的过程中崩溃，会留下一个截断的文件。

危险的不是截断本身，是读取端的处理方式。一种常见的最坏组合是：读取时解析失败，静默当成空值；随后的写入把这个空值原地覆盖回去。于是一次崩溃变成了永久的数据丢失，而全过程没有任何一行错误日志。

有效做法是两件事配对。**写用原子模式**：先写临时文件，写完再重命名，重命名是原子的，读取端要么看到旧的完整版本，要么看到新的完整版本，不会看到半截。前提有三条：临时文件与目标在同一文件系统；持久要求下重命名前对文件、重命名后对目录各做一次 fsync；Windows 上要用带替换语义的接口，目标被占用时会失败，失败要按未写处理。**读到不完整就沿用旧值**：解析失败不当成空，放弃本次更新，保持上一次的有效状态并记录警告。

沿用旧值之外还应当再做一件事：把损坏的那一份改名留下来。文件名带上时间戳、移到一边，不让它被下一次写入覆盖——沿用旧值意味着下一次写入迟早会写到同一个位置，损坏的内容一旦被盖掉，事后就查不出它当时坏成什么样。隔离动作自己失败时要抛出专用错误，不能吞掉，否则这一层保护同样是静默失效。这与 12.3 的日志从第一行代码开始存全量是同一条理由。

对于流式产生的状态（例如一段被起止标记包裹的输出），判据是标记不完整就整段放弃，不要尝试修复。

判据：**静默当空加原地覆盖，是数据丢失最常见的组合；原子写防损坏，沿用旧值防误判，两半都要有。**

## 8.8 降级要保住自救入口

启动阶段的失败处理有一个容易走极端的地方。

一个真实场景：数据库被锁或数据量超限导致启动失败，程序按严谨的做法抛异常退出。结果是用户完全无法进入——**连删除损坏数据的入口都打不开**，因为删除功能也在这个应用里。用户唯一的办法是手工找到数据目录删文件，而多数用户不知道它在哪。

有效做法是对特定的几种失败做窄范围容错：记录日志，以零条历史继续启动，让主界面和删除功能仍然可用；其余任何错误依旧当作致命。

注意这里的分寸——不是启动失败一律降级继续，那会掩盖真问题；是**只对那些降级后用户能自救的失败降级**。

判据：**宁可功能残缺，不能让用户失去修复它的能力。**
